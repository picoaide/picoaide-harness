# DSH 0.2.0-rc.2 评估：官方桌面端、定时任务、语音输入与升级兼容性

日期：2026-09-29 · 基线 pin：`dsh-v0.1.7-rc.2`（`477b4f4205`）· 目标：`dsh-v0.2.0-rc.2`（`639ed01539`）
性质：**只读调研 + 评估**，未升级、未改产品代码。本文只回答四件事：官方新版是什么、有什么启发、能替换我们哪些自研插件、升级是否兼容；另附一节回答"为什么我们客户端没有语音输入"。

## §0 结论先行（TL;DR）

1. **官方最新 = `dsh-v0.2.0-rc.2`**（2026-09-29T09:42Z 发布，npm dist-tag `next`）。npm `latest` 仍是 **0.1.7-rc.2 = 我们当前的 pin**。距我们 448 提交；包集**只增 4 个、零删除**；**会话格式仍是 v4**（我们 pin 也是 v4）⇒ 无世代迁移、回滚只需换二进制。
2. **官方桌面端已经公开分发**了（本次实测）：官网 `/en/download/` 直链 `download.deepseek.com/desktop/dsh-latest-macos-arm64.dmg`（369.8MB）与 `…-windows-x64.exe`（289.3MB），更新 feed `dsh-desk/feeds/<target>/nightly*.yml` 公网可读。**但只有 mac-arm64 / mac-x64 / win-x64**（builder 里的 Linux 段在更新侧不可达），且**只有 nightly 一个通道**；**无渠道/白标/企业面**（`git grep whitelabel|tenant` 对 `apps/desktop` 零命中）。
3. **"定时任务"不是 0.2.0 的新能力**：`packages/schedule/schedule`、`packages/client/ui-schedule`、`packages/context/time-context` 早在 2026-08-13 就进了上游；**我们的 pin 里三行已经写在 web-app 组合中（`disabled: true`），三个包也已经在我们的安装树里**。0.2.0 只是把它从"web 组合里的禁用行"搬成"可选 bundle（默认关）"，并把投递文案改成明确标注的用户定时消息。⇒ **今天就能开；升级反而多一步**（见 §5.2 的静默失效风险）。
4. **升级后几乎没有可以替换的自研插件**：上游 Schedule 的语义是**提醒**（把一条 user 消息投回**原会话**、冷会话会被唤醒），我们的 `packages/host/cron` 是**作业**（定时**新建**会话跑 agent，带工作区/预设/权限钉住、owner 过滤、执行历史、手动运行、DST 缺口留痕）。二者不是同一件事，**替换 = 丢掉"定时执行"**（详见 §4）。
5. **兼容性：技术上可升**——npm 上 150 个声明包在 `0.2.0-rc.2` 全在、上游包集 0 删 4 增、`platform-modules.mjs` 逐字不变（新增 0 条）、会话格式仍 v4（**回滚只需换二进制**）、我们 patch 的 15 个行 id 全部还在、**8 个补丁里 7 个可原样沿用**（只有 `dsh-sandbox-windows-acl` 因目标产物**文件名**从 `lib/types-DxezulnA.js` 变成 `lib/types-Cl_DXjhk.js` 而必须重切，内容锚点未变）。
   **但有一条会当场打红门禁的 P0**：0.2.0 新增 `desktop-product-telemetry` + `product-analytics` 两行，`disabled` 判据是"profile 名 == `desktop`"（正是我们，`profile.ts:1249`），而 `desktop-product-telemetry` 的 `serviceVersion: process.env.DSH_CLIENT_VERSION` 是 schemastery `.required()`，该变量我们全仓零设置 ⇒ 行构造抛错 ⇒ `verify-profile-boot.mjs` 的 `unimportable` 判据红。反向同样危险：一旦补上该变量，分析就**默认开启且无用户开关**，会把 device_id/user_id 发往**上游自家默认 OTLP 采集端点**（端点常量见 `packages/host/product-telemetry-otel/src/index.ts` 的 `endpoint` 默认值）。**处置：显式 disable 这两行 + 登记进 `mustStayDisabled` 双向对拍名单**。
6. **语音输入**：代码与原生库**已经在我们发布的客户端里**（实测 2.8.2-beta.2 Linux 包：`app.asar` 内 89 条 voice/speech/sherpa 条目 + `app.asar.unpacked` 里 linux-x64/arm64 两份 sherpa 原生库共 **~71MB**），缺的只有四件事：**装配**（3 行）、**`pluginNavigation` 服务**（我们禁用了 `ui-plugin-manager`，而语音 UI 插件 `inject` 它）、**麦克风权限**（主窗口只放行剪贴板；macOS 无 usage description / entitlement）、**模型**（int8 228MiB，走宿主 Node 拉取，被我们"默认禁代理"策略挡在认证代理网之外）。

## §2 官方 0.2.0 到底做了什么

### 2.1 桌面端（最大增量，`apps/{desktop,desktop-host,cli}` 119 文件 +3814/−306）

- **已公开分发 + 固定直链**：新脚本 `upload:latest:*` 产出单一固定键 `desktop/dsh-latest-{macos|windows}-{arch}.{dmg|exe}`（`apps/desktop/scripts/desktop-upload-plan.ts:282-287`）；README 明确要求部署侧配 revalidation/purge（覆盖式对象）。实测：官网下载页两个按钮直链上述两个对象（200），nightly feed 指向 `0.2.0-rc.2`。**公开分发起点早于 0.2.0**（`…0.1.7-rc.2-mac-arm64.zip` = 200，`0.1.5-rc.2` = 404）。
- **内置 CLI 运行时 + 原生菜单「Manage dsh Command…」**（PR #5288，24 提交）：`apps/desktop/cli/{dsh,dsh.cmd,link-entry.c}` 用 `ELECTRON_RUN_AS_NODE=1` 跑 `app.asar` 内的 `dsh-desktop-host/lib/cli.js`；macOS 装 `/usr/local/bin/dsh`（`linkat` 保 inode + 可逆收据 `.dsh-desktop-command.json`），Windows 操作 HKCU `Environment\Path`（独立 owner 子键 + 命名 Mutex + 快照 `ESTALE` 闸）；`apps/cli/src/args.ts:195` 只在该路径放开 `--profile desktop`。⇒ 用户**无需自装 Node/pnpm** 就能用 `dsh`。
- **登录 shell 环境**（PR #5393）：`apps/desktop/src/login-shell-environment.ts`，`<shell> -ilc` 读一次环境并**全量覆盖**继承环境（只排除 `PWD/OLDPWD/SHLVL/_` 与 `DSH_*`/`ELECTRON_*`），超时默认 10s 可配，应用退出时 abort 杀进程组。修的是"图形入口启动缺 PATH/代理"。
- **macOS 麦克风签名权限**（PR #5323）：新增 `apps/desktop/scripts/macos-entitlements.plist`（含 `com.apple.security.device.audio-input`）+ `NSMicrophoneUsageDescription`，同时用于 `entitlements` 与 `entitlementsInherit`；配套 `microphone-permissions.ts` 只放行**主 frame 的 audio** 请求（`systemPreferences.askForMediaAccess`）。
- **产品分析默认开启**（PR #5136）：新包 `client/product-analytics`，README 逐字 "defaults to `true` … There is no user-facing control"；主机侧 `host/product-telemetry-otel` 的 `endpoint` 默认值是**上游自家采集端点常量**（见该包 `src/index.ts`，本文不抄主机名），字段 `device_id/user_id/os_version/app_version`（显式声明不含 hostname/用户名/序列号）。
- **Windows 沙箱 ACL 一次完成诊断+修复**（PR #5203/#5432，该包 +1970/−15）：新 PowerShell 诊断脚本 + 技能文档 + 新 e2e。
- 其他：全屏 IPC 扩到 Windows；`koffi` 由 `^3.1.0` **钉成 `3.1.1`**；更新文案补版本/下载/重试说明；**Electron 版本在本区间未变**（仍 `^44.0.0`）。

### 2.2 定时任务（Schedule）

- **能力本体没变**（`packages/schedule` 在两 tag 间只有 5 类改动：reminder framing 文案、三个包的 `locale/*.json` + export、新增 `experimental/schedule-bundle`、web-app 组合与依赖里移除三行/三包、`OPTIONAL_BUNDLES` 收录新 bundle）。
- 语义：6 种选择器（`after/at/every/daily/weekly/cron`）、`title` 必填 ≤120、daily/weekly/cron **必须显式 IANA 时区**、DST 缺口跳过/重叠取较早、**投递到原会话**（冷会话会被唤醒）、同一会话同轮多次触发**合并成一条消息**、硬删任务、投递历史默认 30 天/200 条、4 个工具（`schedule_create/list/update/delete`，update 带乐观并发冲突码）。
- 成本（上游自己认账，`packages/experimental/schedule-bundle/README.md:68-76`）：开启后**每个 live root Agent 的每次请求多 4 个工具 schema**，且 `time-context` 会给**每个 eligible step** 追加一条 **durable user message**（默认最小间隔 10 分钟）。

### 2.3 其他值得知道的

- **异步问答（实验）**：`ui-user-questions` + `interaction/user-questions` + `tool-ask-user` 共 +5600 行；0.2.0-rc.2 说明"等待超时后 Agent 可继续独立工作，用户仍可稍后回答"（需手动配置开启）。这条直接影响我们的 `desktop-loop-notify`（"提问"信号）与用户闸预算假设。
- **插件管理界面大改**（`ui-plugin-manager` +1346）：安装引导精简、区分已安装/不兼容/内置插件的升级提示。我们禁用该行，收益归零。
- **`ui-settings-session-log`（新行）**：`Settings → General` 的"会话日志随官方模型 API 上传"开关；仅当宿主 `session-log-deepseek` 被服务时出现。
- **pi-ai 0.87.1**：第三方模型目录与兼容适配更新，**部分旧模型 ID 被移除**（我们 `llm-pi-ai` 行是 dormant，风险低，但若日后启用需重配目录）。
- PowerShell 持久会话尾提示/退出码修复；侧栏文件页可用本地应用打开当前文件夹。

## §4 能替换我们哪些自研插件？

**结论：本次升级可替换的自研代码 ≈ 0。** 唯一有"上游对应物"的是定时任务，而它是**不同产品语义**。

| 我们的插件 | 上游对应物 | 判定 | 理由（证据） |
|---|---|---|---|

### 5.5 门禁盲区（本次升级要补的判据）

### 6.3 建议

- 若产品上要"语音输入"：走 **1+2+3+4 + 5①（预置模型）**，把它做成**渠道级开关**（品牌渠道可关），而不是默认开——因为 5 的模型获取在"只有认证代理出公网"的客户网里结构上做不到。**（2026-09-29 用户改为默认开启；5 的两个出口已作为渠道包可选字段落地，见 §6.4）**
- 若不打算做：**把 sherpa 原生库从包里裁掉**（~71MB unpacked，Linux 双架构；mac/win 另有各自一份），并把 voice 包加进 `build.files` 排除与 `verify:closure` 豁免——这正好是当前"客户端体积压缩"分支可立即拿到的收益（注意：将来要启用就得重新装回来）。

### 6.4 实施记录（2026-09-29 当天）

用户拍板**默认开启**（不设渠道开关），实施见 `docs/decisions/2026-09-29-voice-input-default-on.md`：
**1+2+3+4+5 全部落地** —— 5 的两个出口都做成了渠道包字段（预置目录 / 内网镜像，见决策文档 §6），
构建期在 `scripts/ci-channels.sh` 校验形状（只报字段名、不回显取值）。
实施中新增三条实测结论（已进决策文档与判据）：

1. **`remote.speech` 只能经 `ctx.get('remote.speech')` 读**：属性代理 `ctx.remote.speech` 只在 inject 了 `remote`
   的 fiber 里成立，桌面 client 插件里直接抛 `cannot get property "remote" without inject`；而这个抛出被
   `void refresh()` 吞掉时，准备面只剩"未装配或正在启动"且没有按钮（打包版真机实测）。
2. **界面上的两个数字**：上游 `setupEstimate.recommendedDiskBytes`（int8 恒 1e9 字节 = 954MiB）是**预留磁盘**建议，
   不是下载量（实际下载 = int8 文件 239,233,841 B = 228MiB，与上游进度条同口径；加 tokens/VAD 共约 231MiB 落盘）；
   准备面必须分开说，否则用户看到的是 4 倍的数字。
3. **typert Remote 的入参个数是严格校验的**（可选参数也要占位）：`prepare(id)` 会抛
   `client api: speech/prepare expected 2 argument(s), got 1` —— 这个错误正是"让失败可见"改好之后立刻暴露的。
