# 上游 DSH 升级评估：0.1.2-rc.1 → 0.1.5-rc.2

日期：2026-09-11
状态：**仅评估，未实施**。本仓库 pin 仍为 `dsh-v0.1.2-rc.1`（a66e470204）。
调查方式：只读源码比对（submodule `git show <tag>:<path>`）+ npm registry 实测 + 上游设计笔记；
探针与原始数据在 `temp/dsh-compat-015/`。

## 1. 结论先行

1. **npm 面通过**：我们声明的 137 个上游依赖里，130 个 `@deepseek-ai/dsh-*` 全部已发布
   `0.1.5-rc.2`（npm `next` tag）；其余 7 个是 cordis 生态独立版本线，不受影响。
   上游包集合 **零删除**，新增 18 个包。
2. **官方右侧栏确实来了，而且它是一次根布局重构**：`ui-sidebar-right`（基于 `ui-dockkit`）
   取代了原来的 `details` 面板，并且 `ui-layout` 的 root 子槽契约从
   `sidebar / conversation / details / shell.overlay` 改成 **`sidebar / main(keyed) / rightbar / shell.overlay`**。
   我们的桌面 advanced frame 正是 `conversation + details` 那套 —— **不升级也就算了，一升级就是空白界面**
   （静默失效：`slots.inject('main')` 等不到声明就永不执行）。
3. **`dsh-better-sidebar` 不能简单退役**：官方右栏在定位上覆盖了"每会话侧栏 + tab 注册 + 文件树 + 文档预览"，
   但**不是超集** —— 编辑（CodeMirror）、终端（node-pty）、Git 面板、内嵌浏览器视图、底部面板、
   `/sidebar/api` 写面官方一个都没有，而这些正是我们 README 对外宣传的能力
   （`README.md:154`：资源管理器、编辑器、终端、Git 与浏览器视图；`README.md:23,136` 也把"终端"列为桌面客户端能力）。
   建议：**升级这一刀不砍它**（官方三行 `disabled` 即可让位），把"右栏放谁"作为独立的产品决策后续再定。
4. **会话格式：我们是 v0，不是 v2**（勘误）。升级链是 **v0→v1→v2→v3**，官方链支持、**副本式迁移**
   （源文件逐字节保留、另发后继世代）。但**降级是静默有损的**：rc1 只认 `session.jsonl[.zstd]`，
   回滚后 rc2 期间新建的会话直接"消失"、迁移过的会话读到旧内容，再升回来 rc2 只认最高世代 v3、
   **丢掉 rc1 期间写入的尾巴**。详见 §5。
5. **打包层还有一个 P0（且门禁形同虚设）**：上游把原生插件从 `@deepseek-ai/node-addon-landlock-run*`
   改名为 `@deepseek-ai/node-addon-system*`，我们的 `asarUnpack` 与新插件都还指着旧名；
   而 `verify-packaged-runtime.ts` 对"整包不存在"的条目是**跳过**的，所以**会带着坏掉的沙箱通过门禁**。
   另外 rc2 的会话写入需要新插件的 flock prebuild，缺了会退化成只读会话。详见 §6.1。
6. 结论建议：**可以做，但必须把"桌面 advanced frame 重写 + 打包改名 + patch 表重切"作为同一个变更集**推进；
   单独升级依赖的结果是"窗口能开、会话区空白、打包版沙箱静默失效"。

## 3. 【P0】根布局重构：桌面 advanced frame 结构性失效

### 3.1 上游把右列从 Details 面板换成停靠面

上游设计笔记（`.agents/notes/implemented/feature/2026-09-04-right-sidebar-docking-infrastructure.zh.md`）原文：
右列曾是"单一用途的 Detail 面板"，`ui-chat` 以 `DetailsPanel` 占据 `details` 坑位；
现在改为**每会话一份的停靠面**（pane/tab/浮动/撤销序列），由 `ui-sidebar-right` 基于 `ui-dockkit` 持有，
并**明确删除** `DetailsPanel`、`ToolDetails`、tool-node reader、chat store selection、`CENTER_MIN` 与 `details` 槽位。

bundle 侧新增 8 行（`packages/bundle/web-app/cordis.patch.yml`，默认启用）：
`ui-sidebar-right`、`ui-sidebar-documentpreview`、`ui-sidebar-files`、`workspace-files`、
`file-upload`、`resources`、`open-in-app`、`ui-open-in-app`。bundle 行集合**零删除**。

### 3.3 我们现在的实现（升级后逐条失效，且**全部静默**）

`packages/host/desktop/src/profile.ts:556` 把 `ui-layout` 行 `disabled: true`，因此桌面 frame 是 `root` 的**唯一声明者**：

```ts
// packages/host/desktop/src/client/advanced-shell.ts:56-65
children: { 'sidebar', 'conversation'(session-maybe), 'details'(session), 'shell.overlay' }
inject: () => ({ layout: desktopLayout, platform })
```

1. `ui-conversation` 只 inject `main`；我们没声明 ⇒ `slots.inject` 的语义是"等声明出现再执行"
   （`ui-renderer/src/client/registry.ts:172-208`：`specDynamic(key)` 为 `undefined` 直接 return，回调永不触发）
   ⇒ **聊天主界面不会挂载**，`renderSlot('conversation')` 永远是空的 —— 现象是"窗口打开了、侧栏在、中间什么都没有"。
2. `rightbar` 未声明 ⇒ 官方右栏静默不挂载。
3. `details` 槽位上游已废弃 ⇒ 我们的 details 列永远空（死代码）。
4. `DesktopLayoutState`（`layout-state.ts:66-125`）只有 `toggleSidebar/openDetails/closeDetails`；
   rc2 的 ui-sidebar 在 `inject` 里硬要求 `layout` 服务，并在点击面板行时调 `ctx.layout.selectPanel(id)`
   （`ui-sidebar/src/client/index.ts:38,68`）；`ui-sidebar-right` 调 `layout.openRightbar/closeRightbar`
   （`ui-sidebar-right/src/client/index.ts:137-140`）。一旦这些代码路径被触发就是 `TypeError: … is not a function`。
5. 我们没 provide `usePanelInfo`（ui-layout 是它唯一的提供者，而我们把 ui-layout 禁用了）。
   它由 `sidebar.panellist` 的每一行消费（`ui-sidebar/src/client/SidebarRoot.tsx:59-60`）。
   上游随包组合**不注册任何 panellist 行**，所以默认路径下不会立即崩；但任何注册了
   `sidebar.panellist` 的插件（含我们日后要加的）在 rc2 下都会渲染即 `TypeError`。
6. 类型面：`packages/host/desktop/src/client/contracts.ts` 自行合并声明了 `'conversation'` 与 `'details'`，
   升级后这两个 key 在上游已不存在（残留声明不会报错，但会掩盖"槽位已死"这一事实）。
7. **我们自己的槽位注册也一起死**（这条最容易被低估）：所有挂在 `conversation.*` 子树下的注入
   都会跟着那棵没挂载的子树一起不执行 ——
   `conversation.hero.brand.mark`（`packages/client/branding/src/client/index.ts:82`、
   `packages/host/enterprise/src/client/index.ts:148`）、
   `conversation.session.header.actions`（enterprise `index.ts:156`）、
   `conversation.session.header.utilities`（`packages/host/desktop/src/client/desktop-update.tsx:56`）、
   `conversation.chat.turnTail`（`packages/client/better-sidebar/src/client/intercept.tsx:75`）、
   memory-evolve 的 `conversation.view` tabs。
   rc2 保留了这些**叶子槽位名**，只是把父级从 `conversation` 挪到 `main.conversation`
   ⇒ 修复是"两侧同时对齐"，不是单点改一个字符串。
8. 失败形态确认是**静默**而非崩溃：rc2 的 `slots.inject(name, …)` 语义是"等声明出现"
   （`packages/client/AGENTS.md:141`），未声明就永远不回调；现象 = 应用正常启动、
   会话区与右列空白、相关的自家注入全部不生效，控制台没有对应报错。

### 3.4 修复形状（rc2 权威实现摘录，可直接照抄）

`ui-layout/src/client/index.ts` 一次 register 做四件事：

```ts
const disposePanelInfo = ctx.slots.provideRoot({ hooks: { panelInfo } })      // panelInfo: HostObservable<PanelInfo>
const disposeService   = ctx.reflect.provide('layout', layoutController)      // ILayout 5 方法
const disposeRegistration = ctx.slots.register({
  name: 'root', locale: 'common',
  children: {
    'sidebar':       { kind: 'single', scope: 'root' },
    'main':          { kind: 'keyed',  scope: 'root' },
    'rightbar':      { kind: 'single', scope: 'root' },
    'shell.overlay': { kind: 'list',   scope: 'root' },
  },
  store: createLayoutStore,                                                   // panelInfo + layoutInfo + actions
}, AppFrame)
const disposePanels = ctx.slots.subscribe('main', retainMainPanels)           // 选中态随 main 键集合收敛
```

渲染（`ui-layout/src/client/AppFrame.tsx:196-220`）：

- `renderSlot('sidebar', { collapsed, width })`
- `renderSlot('main', {}, { entryKey: activePanelId ?? 'conversation' })`
- `renderSlot('rightbar', { width: normal.rightbar, viewportWidth: viewport, canShow: normal.rightbar > 0 })`
- `renderSlot('shell.overlay', {})`
- grid = `${sidebar}px minmax(0,1fr) ${rightbar}px`；宽度数学 `columns.ts`
  （`CENTER_MIN=400`、`SIDEBAR_MIN/MAX/DEFAULT/COLLAPSED=264/420/280/56`、`SIDEBAR_AUTO_COLLAPSE=1024`、
  `RIGHTBAR_MIN=300`、`RIGHTBAR_MAX_RATIO=0.7`、`RIGHTBAR_DEFAULT_RATIO=0.45`）
- store 形状（`stores.ts`）：`{ panelInfo:{activePanelId}, layoutInfo:{sidebar,viewportWidth,narrowExpanded,rightbar,rightbarShown,rightbarTrack,rightbarFullscreen,rightbarInstant} }`
- ILayout：`selectPanel / beginNavigation / toggleSidebar / openRightbar(track,fullscreen) / closeRightbar`

**三条容易做错的细节**：

1. `details` → `rightbar` **不是纯改名**：rc1 的 `details` 是 `scope:'session'`，rc2 的 `rightbar` 是
   `scope:'root'`（会话作用域下沉到官方自己声明的 `rightbar.session` 子槽）。因此我们
   `AdvancedFrame.tsx:86` 那个 `SessionProvider` 包裹**要重新考虑**——官方 `AppFrame` 渲染 `rightbar` 时
   **没有**包 `SessionProvider`（`RightbarRoot` 自己在内部处理会话绑定）。
2. 我们的 frame 需要 `provideRoot({hooks:{panelInfo}})` 与 `slots.subscribe('main', retainMainPanels)`
   这类 rc2 新语义；我们自持 frame 目前都没有（未验证是否有别的东西强依赖它们，但 `usePanelInfo`
   是 `sidebar.panellist` 每行都要用的）。
3. 死掉的 `conversation.*` 注入要**逐个重新挂到 `main.conversation` 子树下的对应叶子槽位**
   （见 §3.3 第 7 条清单），漏一个就是"品牌标/更新按钮/任务面板静默消失"。

**两条路线**：

- **A（推荐）继续自持 frame**：按上面契约重写 `advanced-shell.ts` / `AdvancedFrame.tsx` / `layout-state.ts` / `contracts.ts`，
  保留桌面自有 chrome（macOS/Windows 标题栏行、桌面样式、窄屏策略）。工作量集中在一个包，测试面清晰。
- **B 让位官方 frame**：`ui-layout` 行不再 disable、删掉桌面 frame。省掉重写，但丢桌面 chrome 与自持布局
  （产品上一路自持 frame 的决策要回退），且桌面样式与 macOS 标题栏行需要另找注入点。

## 4. 【P1】官方右栏能力与 `dsh-better-sidebar` 的取舍

### 4.1 官方右栏能力（rc2）

- 面：每会话一份 `SurfaceState`（布局/历史/铸造计数），内存态，刷新回默认；
  两格上限、20–80% 分割、普通/全屏两种呈现、浮动面板（portal）、tab 拖拽/复制/右键菜单。
- 随包类型：引导页（guide）、文档预览（Markdown/代码/HTML/PDF/纯文本）、**工作区文件树**。
- 扩展面四个槽位：`sidebar.right.pane.tab`（按 kind 分派正文）、`sidebar.right.pane.tab.title`、
  `sidebar.right.tab.guide`（chain 替换引导页）、`sidebar.right.tab.menu.item`（tab 菜单项）。
- 服务：`ctx.sidebarRight`（导航面：`openResource` / `openTab` / 关闭 / 重开）、`ctx.sidebarRightTabs`（类型注册表）。
- 宿主依赖：`api/workspace-files`（有界读取、目录列举、agent 写入变更流）随 web bundle 默认挂载。

### 4.2 与 better-sidebar 的差距（逐项，证据见 `temp/dsh-compat-015/OFFICIAL-SIDEBAR.md` §4）

| better-sidebar 能力 | 官方 0.1.5 | 说明 |
|---|---|---|
| 每会话侧栏 + tab 注册服务 | ✅ | 官方是 `ctx.sidebarRightTabs.register` + keyed `sidebar.right.pane.tab`，还多出 glob 地址路由 / 优先级 band / `canOpen` 否决 |
| 文件查看器注册 | ✅（更弱） | 官方按扩展名匹配、由 owner 统一读；缺 `detect(head)` 内容嗅探与自定义 `load()` |
| 文件树 / 资源管理器 | 🟡 | 官方 README 自述 "Listing only"：无搜索、无 watcher、无拖放/重命名/右键、无当前文件高亮 |
| 文档预览 | 🟡 | 官方有 md/代码/图片/PDF/HTML/文本；**无 Mermaid、无 Office 内联**（better-sidebar 有 Mermaid） |
| 布局/Tab 状态持久化 | 🟡 | 官方明确 "Memory-only. Nothing is persisted; a reload starts every session collapsed"；better-sidebar 按会话持久化 |
| **编辑（CodeMirror 多语言）** | ❌ | 官方 "Preview, not editing"，`workspace-files` 只读无 mutation |
| **终端（node-pty + xterm）** | ❌ | rc.2 客户端侧无任何终端 UI 包 |
| **Git 面板（diff/暂存/提交/历史）** | ❌ | 无 git tab 类型 |
| **内嵌浏览器 tab** | ❌ | 官方无 webview 类型（且我们产品已在 `sidebar-policy.ts:57-71` 默认关掉该 tab，AI 浏览器是独立的 host 插件） |
| 底部面板 / 双工作台 | ❌ | 官方只有右侧一列（split + 浮动面板有） |
| HTTP 面 `/sidebar/api`·`/sidebar/bundle`·`/sidebar/file` | ❌ | 官方文件能力走 Typert Remote `workspaceFiles`，只读、无 git/pty/chunk 路由 |
| 官方更强处 | — | glob tab 仲裁、`dsh-resource://` 统一资源模型 + `useResource`、文件变更流、`open-in-app` 外部应用、流式 `file-upload`、`present` 交付链 |

**关键判断：官方右栏不是 better-sidebar 的超集。** 它把"每会话停靠面 + tab 宿主 + 只读预览/文件树"做成了第一方能力，
但把"可编辑 / 终端 / Git / 浏览器 / 底部面板"整块留空。而我们 README 正在对外宣传这些能力
（`README.md:154` "资源管理器、编辑器、终端、Git 与浏览器视图"；`:23`/`:136` 把"终端"列为桌面客户端能力）。

### 4.3 消费面与移除成本（若真要走"退役"）

消费点只有一个（软依赖）：`packages/host/cron/src/client/index.ts:116-131`
注册 `pico:cron` tab；同控制器另有主区中心面板（`mountCronPanel`），移除只丢侧栏 tab。
但"删包"远不止删目录，共 12 处硬引用：desktop `profile.ts:58/492/510`（`createRequire(...).resolve` 缺包即启动抛错）、
desktop `package.json:277`（`workspace:*`）、`scripts/prebuild-workspace-deps.ts:58`、`scripts/check-workspaces.mjs:48/59/73`、
`scripts/verify-layout.mjs:61`、两条桌面测试（`sidebar-policy.spec.ts`、`client-environment.spec.ts:92-97`）、
`THIRD_PARTY_NOTICES.md:527`，外加三条 HTTP 面、node-pty 原生依赖与懒加载 chunk 机制。

**bundle 结构上的好消息**：better-sidebar **不占用任何根布局槽**（只注册 `settings.section` 与
`conversation.chat.turnTail`，两者 rc.2 仍在），面板是自己 portal 到 `document.body` 的 fixed 元素

### 5.2 迁移机制（rc2 权威描述）

- rc2 补齐迁移链：`session-format`、`session-format-catalog`、`v0-to-v1`、`v1-to-v2`、`v2-to-v3`。
- **副本式（copy-on-write）**：历史世代文件不可变；**read open 只在内存里迁移**；
  **write open**（= 恢复/继续一个会话）才在**同目录**写临时文件 → Worker 线程校验 → 复核源 revision →
  **无覆盖发布**后继世代。源文件**逐字节不变**（`session-persistence-jsonl/README.md:56-80`）。
- 迁移会**重编 `seq`、重写 header**，保留 session id。
- `compression` 默认 `zstd`（每批一个带校验和的 Zstandard 帧）。
- **没有任何开关**：backend config 只有 `root` + `compression`，没有环境变量/CLI flag 能控制迁移。
- 迁移可能**拒绝**（`SessionFormatUnsupportedMigrationError`）：v0 边拒绝冻结清单外的事件类型与
  非预期 payload 成员；v2→v3 边拒绝首个 step 之前的 surface 事件等。被拒的会话**永远无法 write open**
  （源文件仍在）。子代理对现场 **37 个真实会话日志**做了静态探针：0 个未知事件类型、0 个未知 payload 成员、
  0 个 surface-before-step、0 个解码错误 ⇒ **拒绝是尾部风险，不是预期路径**。

### 5.3 【P0】降级是静默有损的

- rc1 只找 `session.jsonl[.zstd]`，**看不见** `session.v3.jsonl[.zstd]`（rc1 `index.ts:521-524,823`）。
- 于是回滚到 0.1.2-rc.1 之后：rc2 期间新建的会话**从列表里消失**；被迁移过的会话**读到旧的 v0 内容**；
  而且 rc1 会**继续往 v0 文件追加**。
- 再升回 rc2：rc2 选"数字最高的世代"= v3（rc2 `index.ts:1367-1399`），
  **静默丢弃 rc1 期间写入的全部内容**。
- 结论：**升级后不要就地降级**。若必须保留回滚能力，回滚要"整目录回滚"
  （`<DSH_HOME>/sessions/` + `<DSH_HOME>/storages/session_projcache.json` 一起恢复），
  且回滚前必须冻结/停止写入。

### 5.4 升级前必做

1. 备份 `<DSH_HOME>/sessions/` 与 `<DSH_HOME>/storages/session_projcache.json`（整个 `DSH_HOME` 最稳）；
2. 测试环境用真实历史跑「打开旧会话 → 继续对话（触发 write open）→ 重启 → 再打开」；
3. 确认我们 cron / browser 插件引用的会话仍可解析；
4. 明确回滚策略 = 整目录恢复，**不是**换回旧二进制。
