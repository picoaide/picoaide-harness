# macOS 原地自更新：应用自己换掉自己并重开（2026-10-09）

状态：已实施（`packages/host/desktop`）

## 问题（用户 2026-10-09 反馈）

> 当前项目编译出的 macOS 程序每次更新时需要手动退出应用并手动拖动程序到应用程序文件夹中
> 替换原来的应用。

改造前 macOS 的交付口径只有一条（`electron-runtime.ts` 的 `installUpdate`）：把下载好的
DMG `shell.openPath(...)` 打开，然后弹一句"磁盘映像已打开。请用新版本替换「应用程序」里的
X，然后重新打开。"剩下的四步 —— 退出应用、拖进「应用程序」、覆盖旧版本、重新打开 ——
全部由用户手工完成。Windows 早就是"应用自己重启、安装程序接管"，macOS 缺的正是这一步。

## 现状取证

| 位置 | 事实 |
|---|---|
| `electron-runtime.ts:739`（改造前） | darwin 分支 = `shell.openPath(dmg)` + 一段"请自己拖"的提示；没有任何替换动作 |
| `updates.ts:1119`（`installReady`） | 交付前会复检"这份包确实属于当前更新源 + SHA-256 命中"，复检不过就撤掉 ready 状态 —— 不改 |
| `update-download.ts` | 只产出**已公证的 DMG**；Linux 的 AppImage 同样只能提示用户手动替换 |
| `tray-locale.ts`（`darwinOpenedDetail`） | 唯一一条 macOS 安装文案就是"请用新版本替换…"（中英各一句） |

## 决策

**在 macOS 上用"宿主退出 → 一个 detached 的 `/bin/sh` 帮手完成替换 → 帮手把应用重新
打开"取代"打开磁盘映像让用户拖"。** 回落路径逐字保留：做不到时仍然打开磁盘映像。

### 1. 三段时间线

```
宿主（旧版本）                              帮手（/bin/sh，detached，launchd 收留）
─────────────────────────────              ──────────────────────────────────────
① canInstallMacosInPlace（零副作用）
② 确认框（措辞与②的结论一致）
③ prepareMacosInPlaceUpdate：
   挂载 DMG（只读）→ 卷根唯一 .app →
   BundleID / 版本 / TeamID / 剩余空间
④ 写帮手脚本 + detached 起进程，等 'spawn'
⑤ requestQuit(0) ───────────────────────▶ ⑥ 等宿主 pid 退出（≤120s）
                                           ⑦ ditto 到 <同目录>/.<名>.update-<版本>.app
                                           ⑧ codesign --verify --strict 暂存件
                                           ⑨ mv 旧包→备份；mv 暂存件→目标
                                           ⑩ 卸影像、重开应用
                                           ⑪ 等新版写启动标记（≤30s）
                                              等到 ⇒ 删备份、记 ok
                                              等不到 ⇒ 回滚 + 重开旧版本、记 failed
```

### 2. 判据全部"在动用户文件之前"

- **签名校验在替换之前**（第 ⑧ 步）而不是之后：失败时用户的应用一个字节都没变。
- **新旧包必须同身份**（`CFBundleIdentifier`）、**同期待版本**（清单声明的版本）、
  **同签名团队**（`TeamIdentifier`）。三者任一不符即**抛错**，不是"换一种交付方式"：
  `codesign --verify` 对自签/临时签名同样通过，TeamID 才是这一层真正的**来源**判据
  （当前应用没有 TeamID 的开发版不强制 —— 否则开发流程被堵死）。
- **`mv` 而不是 `rm -rf` + 复制**：旧包改名成备份（同卷 rename，瞬时），失败可就地换回。
  暂存件也在**目标同目录**，于是最后一次落位是原子 rename，目标"消失"的窗口是微秒级。
- **挂载点只用 `rmdir`，绝不递归删除**：万一上一次的影像还挂着且卸载失败，递归删除会
  去删**卷里的内容**。非空就让 `hdiutil attach` 自己报错。
- 每一步失败的结论都写进**结果文件**；退出码 0/1 与之同义。

### 3. "成功"由新版本自己证明

帮手在重新打开应用之前**删掉**启动标记，然后等新版本把它写回来（`version=<目标版本>`）：
等到了才删备份，等不到就回滚。这不是为了好看 —— 没有这一步，"更新成功"只是"文件换好了"
的猜测，而一个新版本起不来时用户会同时失去新旧两个版本。删标记这一步是必须的：否则
**上一次**留下的同名标记会让帮手把"根本没起来"误判成成功。

标记由宿主在启动路径上尽早写（`electron-runtime.ts` 的 `mount()` 第一件事，
`writeMacosUpdateBootMarker`）。这条**跨版本契约**是本次改造唯一一个"未来版本必须继续
遵守"的约定，写在 `macos-update-install.ts` 的模块注释里。

### 4. 失败对用户可见（一次）

宿主下次启动时读结果文件（`readMacosUpdateOutcome`），判据是"记录的**目标版本**是不是
就是当前运行的版本"：

| 记录 | 当前版本 | 结论 |
|---|---|---|
| 任意 | = 目标版本 | 更新已生效 ⇒ 删备份、清记录（帮手被杀了也算生效） |
| `failed`/`running` | ≠ 目标版本 | 报一次失败（原因 + 日志路径 + 备份路径）⇒ 清记录 |
| `ok` | ≠ 目标版本 | 静默清理（例如用户后来手动降级） |

`running` 是"帮手没写完结果就被杀"的形态：`to === 当前版本` 时它是**成功**，否则按中断报错。

### 5. 回落面（与改造前逐字一致）

| 情形 | 行为 |
|---|---|
| 开发态（`app.isPackaged === false`） | 打开磁盘映像 |
| 可执行文件不在 `.app` 里 / 非 macOS | 打开磁盘映像 |
| App Translocation（从 DMG/下载目录直接运行） | 打开磁盘映像 |
| 目标目录或应用包不可写（root 安装、只读卷） | 打开磁盘映像 |
| 剩余空间放不下一份新副本 | 打开磁盘映像 |
| 影像挂不上（`hdiutil attach` 失败） | 打开磁盘映像（**2026-10-12 修订**） |
| 挂载点被占 / 卷根是空的（陈旧挂载、影像挂在别处） | 打开磁盘映像（**2026-10-12 修订**） |
| 同一版本已原地失败过 `MACOS_UPDATE_FAILURE_LIMIT` 次 | 打开磁盘映像（**2026-10-12 修订**） |
| 卷里不是一个应用 / 身份/版本/TeamID 对不上 / 架构不符 | **失败**（`lastError = 'invalid-artifact'`） |

**不弹管理员授权**：需要提权才能替换的安装（root 所有）一律走回落，绝不出现密码框。
代价写在下面的修订段：这类账号**根本用不了原地更新**，只能走"打开磁盘映像 + 管理员拖拽"。

## 修订（2026-10-12，合并前审计）

合并前的多轮审计（报告与逐条证据见 PR 描述）在**实现**上定案了 6 条 P1 与若干 P2/P3。
这一段记录行为变更本身，编号与审计报告一致：

- **A1 启动标记整行定串匹配**：`grep -q "version=$VERSION"` 是子串匹配，会被版本号前缀吃掉
  （目标 `2.8.3` 命中标记里的 `2.8.3-beta.1`／`2.8.3-beta.10`；本仓的预发↔正式、`beta.1`↔`beta.10`
  天然互为前缀）⇒ 误判"新版已启动"并删掉唯一备份。现在要求**整行相等**（`grep -qxF`）。
- **A3 启动确认的判据面（两轮结论相反，最终取"减法"）**：改造后的第一版曾把启动标记挪到
  单实例锁**之前**、并加一条"目标路径下的主程序在跑"（`pgrep -f`）作为**独立**成功判据。
  第二轮审计复核把它推翻了，两条都撤掉：
  - `pgrep -f` 只是**命令行文本匹配**。把 TARGET 改名成 BACKUP 之后，一个**旧实例**的 argv
    仍然是 `TARGET/Contents/MacOS/…` —— 于是"旧实例还活着"会被判成"新版本起来了"，
    同时做出三件事：不回滚、删掉那个正在运行的实例的文件、把结果记成 `ok`。
  - 标记写在进程极早期也不行：新版"起来了但**根本不是可用应用**"（启动路径上的致命错误）
    同样会命中它，而负向标记要等 Electron 起来才写得下 —— 胜负交给竞态。
  最终形态：**标记回到"应用真的走到可用"的那一刻写**（`mount()` 的第一件事，即改造前的
  位置），确认**只认标记**（版本 + bundle 两行都要整行命中），致命启动失败由负向标记
  （`boot-failed.txt`，在弹同步对话框**之前**写）当场判否。代价见"认账"。
- **A2 先读结论、再清理**：原来是"清理（删备份）→ 读结果 → 把已被删掉的备份路径报给用户"。
  现在先读结果；有待通报的失败时，那个备份作为 `keep` 传给清理函数；而**通报里只给仍然存在
  的备份路径**（`application-did-not-start` 那条最常见路径上，帮手已经把备份换回原位，
  记录里的路径本来就不存在）。
- **A9 版本序判据**：原来只判"相等"，降级也会被当成一次正常更新。客户端数据面是前向 only 的
  （会话格式跨代、迁移 0066 使存量会话失效），静默降级可能得到"旧 app + 新数据"。
  现在按 semver 判序，降级**拒绝**并抛错。
- **A8 架构闸门**：新增 Mach-O 头解析（`machOArchitectures`，不依赖 `lipo` —— 它属于
  Xcode 命令行工具，裸机不保证有），暂存件必须支持**当前进程架构**（`process.arch`，
  不是 `uname -m`：后者在 Rosetta 下报 `x86_64`）。认不出架构时放行并记日志。
- **A14 标记写失败不再静默**：`writeMacosUpdateBootMarker` 现在把失败原因**作为返回值**
  交出来（调用方记日志），并且标记里带 `bundle=`（只认版本号会被**同版本的另一份副本**
  或 `yarn dev` 伪造）。致命启动失败额外写一条**负向标记**，帮手看到它立刻回滚。
- **A10 备份删除只有一个所有者**：帮手**不再**在脚本里删备份（脚本侧的 `pgrep` 无论怎么写
  都可能把"旧实例还活着"判成"没人占用"，见 A3 条）；删除点收敛到宿主侧唯一一处
  `settleMacosUpdate → removeMacosUpdateBackup`，那里的占用判据是 fail-closed
  （只有 `pgrep` 退出码 1 才算没人占用）、并且对模式做了 ERE 转义。
- **A13 环境类失败归回落**：`hdiutil attach` 失败、挂载点被占、卷根挂空，这些都不是
  "这份载荷不能用"，一律回落成"打开磁盘映像"（原来它们与载荷不合格共用抛错桶，
  配合 A11 会让用户卡在点一次失败一次的循环里）。
- **A15 失败账本**：`updates/macos/failures.txt` 记"某版本原地失败过几次"，达到
  `MACOS_UPDATE_FAILURE_LIMIT`（2）就不再走原地替换、回落成打开磁盘映像；
  正在运行的版本每次启动自洁。
- **A11（宿主侧）**：`installReady` 的 catch 现在同时**撤掉 ready 状态**。原来只记
  `lastError`，而 `runManualCheckTask` 在 ready 时直接转去安装 ⇒ 点「检查更新」也不会
  重新取清单/重新下载。
- **A6/A5 收尾**：帮手加了 `trap cleanup EXIT`（+ `INT TERM HUP`），任何出口都
  卸载影像，并在两次 `mv` 之间被杀时把缺失的目标补回来。
- **A4/N8 残留清理**：`.broken` 形状纳入清理正则；帮手脚本名带 pid
  （`/bin/sh` 是**按偏移增量**读脚本的，固定名 + 覆盖重写会让仍在运行的上一条读到错位内容）。
- **A10 删备份前看占用**：多用户 Mac 上另一个账号可能正跑着被换下来的那一份
  （单实例锁按 userData 隔离，挡不住跨账号实例）—— 有进程在跑就留着，下次启动再收。
- **A12 支持包纳入更新现场**：`apply-update.log` / `last-apply.txt` / `booted.txt` /
  `failures.txt` 有界地（单文件 1 MiB，与其它证据共用 50 MiB 总预算）进"导出诊断"。
- **P0（判据面）**：`macos-update-helper.integration.spec.ts` 是 `describe.skipIf(≠darwin)`，
  而唯一的 mac runner job 只打包 ⇒ 这 5 条在 CI 上**从未执行**（实测 `5 skipped`、退出码 0，
  与"通过"不可区分）。现在 `desktop-macos` job 里新增一步真跑它，并加组级判据：
  **跳过的条数必须为 0、用例数 ≥ 5**（vitest 4.1.8 的 JSON 报告里"跳过"落在
  `numPendingTests`，`it.todo` 落在 `numTodoTests`）。

## 边界（不做）

- 不引入 `electron-updater`、不加 ZIP/blockmap 第二条载荷与发布路径、不做差分下载、
  不改服务端清单与 R2 布局 —— 2026-09-12 的决定继续成立
  （`docs/decisions/2026-09-12-client-update-resilience.md`）。
- 不改服务端、不改渠道面：脚本、日志、结果文件全部落在 `userData/updates/macos/`，
  随渠道隔离；文案走 `productName` 与既有中文文案表。
- 不做"静默重启"：安装始终由用户显式触发（对话框上还有一个「稍后」）。
- 不做自动降级回滚之外的失败自愈：新版本起不来才回滚；替换成功但随后崩溃不在本轮面内。

## 认账（未闭环）

- **`hdiutil create` 在本机砂箱里跑不了**（返回"操作不被允许"），所以"造一个 DMG 再挂"
  这一步进不了自动化用例；`tests/macos-update-helper.integration.spec.ts` 喂的是**解开的**
  应用包路径（帮手不关心它挂在哪）。作为补偿，2026-10-09 用**真实已公证 DMG**
  （`PicoAide-Harness-2.7.3-beta.2-mac.dmg`，147 MiB，内含 379 MiB 的应用）手工跑过一遍
  生产路径（`prepareMacosInPlaceUpdate` 用真 runner + 真帮手脚本，只把重启命令换成
  `/usr/bin/true`）：
  - 真 `hdiutil attach -nobrowse -readonly -noverify -mountpoint <userData>/updates/macos/image`
    挂载成功，卷根形态与假设一致（唯一 `.app` + `Applications` 符号链接 + 三个点文件）；
  - 真 `plutil`/`codesign -dv`/`du`/`statfs` 全部通过，计划里的路径与实际落点一致；
  - 帮手 `ditto --noqtn` 出 379 MiB 的副本后 `codesign --verify --strict` **通过**
    （"复制会丢签名"这个最大的未知项被否证），落位、卸载影像、按启动标记删备份全部按预期，
    全程 2.1 秒，替换后的包 `codesign --verify --strict` 报
    `valid on disk / satisfies its Designated Requirement`（含全部嵌套 helper）。

  仍未覆盖的是**下载 → 挂载 → 帮手 → 新版本真的接管窗口**这条完整链路（要一台真机点一次
  "安装更新"）。
- **自动回滚只覆盖"新版本进程没起来"**（30s 内没写标记）。起来了但随后崩溃、或被用户
  立刻退出，不在面内；备份此时已经删掉，恢复要靠重新下载 DMG。
- 帮手脚本是**字符串模板**（`macosUpdateHelperScript`），不是被类型系统检查的代码。
  静态契约由 `macos-update-install.spec.ts` 的文本判据 + 真机集成用例守住。
- **2026-10-12 审计新增的未闭环项**（都写清了代价，不是"以后再说"）：
  - **两次 `mv` 之间仍不是原子的**：`trap cleanup EXIT` 覆盖了 SIGTERM/SIGINT/HUP，
    但 **SIGKILL 与断电** 仍会留下"目标不存在"的现场，而没有应用能运行来自救。
    彻底的做法是 `renamex_np(…, RENAME_SWAP)`（macOS 10.12+/APFS 支持两路径原子交换），
    需要一段原生代码（仓库已有原生 addon 先例），本轮没做。
  - **回滚不回滚数据**：新版本只要运行过就可能已经写过 userData/会话格式。现在第二道判据
    （目标下的主程序在跑 ⇒ 不回滚）把"误回滚"挡掉大半，但"新版本真的崩在写数据之后"
    这条形态仍会得到"旧 app + 新数据"。成熟实现（Squirrel/Sparkle）不做自动回滚正是为此；
    真要闭环得先落一条"新版已开始动用户数据"的 journal，再据此禁止自动回滚。
  - **TeamID 只比字符串，不比 designated requirement**：TCC 权限绑的是 DR。当前应用没有
    TeamID（ad-hoc 打包件）时不强制一致 —— 这条放宽没有闭环（本轮只把它记录在案）。
  - **非管理员账号用不了原地更新**：`/Applications` 对 admin 组可写、无 sticky 位，
    非管理员既不能替换也不提权（刻意），只能走"打开磁盘映像 + 请管理员拖拽"。
  - **暂存/备份件仍以 `.app` 结尾**：会被 Spotlight/LaunchServices 当成第二个 app 索引。
    改成不以 `.app` 结尾（或挪进隐藏子目录）是纯收益，但会动到 `mv` 落位的形状，本轮没做。
  - **成功安装后不删下载的 DMG**：`<userData>/updates/` 里每个版本留一份 ~150 MB
    （既有行为，与本改造无关；`failures.txt` 所在的目录已经是同一个树）。
  - **启动确认只认标记，因此"用户自己的实例占着单实例锁"时更新会被回滚**（A3 条取"减法"的
    代价）：标记写在应用真正走到可用时。如果用户在替换窗口里手动打开了应用并持有锁，
    帮手 `open` 出来的新实例会在单实例锁上立刻退出、标记不写 ⇒ 帮手回滚成旧版本并报
    "新版没启动"。此时盘上其实已经换好了，但**回滚是安全方向**（不删任何正在运行的文件、
    状态一致），用户重试一次即可；反过来（保留新版本）会让那个正在运行的旧实例变成
    "文件已删"的幽灵。要消掉这个回滚，需要"新实例主动让路"的交接协议（version-stamped
    handoff marker），本轮没做。
  - **30 秒 boot 窗口内的"起来了但随后崩溃"仍在面外**：标记一旦写下，随后的崩溃不会触发
    回滚（备份此时由宿主回收）。这与原认账一致，只是现在"根本没变成应用"那一段已经被
    负向标记覆盖。
