> 决策记录。事实面的入口是 `upstream.json`（固定点）、`scripts/upgrade-upstream.mjs`
> （唯一的升级入口）与本文；评估与预判见
> `docs/planning/2026-09-29-dsh-0.2.0-rc.2-assessment-and-voice-input.md` §5（该文写于升级前，
> 其"处置"列已被本次执行取代，见该节顶部的执行记录指针）。
> 状态：**已收口** —— `yarn check` 32/32、打包版 E2E 43/43、裁决五/六均已定案并落地。

## 背景

上游固定点从 `dsh-v0.1.7-rc.2`（`477b4f420553e8a52c2fbccc464d7561b239c443`）升到
`dsh-v0.2.0-rc.2`（`639ed015397290b3745d163aafe02ffee4aa3f84`），中间 **448 个提交**。

这次升级在数据面上是干净的，这一点先行确认（它决定了回滚成本）：

- **会话格式仍是 v4**：`SESSION_FORMAT_VERSION` 两版相同，`verify-session-restart` 的
  16 项（含 v0 → v4 的副本式迁移）在升级后全绿 ⇒ **无数据迁移，回滚只需换回二进制**；
- **`scripts/platform-modules.mjs` 逐字不变**（重抽后零 diff）⇒ 客户端 bundle 的冻结模块表未动；
- 上游包集**零删除、新增 4**：`@deepseek-ai/dsh-client-product-analytics`、
  `@deepseek-ai/dsh-client-ui-settings-session-log`、`@deepseek-ai/dsh-experimental-schedule-bundle`、
  `@deepseek-ai/dsh-otel`。

代价落在两处**默认值**上：一条新行会让 profile 起不来，一个上游的版本钉法会静默废掉我们的补丁
——两条都不是"升级脚本能自己发现"的形态，所以各留一条裁决。

## 裁决一：0.2.0 新增的两条桌面分析/遥测行**显式关闭**

**问题**：`web-app/cordis.patch.yml` 新增 `desktop-product-telemetry`（宿主 OTLP 上报）与
`product-analytics`（客户端事件采集），两行的 `disabled` 判据都是
`ctx.get('profileContext')?.name !== 'desktop'` —— 而桌面**必须** provide `profileContext`
（见 `packages/host/desktop/src/main.ts` 的 provide 注释），于是它们在桌面组合里**默认启用**。

**为什么这是 P0（不是"多一个上报"）**：`desktop-product-telemetry` 的
`serviceVersion: !!js process.env.DSH_CLIENT_VERSION` 在 schema 里是 `.required()`
（`packages/host/product-telemetry-otel/src/index.ts` 的 Config），而 `DSH_CLIENT_VERSION`
只有**上游自带的 Electron 壳**（`deepseek-harness/apps/desktop/src/client-metadata.ts`）会设，
我们的启动器不设 ⇒ 该行 Config 校验失败、拿不到 fiber ⇒ `verify-profile-boot.mjs` 的
`unimportable` 判据点名它，`yarn check` 直接红。这是"升级完成但产品起不来"的形态。

**定案：两行都在 `cordis.patch.yml` 里 `disabled: true`，并登记进 `verify-profile-boot.mjs`
的 `mustStayDisabled`（该名单与 `cordis.patch.yml` 双向对拍，漏登记与多余登记都红）。**

为什么不做"补一个 `DSH_CLIENT_VERSION` 让它能挂载"：那条路要同时回答第二个问题——**这些事件发到哪**。
`endpoint` 的 schema 缺省是上游厂商自建的收集器（见该包 `src/index.ts` 的默认值），事件含
`device_id` / `user_id` / `os_version` 与使用行为。本产品是自托管 + 白标交付，**客户端使用数据出境到
模型厂商不在交付承诺内**；我们自己的错误上报走 `error_reporting_enabled` + 客户自建的
GlitchTip 兼容端点，两套并行的"上报"只会让交付面的口径变模糊。所以关闭是产品口径，不是权宜。

两行**必须成对关闭**：客户端那半没有宿主消费服务时只会积压队列。

**行为面影响**：无用户可见变化（这两行在 0.1.7 及以前不存在）。
**未被这次裁决覆盖的相邻项**：`ui-settings-session-log`（新的客户端设置行）与 `otel`（新的
base bundle 服务行）保持挂载——前者贡献的设置项只在宿主 `session-log-deepseek` 被服务时出现，
而我们把那一行关了；后者源码自述"挂载不创建队列/身份/网络连接"，无消费者时惰性。

## 裁决二：koffi 必须**全树只有一代**，且仍是 3.1.5

**问题**：上游 0.2.0-rc.2 把 7 个包的 `koffi` 声明从 `^3.1.0` 改成**精确的 `3.1.1`**
（`fs-local`、`session-persistence-jsonl`、`sandbox-windows-acl`、`subprocess-local`、
`win32-process`、`directory-picker-native`、上游 `apps/desktop`）。我们根 `package.json` 的
resolution 键是 `koffi@npm:^3.1.0 → 3.1.5`，**它不再匹配任何声明** ⇒ 钉版被静默绕过，
安装树里同时出现：

- 顶层 `koffi@3.1.5`（桌面包自己声明的那份）；
- `@deepseek-ai/dsh-subprocess-local/node_modules/koffi@3.1.1` —— **一个没有任何
  `@koromix/koffi-*` 平台包的嵌套副本**，它的原生二进制只能向上解析到 3.1.5 的平台包。

**为什么不能接受**：3.1.5 这个钉版不是随手写的 —— 提交 `3fc50cab89`（fix(windows)）把它固定下来，
理由是 **3.1.4 的交叉编译 Windows 二进制会 access violation 崩溃**（issue #145/#149），并为它加了
打包回归断言。让上游的 `3.1.1` 进来等于把那条修复退回去，而症状只在 Windows 上出现。
"JS 是 3.1.1、原生二进制是 3.1.5"这种混装更是只在真机才炸的形态。

**定案**：补一条 `koffi@npm:3.1.1 → 3.1.5`（`^3.1.0` 那条保留给上游 `apps/desktop-host`），
reinstall 后全树只剩 `koffi@3.1.5` 与 `@koromix/koffi-*@3.1.5` 两族条目。

**同时修掉判据本身的盲区**（这才是这条裁决的重点）：原断言是
`expect(workspaceManifest.resolutions).toMatchObject({ 'koffi@npm:^3.1.0': '3.1.5' })`
——**只要 key 还在就绿**，而上游改声明范围恰好只让 key 失去匹配对象，不改 key。现在改成对
**锁文件**判：枚举 `koffi` 与 `@koromix/koffi-*` 的全部 `@npm:` 描述符，其版本集合必须恰为
`['3.1.5']`，并显式断言 `3.1.1`（上游当前声明值）与 `3.1.4`（崩溃版本）都不在锁里。
这样"上游再改范围"这一类变化会直接红，而不是悄悄换掉交付二进制。

## 裁决三：`@deepseek-ai/dsh-otel` 补进部署根声明

**问题**：`verify:closure` 报两条必填一方 peer 未在部署根声明，链都收敛到同一个包：
`dsh-base → dsh-session-telemetry-otel → dsh-otel` 与
`dsh-web-app → dsh-host-product-telemetry-otel → dsh-otel`。

**定案：声明它。** 先取事实：`@deepseek-ai/dsh-otel` 是 `base` 与 `web-app` 两个 bundle 的
**直接依赖**，本来就在安装树里 ⇒ 声明"我真的分发它"是如实陈述，不是为消红造假依赖。
这与 0.1.7 那次裁决二的同一条逻辑一致：**能声明就声明，不能声明（包真的不存在）才退回
可被打破的 `UNMOUNTED_PEER_EXEMPTIONS`**。这里不需要豁免，所以没动豁免表。

## 裁决四：8 个补丁全部保留 —— 7 个原样改名、1 个必须重切，**零 DROP-UPSTREAMED**

**先回答"还生效吗"**：每个补丁都在**仓库之外**（避免 `git apply` 对忽略路径假通过）对 npm 上
`0.2.0-rc.2` 的真实 tarball 做 `patch -p1 --dry-run`，7/7 命中。

**唯一需要重切的是 `dsh-sandbox-windows-acl`**：它的目标产物是哈希命名文件
`lib/types-DxezulnA.js` → `lib/types-Cl_DXjhk.js`（上游源码 `src/acl.ts` 两版逐字节相同，
只是打包哈希变了）。重切只改 diff 头与 hunk 行号，语义（Win32 5 / ERROR_ACCESS_DENIED 的解释
与两条出路）逐字不变；重切后同样过仓库外 dry-run，并在真实 `node_modules` 里复核落地。

**再回答"还有必要存在吗"（逐条查上游源码，而不是查 tarball 是否还能打上）**：

| 补丁 | 上游 0.2.0-rc.2 是否已自行实现 | 依据 |
|---|---|---|
| `dsh-subprocess-local` | **没有** | `packages/subprocess/subprocess-local/src/runner-launch.ts` 的 `runnerEnvironment()` 仍只剔除 `RUNNER_CONTROL_ENV_PREFIXES`，不注入 `ELECTRON_RUN_AS_NODE`。（同仓 `ptc-runtime-node` 与 `speech-to-text-sensevoice` 各自注入，与 patch 不冲突） |
| `dsh-mcp-client` | **没有** | 全 `packages/*/*/src` 对 `authProvider` **零命中** —— 官方 MCP 授权规范仍未被上游接进传输层 |
| `dsh-web-fetch-http` | **没有** | `src/network.ts` 的 `isPublicIpAddress` 仍以 `ipaddr.range() === 'unicast'` 为唯一判据（fake-IP 段照旧被误杀） |
| `dsh-plugin-package-inventory-deepseek` | **没有** | `src/index.ts:178` 的 `resolver.resolve(activeEntry)` 仍无 try/catch |
| `dsh-client-ui-brand-official` | **没有** | 槽位仍由官方 mark 占用，品牌替换只能靠 patch |
| `dsh-client-ui-sidebar-documentpreview` | **没有** | Office 渲染器仍默认注册（我们不带 LibreOffice 引擎） |
| `app-builder-lib@26.15.3` | 不适用 | 第三方；上游 `apps/desktop` 仍钉 `26.15.3`，patch 键链不变 |

⇒ **本次没有 DROP-UPSTREAMED**。7 个补丁对应的上游源码在两版之间**逐字节相同**（只有
`package.json` 版本号变化），所以"上游吸收了我们的补丁"这一类机会这次不存在。

**判据面**：补丁仍需 `verify-patches`（仓库外 pristine dry-run + 结果逐字节对拍）与
`check-patch-resolutions` 双向守卫；改补丁后跑 `YARN_GLOBAL_FOLDER=<ws>/temp/yarn-global
corepack yarn install` 并提交 `yarn.lock`。

## 裁决五：`session-telemetry-otel` 改为**静态关闭**，并修掉掩盖它的那条冒烟入参

这不是 0.2.0 引入的，是本次对照"默认值面"时顺带确认的既有事实：

- 上游该行缺省 `FEEDBACK_ONLY`：**用户显式反馈时**（点赞/点踩、编辑、撤回）把**截至该事件的
  完整会话规范前缀**（含消息正文、工具参数与结果、工作区路径）导出到 OTLP 采集端；
- 我们唯一的关闭手段是 `packages/host/desktop/src/profile.ts` 里那条
  "`DSH_TELEMETRY_DISABLED` 非空 ⇒ 该行 disabled" 的补丁，而 **`DSH_TELEMETRY_DISABLED`
  在本仓只由 CI/测试设置，运行期没有任何地方设它**（`main.ts` 只把它读进去传给组装层）
  ⇒ **生产客户端该行实际是挂载的**；
- 0.2.0 把它的默认采集端换成了新域名，并新增 `maxRequestBytes: 4000000`。

它和我们已关闭的 `session-log-deepseek` 是**同一类数据出境**（会话正文离开客户环境），差别只在
触发条件（显式反馈 vs 每个带 sessionId 的请求）。

**定案（2026-10-01 产品拍板）：与 `session-log-deepseek` 对齐，`cordis.patch.yml` 里静态
`disabled: true`，并把该行登记进 `mustStayDisabled`。** 代价是用户反馈不再上传给上游；
反馈本身照常记录在本地会话日志（`message-feedback` 行未动），本地链不受影响。
`profile.ts` 的环境变量门控保留，作为已禁用行上的幂等补丁。

### 5.1 这条闸门此前**在门禁上是无牙的**（本次实测，值得单独记）

`verify-profile-boot.mjs` 构造 profile 时传的是 `prepareDesktopProfile('1', home, 'win32')`
—— 即**总是**把 `DSH_TELEMETRY_DISABLED` 当作已设置。后果是那条运行期补丁在冒烟里永远生效，
"生产运行期没人设这个变量"这个事实被完全挡住。实测（隔离备份 + `trap` 还原 + sha256 前后对拍）：

| 变异 | 修复前 | 修复后 |
|---|---|---|
| 把 `- id: session-telemetry-otel disabled: true` 从 `cordis.patch.yml` 删掉 | **EXIT=0**（探针：`row=true fiber=none`） | — |
| 同时删掉静态禁用与名单项（行为闸门成唯一防线） | **EXIT=0**（假绿） | **EXIT=1**，报 `session-telemetry-otel is ACTIVE …` |

**修法两层**：
1. 冒烟改用**生产形态**入参 —— `prepareDesktopProfile(undefined, home, 'win32')`。
   冒烟要判的本来就是生产形态；传 `'1'` 等于自己把要判的对象改掉。
2. 补一条**与名单无关的行为判据**：`ctx.get('sessionTelemetry')` 必须不存在。
   该行是 `sessionTelemetry` 服务的**唯一**提供方（全仓只有一处
   `super(ctx, 'sessionTelemetry')`），所以"服务不存在"就是"这一行没生效"，
   与既有的 `office-to-pdf` → `officeToPdf` 判据同形；删名单项或改名单都不影响它。

**一般化的教训**：冒烟/门禁的**入参**也是判据的一部分。当某个缺陷的形态是"生产环境里某个开关
没人设"时，用"把开关设上"的入参去跑冒烟，判据就永远看不见它 —— 这类入参必须在代码里写明
它代表哪种形态，并在缺陷修复时重新审视。

## 裁决六：随包分发的语音模型权重**补上来源与许可声明**

安装包里的识别权重约 230 MB，是客户交付物的一部分，但不进 npm 依赖树，所以原有的包表覆盖不到。
查证后的准确事实（两条许可**不同**，不能笼统写成"开源"）：

## 影响面与未闭合

**升级带来的、用户可见的行为变化**（上游升级指南 `docs/upgrade-guide/v0.1.7-rc.2/` 的两篇，
均在 0.2.0-rc.2 新增）：

- **Schedule 三行搬进可选 bundle**：`time-context` / `schedule` / `ui-schedule` 从 web-app 组合
  移出，改由 `@deepseek-ai/dsh-experimental-schedule-bundle`（插件页"自动化任务"）插入。
  升级指南逐字警告"按 id 打开过 Schedule 的 profile 升级后会 `patch: entry schedule not found`、
  存量提醒停止投递"。**我们不受影响**：全仓对这三个 id 的引用为 0（自研 cron 走
  `packages/host/cron`，与上游 Schedule 无关），已复核 `cordis.patch.yml` 与用户补丁层都没有
  按 id 的 `disabled: false`。
- **工作详情（`ui-chat.transcriptView`）**：历史保存值 `normal` 现在显示为 **Detailed**（不再是
  Standard），非桌面 Web 的"缺省/非法值"也改为 Detailed，**桌面仍用 standard**。受影响面 =
  曾显式保存过 `normal` 的用户（行进中的 Turn 会展开过程组而不是折叠摘要）。存储值不被改写，
  用户可在 设置 → 通用 → 工作详情 里选回 Standard。

**清单面**：`THIRD_PARTY_NOTICES.md` 按 `verify:notices:write` 重生成（543 → 571 行；
554 个生产包，313 行过期 + 330 行新增，主要是 `@anthropic-ai/sdk` / `@aws-sdk/*` 的版本迁移，
外加裁决六的模型权重一节）。
`mac-runtime.ts` 的 `MACOS_ARM64_NATIVE_ENTRIES`、`verify-packaged-runtime.ts` 的
`REQUIRED_*` 清单与 `package.spec.ts` 的 `asarUnpack` glob **本次无需改动** ——
原生包家族没有改名，koffi 的平台包路径（`linux_x64/koffi.node` 等）逐字不变，
`asarUnpack` 的 `**/*.node` 覆盖仍然成立。
