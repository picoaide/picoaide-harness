## 1. 决定

**平台上的应用只在桌面客户端内使用**（形态对齐微信小程序）：员工从应用中心点开应用 → 由客户端
内置浏览器渲染；**任意浏览器直连应用地址都不能进入应用**。

## 2. 为什么（背景）

2026-09-19 的多视角评审与随后的对抗式回归审计证明：**"应用子域 + URL 换票"这条浏览器链路的
安全面很难收敛**——

- 登录 CSRF / 会话固定（把换票链接发给别人，对方以自己的浏览器获得**攻击者身份**的会话）；
- 该缺陷修好后仍可被**攻击者自选的 Host 头**按请求关闭（回归审计 P0，已修）；
- 即便修死，还残留：地址栏粘贴不可区分、跨 registrable domain 部署降级、兄弟应用可写同域
  cookie 造成两步会话固定、未识别 Host 回落主站、平台页无 favicon 等一串同源问题。

而客户端的形态天然消掉这一整类：

| 浏览器模型 | 客户端专属模型 |
| --- | --- |
| 身份靠 **URL 里的票** 传递（可转发、可粘贴、进历史/Referer） | 身份由**客户端注入**（它本来就持有员工会话） |
| 任何人可访问应用 origin（钓鱼/CSRF 面） | 没有可被第三方导航进入的会话入口 |
| SSO 组织**没有**浏览器 OIDC 登录 ⇒ 登录可见应用对他们不可用 | 客户端本来就走 OIDC 深链 ⇒ **顺带解决该缺口** |

## 3. 语义变化

| 项 | 现在 | 变更后 |
| --- | --- | --- |
| `access=public` | 允许匿名浏览器访问 | **仅客户端内匿名可用**（不再是"公网任何人"） |
| `access=login` / `whitelist` | 浏览器登录 + 换票 | **客户端注入员工身份**；浏览器入口关闭 |
| 分享应用 | 发 `https://<app>.<基域>` 链接 | 发深链（`picoaide://` / 渠道 scheme）→ 在客户端打开 |
| 浏览器换票链路 | 主路径 | **兼容模式**（由平台开关保留，默认关闭）；保留已落地的 fail-closed 加固作为安全网 |
| 应用 CRUD/诊断/发布 | 已有（客户端内） | 不变 |

## 4. 强制手段（可选的两种，本决策采用第 1 种起步）

1. **客户端铸造会话**（改动小、无需证书）：应用子域**不再提供任何浏览器可获得会话的入口**
   （登录页/换票端点在该模式下拒绝）；会话只能由客户端通过**已认证的员工 API** 铸造并写入
   自己的浏览器分区。浏览器拿不到会话 ⇒ 进不去应用。
2. **客户端内部 origin**（更强，无公网应用 origin）：应用只在客户端内部地址提供，公网子域
   直接 404。属后续加固项。

两者都保留"平台级开关"以便需要浏览器访问的部署回退（回退时用已落地的 fail-closed 换票加固）。

## 5. 深链必须渠道化（OEM/白标硬约束）

**深链 scheme 不属于厂商，属于渠道**：`channel.json` 的 `desktop.deep_link_scheme` 是唯一真源
（官方缺省 `picoaide`；example-a = `example-a-harness`、example-b = `example-b-harness`；OEM 客户可自定义，
甚至由客户方指定自己的 scheme）。任何地方**不得写死 `picoaide://`**。

现状（已核实，可直接复用）：

- 服务端真源=`server/internal/channel` 的 `DeepLinkScheme()`（带缺省与畸形校验，遇非法回落官方），
  已被 OIDC 深链复用：`server/internal/serverauth/oidc.go:389` 生成 `<scheme>://auth?token=…`；
- 客户端侧 scheme 随渠道包构建注入（桌面壳构造期注入 `DEEP_LINK_SCHEME`；企业侧由
  `picoaide-session` 行 config 注入）。

因此本决策补充三条硬规则：

1. **应用深链只允许由"知道自己是哪个渠道"的一方生成**：优先**客户端自己生成**（它持有随包 scheme）；
   服务端若要渲染（例如浏览器落到应用地址时的"请用客户端打开"引导页），必须走
   `channel.DeepLinkScheme()`，**不得有第二份实现**。
2. **链接格式是渠道级契约**，需要写进渠道包文档并在真源里定义（例如 `<scheme>://app/<app_id>`），
   任何新增的深链形态（打开应用/打开会话/回跳登录）都要复用同一套解析与校验，**校验保持严格**
   （未知 scheme/未知 host 一律丢弃，不静默回落官方 scheme）。
3. **多客户端并存可预期的**：同一台机器可能同时装了官方与 OEM 客户端，链接必须指向**目标部署所属
   渠道**的 scheme；跨渠道链接不工作属预期行为，需在文案里说清"请用你所在企业的客户端打开"。

## 6. 影响与待办（实施波次见台账）

- **服务端**：客户端铸造会话的员工 API；`apps.client_only` 开关（默认开）；应用子域在开启时
  拒绝登录页/换票；身份帧来源从"应用会话"扩展为"客户端注入会话"（同一份身份契约）。
- **客户端**：打开应用时先铸造会话并注入内置浏览器分区；应用中心"打开"与深链统一走这条路；
  分享文案改为深链。
- **文档/发布说明**：访问模型改写；把"浏览器模式"的一串限制标注为"仅兼容模式存在"；
  作者手册里"应用地址"相关段落同步（作者不应再假设公网可访问）。
- **保留**：换票 fail-closed 加固（兼容模式的安全网）、未识别 Host 404（防止公网 origin 被
  Host 混淆利用）、`/readyz` 等运维面不受影响。
