## 3. 关键判据（这次新增/升级的门禁）

### 3.1 P0-9：自有插件行不再"静默不激活"

上游 0.1.6 用 `auditStartupEntries` 取代 `assertEntriesActivated`：只有 7 个全局 required id
（`agent-loop`/`webserver`/`modules`/`connection`/`headless-runner`/`acp`/`sdk-jsonrpc-server`）
与 bootstrap Include 会 `throw`，**我方 18 个 `desktop-*`/`picoaide-*`/`pico-*` 行一个都不在表里**。

四种失败形态**逐类实测**（`temp/upgrade-016/probe-row-failure-classes.mjs`，可复跑）：

| 形态 | 上游行为 | 我们的守卫 |
|---|---|---|
| A 行的 `inject` 里有永不出现的服务（fiber 停在 PENDING） | **只打一条 warn**，`boot()` 正常 resolve | 判红 |
| B 必需行被 `disabled: true` | **连 warn 都没有**（doc：disabled required entries are ignored） | 判红 |
| C `apply` 同步抛异常 | `boot()` 直接 reject | 本来就 fail-loud（**不是**本次修的对象） |
| D 包说明符解析不到 | `boot()` 直接 reject | 本来就 fail-loud |

判据落在三处，共用**同一个真源** `packages/host/desktop/src/startup-rows.ts`：

1. `REQUIRED_DESKTOP_ROWS`（18 条）+ `assertRequiredRowsActive(ctx)`：`src/main.ts` boot 之后断言，
   失败走桌面自己的致命路径（Windows GUI 没有 stderr，warn 等于没有）。
2. `tests/startup-rows.spec.ts`：①每条 id 真的在 `composeEntries([prepared.patches])` 里且未 disable；
   ②`FIBER_ACTIVE`/`FIBER_FAILED` 与 cordis `lib/types/fiber.d.ts` 的 `const enum` 对拍
   （`const enum` 运行时被擦除，只能钉数值）；③断言本身对缺席/禁用/无 fiber/状态不对四态都判红。
   变异验证：改 id、改常量、短路收集、吞掉 loader 缺失、忽略 disabled —— **5/5 变红**。
3. `scripts/verify-loader-boot.mjs` 从**存在性**断言升级为激活断言（并加"任何已启用行不得 FAILED"）；
   `scripts/verify-profile-boot.mjs`（唯一挂载完整桌面组合树的地方）加必需行激活断言 + FAILED 扫描。
   变异验证：`FIBER_ACTIVE` 改错 → 红；把非必需行打成 FAILED → 红（只有 FAILED 扫描能抓到）。

**实测现状**：完整桌面组合树 **189 个条目、非 ACTIVE 且未 disable 的行 0 条**
（`temp/upgrade-016/probe-new-rows-state.mjs`）。

> 判据纪律：`REQUIRED_DESKTOP_ROWS` 只列"缺了它这个产品就不是它"的行，**不含可选客户端 UI 行** ——
> `profile.ts` 的 `filterRows` 会有意丢弃组合里解析不到的客户端行，把它们放进来就是启动假报警。

### 3.2 P1-13：`healProfilesModuleFallback` 语义

alpha.2 的改动是**加法**：新增 `materialize` 选项（默认 `true`）、新增只算不落盘的
`createProfileResolutionGeneration`、返回值从 `void` 变成 `ProfileResolutionGeneration`，
另拆出 `healIsolatedProfileModuleFallback` / `unlinkProfileModuleFallback`。
我们的单点调用 `healProfilesModuleFallback({ installAnchor, home })` **形状未变、返回值未用**
⇒ 无需改调用点。落盘形态也未变（proxy 记录仍是 `dsh.moduleFallback.targets`）。

但**打包版链路依赖"真的落盘"**（`module-resolution.ts` 的 CJS 重试、`removeStaleAsarFallbackLinks`
都建立在"共享 fallback 里有一条指向安装树的链接"之上）。因此补一条能力判据：
`tests/profile.spec.ts` 的 `profile module fallback generation (P1-13)`
—— 变异验证：把调用改成 `materialize: false` ⇒ **变红**。

### 3.3 G-9：打包清单必须覆盖"补丁目标新引入的静态 import"

`@deepseek-ai/dsh-sandbox-windows-acl`（**我们打补丁的包**）在 alpha.2 新增两处运行期静态 import：
`lib/runner.js` → `@deepseek-ai/dsh-subprocess/control`、`lib/types-CutH1Lgc.js` → `@deepseek-ai/dsh-lazy-require`。
两条此前**没有任何清单覆盖** ⇒ `afterPack` 会放行一个"点开 Windows 沙箱才炸"的包。

修法：两条（连同 package.json，共 4 条）进 `REQUIRED_PACKAGED_RUNTIME_ENTRIES`；
判据 = `tests/verify-packaged-runtime.spec.ts` 的「上游补丁目标的静态 import 必须在打包必需清单里」
（generic：扫 7 个补丁目标的 `lib/**/*.js`，把可解析的子路径 import 与清单对拍，只对磁盘上真实存在的落点提要求）
+ 「显式钉住 G-9 两条」。变异验证：删任一条 ⇒ **变红**（generic 用例还顺带发现 `dsh-subprocess-local` 也 import 同一子路径）。

### 3.5 P0-4 的服务端第二道闸门（D2 的「评估服务端剔除」结论：**要做**）

上游 0.1.6 起 `session-log-deepseek` **默认开启**，通过 `ctx.deepseekLlmApiExtensions.register('dsh_session_log', …)`
往每个带会话的 LLM 请求体顶层塞一份会话日志后缀（会话正文 / 工具参数与结果 / 工作区路径），
而我们的网关把请求体**逐字节转发**给客户配置的供应商。客户端侧已 `disabled`（治本，但只对
**我们发的**客户端生效，且上游默认值是 `true`，下次升级忘了就复发），因此加服务端侧第二道：

- 位置：`server/internal/llmgateway/sanitize.go`；三个转发入口全部接入
  （`forward` / `forwardEndpoint` / `forwardAnthropic` ⇒ 四条出站路径；
  `/v1/embeddings` 的体是服务端自己拼的 `{model,input}`，无客户端透传面，故不经过）。
- 判据取**前缀族** `dsh_` 而不是单个键名：0.1.6 这个字段就是「默认开启、无声新增」的
  （rc.2 完全没有），只钉一个名字意味着上游下次再加同族字段要重踩一遍。依据是上游自己的
  README：该字段「is a sibling of the DeepSeek request's model-input fields and is not
  inserted into messages, the system prompt, or tool schemas」——OpenAI 三个契约与
  Anthropic Messages 都没有 `dsh_` 前缀的顶层字段。
- 语义边界（故意保守）：只删**顶层**键；不含前缀时**原样返回同一段字节**（零重编码，网关
  「逐字节转发」的既有语义不变）；非 JSON 对象/解析失败时原样转发并记日志 —— 净化动作绝不
  能让一个合法请求失败。
- 判据：单元 7 例（含「无前缀不得重编码」「前缀只出现在值里不得剔除」「坏 JSON 原样透传」）
  + 端到端 6 例（四条路径 × 流式/非流式 + 反向对照 + Anthropic 路径）
  + **源码形状守卫**：任何 `bytes.NewReader(raw)` 所在函数都必须调用 `sanitizeOutboundBody`，
  将来新增协议忘接净化即红。**变异验证 4/4 全红**（拆三个入口各自的红、净化改恒等的红）。

认账残留：若上游改用**别的前缀**引入同类字段（例如 `deepseek_session_log`），服务端这条抓不到，
只能靠客户端侧闸门 + 升级审计的「上游新增默认行」清单兜住（本次就是靠审计发现的）。

### 3.6 终端（D3 拍板后补的行为判据）

产品口径：**终端该支持就支持** ⇒ `ui-sidebar-terminal` + `terminal-controller` 保持上游默认启用，
不加 `disabled`。但"启用"不等于"能用"，因此补了一条行为探针
`packages/host/desktop/scripts/e2e-terminal.mjs`（`yarn workspace dsh-plugin-desktop e2e:terminal`）：

登录 → 建工作区/会话 → 展开官方右栏 → 点「新建终端」→ 断言右栏出现 `bash` 标签 +
xterm 表面（DOM renderer 的 `.xterm-rows`）拿到提示符 → CDP 真敲
`echo PICO_TERMINAL_OK_2026` + Enter → 断言回显里出现 marker。**12 条断言全 PASS**，
截图在 `packages/host/desktop/.e2e-terminal/shots/`。

链路含义：客户端 `ui-sidebar-terminal`（inject `webTerminals`）→ 宿主
`@deepseek-ai/dsh-api-terminal-controller`（inject `subprocess` / `sandboxPolicy` / `typert`，
经 `subprocess.spawnTerminal` 起 pty）→ xterm 表面。也就是说这条断言同时证明了
**宿主行 ACTIVE 且真的能起进程**，而不只是"入口渲染出来了"。

写探针时踩到的三个坑（都写进脚本头注释，别再简化）：
① `clickLabel` 必须跳过 `disabled` 按钮（禁用按钮也能 `.click()`，「点了但没反应」会记成成功；
工作区选择器的「打开」在目录列表加载完前就是禁用的）；
② 点完「打开」必须断言模态框**真的关了**再往下走，否则后面全部在模态框后面空点；
③ 终端是 xterm 的 DOM renderer（`.xterm-rows` 有文本），不是 canvas，断言直接读文本。

安全口径（要写进发布说明）：**用户终端 ≠ Agent 沙箱** —— 它是登录用户自己的 shell，
不受会话沙箱模式与审批约束（上游设计如此）。

### 3.7 反假绿纪律


- **存在性 ≠ 激活**：`resolve(id)` 拿得到条目配置，不代表插件活着（P0-9 的双重盲区就是这么来的）。
- **补丁按 id 匹配、`name` 只当断言**：`applyEntryPatches` 把 `name` 从补丁里解构掉、只用于
  "name mismatch ⇒ skipping"（`@deepseek-ai/cordis-plugin-include/lib/index.js:69,96-99`）⇒
  **补丁改不了行的包名**，别指望用补丁模拟"包改名"。
- **补丁层的顺序有意义**：目标行是后面的层 `insert` 出来的，早于它的补丁就是"id 不存在 ⇒ 静默跳过"
  （本仓 `.cordis.patch.yml` 语义：id 不存在**只 warn**）。
- **不要与 `yarn check` 并发跑 yarn/vitest**：`prebuildWorkspaceDeps` 会对 `clean: true` 的包
  （如 `@picoaide/dsh-host-home`）先清 `lib/` 再重建，并发构建会读到空 `lib/`，
  表现为莫名其妙的 `TS2305: Module './desktop-home.ts' has no exported member …`。
  本次踩到一次（自证为瞬时竞态：lib 重建后两个符号都在）。
