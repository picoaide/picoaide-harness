## 3. 关键判据（这次新增/升级的门禁）

### 3.1 P0-9：自有插件行不再"静默不激活"

上游 0.1.6 用 `auditStartupEntries` 取代 `assertEntriesActivated`：只有 7 个全局 required id
（`agent-loop`/`webserver`/`modules`/`connection`/`headless-runner`/`acp`/`sdk-jsonrpc-server`）
与 bootstrap Include 会 `throw`，**我方 18 个 `desktop-*`/`picoaide-*`/`pico-*` 行一个都不在表里**。

四种失败形态**逐类实测**（`temp/upgrade-016/probe-row-failure-classes.mjs`，可复跑）：

| 形态 | 上游行为 | 我们的守卫 |
|---|---|---|
| A 行的 `inject` 里有永不出现的服务（fiber 停在 PENDING） | **只打一条 warn**，`boot()` 正常 resolve | 判红 |
| B 必需行被 `disabled: true` | **连 warn 都没有**（doc：disabled required entries are ignored） | 判红 |
| C `apply` 同步抛异常 | `boot()` 直接 reject | 本来就 fail-loud（**不是**本次修的对象） |
| D 包说明符解析不到 | `boot()` 直接 reject | 本来就 fail-loud |

判据落在三处，共用**同一个真源** `packages/host/desktop/src/startup-rows.ts`：

1. `REQUIRED_DESKTOP_ROWS`（18 条）+ `assertRequiredRowsActive(ctx)`：`src/main.ts` boot 之后断言，
   失败走桌面自己的致命路径（Windows GUI 没有 stderr，warn 等于没有）。
2. `tests/startup-rows.spec.ts`：①每条 id 真的在 `composeEntries([prepared.patches])` 里且未 disable；
   ②`FIBER_ACTIVE`/`FIBER_FAILED` 与 cordis `lib/types/fiber.d.ts` 的 `const enum` 对拍
   （`const enum` 运行时被擦除，只能钉数值）；③断言本身对缺席/禁用/无 fiber/状态不对四态都判红。
   变异验证：改 id、改常量、短路收集、吞掉 loader 缺失、忽略 disabled —— **5/5 变红**。
3. `scripts/verify-loader-boot.mjs` 从**存在性**断言升级为激活断言（并加"任何已启用行不得 FAILED"）；
   `scripts/verify-profile-boot.mjs`（唯一挂载完整桌面组合树的地方）加必需行激活断言 + FAILED 扫描。
   变异验证：`FIBER_ACTIVE` 改错 → 红；把非必需行打成 FAILED → 红（只有 FAILED 扫描能抓到）。

**实测现状**：完整桌面组合树 **189 个条目、非 ACTIVE 且未 disable 的行 0 条**
（`temp/upgrade-016/probe-new-rows-state.mjs`）。

> 判据纪律：`REQUIRED_DESKTOP_ROWS` 只列"缺了它这个产品就不是它"的行，**不含可选客户端 UI 行** ——
> `profile.ts` 的 `filterRows` 会有意丢弃组合里解析不到的客户端行，把它们放进来就是启动假报警。

### 3.2 P1-13：`healProfilesModuleFallback` 语义

alpha.2 的改动是**加法**：新增 `materialize` 选项（默认 `true`）、新增只算不落盘的
`createProfileResolutionGeneration`、返回值从 `void` 变成 `ProfileResolutionGeneration`，
另拆出 `healIsolatedProfileModuleFallback` / `unlinkProfileModuleFallback`。
我们的单点调用 `healProfilesModuleFallback({ installAnchor, home })` **形状未变、返回值未用**
⇒ 无需改调用点。落盘形态也未变（proxy 记录仍是 `dsh.moduleFallback.targets`）。

但**打包版链路依赖"真的落盘"**（`module-resolution.ts` 的 CJS 重试、`removeStaleAsarFallbackLinks`
都建立在"共享 fallback 里有一条指向安装树的链接"之上）。因此补一条能力判据：
`tests/profile.spec.ts` 的 `profile module fallback generation (P1-13)`
—— 变异验证：把调用改成 `materialize: false` ⇒ **变红**。

### 3.3 G-9：打包清单必须覆盖"补丁目标新引入的静态 import"

`@deepseek-ai/dsh-sandbox-windows-acl`（**我们打补丁的包**）在 alpha.2 新增两处运行期静态 import：
`lib/runner.js` → `@deepseek-ai/dsh-subprocess/control`、`lib/types-CutH1Lgc.js` → `@deepseek-ai/dsh-lazy-require`。
两条此前**没有任何清单覆盖** ⇒ `afterPack` 会放行一个"点开 Windows 沙箱才炸"的包。

修法：两条（连同 package.json，共 4 条）进 `REQUIRED_PACKAGED_RUNTIME_ENTRIES`；
判据 = `tests/verify-packaged-runtime.spec.ts` 的「上游补丁目标的静态 import 必须在打包必需清单里」
（generic：扫 7 个补丁目标的 `lib/**/*.js`，把可解析的子路径 import 与清单对拍，只对磁盘上真实存在的落点提要求）
+ 「显式钉住 G-9 两条」。变异验证：删任一条 ⇒ **变红**（generic 用例还顺带发现 `dsh-subprocess-local` 也 import 同一子路径）。

### 3.5 P0-4 的服务端第二道闸门（D2 的「评估服务端剔除」结论：**要做**）

上游 0.1.6 起 `session-log-deepseek` **默认开启**，通过 `ctx.deepseekLlmApiExtensions.register('dsh_session_log', …)`
往每个带会话的 LLM 请求体顶层塞一份会话日志后缀（会话正文 / 工具参数与结果 / 工作区路径），
而我们的网关把请求体**逐字节转发**给客户配置的供应商。客户端侧已 `disabled`（治本，但只对
**我们发的**客户端生效，且上游默认值是 `true`，下次升级忘了就复发），因此加服务端侧第二道：

- 位置：`server/internal/llmgateway/sanitize.go`；三个转发入口全部接入
  （`forward` / `forwardEndpoint` / `forwardAnthropic` ⇒ 四条出站路径；
  `/v1/embeddings` 的体是服务端自己拼的 `{model,input}`，无客户端透传面，故不经过）。
- 判据取**前缀族** `dsh_` 而不是单个键名：0.1.6 这个字段就是「默认开启、无声新增」的
  （rc.2 完全没有），只钉一个名字意味着上游下次再加同族字段要重踩一遍。依据是上游自己的
  README：该字段「is a sibling of the DeepSeek request's model-input fields and is not
  inserted into messages, the system prompt, or tool schemas」——OpenAI 三个契约与
  Anthropic Messages 都没有 `dsh_` 前缀的顶层字段。
- 语义边界（故意保守）：只删**顶层**键；不含前缀时**原样返回同一段字节**（零重编码，网关
  「逐字节转发」的既有语义不变）；非 JSON 对象/解析失败时原样转发并记日志 —— 净化动作绝不
  能让一个合法请求失败。
- 判据：单元 7 例（含「无前缀不得重编码」「前缀只出现在值里不得剔除」「坏 JSON 原样透传」）
  + 端到端 6 例（四条路径 × 流式/非流式 + 反向对照 + Anthropic 路径）
  + **源码形状守卫**：任何 `bytes.NewReader(raw)` 所在函数都必须调用 `sanitizeOutboundBody`，
  将来新增协议忘接净化即红。**变异验证 4/4 全红**（拆三个入口各自的红、净化改恒等的红）。

> **勘误（2026-09-22，网关出站体改造后）：本节上面的「逐字节转发」与「解析失败原样转发」两条
> 已不再成立**，读本节时以这里为准：
>
> 1. **坏 JSON 不再原样转发**：客户端体解析失败（含 `1e999` 这类整数/浮点溢出）时，网关
>    **400 失败关闭**，不再透传。原因是一次真实审计：fail-open 会让请求绕过同批新增的
>    `file_id` 归属守卫与 `user_id` 注入（解析不了就什么都不做，等于把守卫静默关掉）。
>    改写形态（`user_id` 注入）与拒绝形态都以 `json.Valid` + `Decoder.UseNumber()` 为判据，
>    **绝不接受"解析失败就放过"**。
> 2. **转发不再保证逐字节**：需要注入官方用户标识（chat 顶层 `user_id`、Responses 顶层
>    `user`、Anthropic `metadata.user_id`；服务端注入、客户端不可伪造）或命中 `file_id`
>    归属校验时，出站体是**重新编码**的 JSON。两条边界：≥64 KiB 且不含 `file_id`/
>    `"<键名>":`/`\u` 的体走**字节保持**快路径（直接尾插 `,"user_id":"uN"`）；
>    重新编码用 `SetEscapeHTML(false)` 且键序稳定，前缀缓存不受影响。空 body（`null`）→ 400。
>    另：`metadata` 存在但不是对象 ⇒ 400（不再静默改写并丢弃客户端原值）；`/v1/embeddings`
>    的客户端体从不转发，故其出站加工已移除（原为空转 + 纯误伤 404 面）。
> 3. **计量口径不变**：`usage` 的用量/费用仍按**客户端原始字节**估算 prompt
>    （`estimatePromptFallback` 吃 `raw`），出站体只用于转发，两者不再共用同一个切片。
> 4. `sanitizeOutboundBody` 自身（`dsh_` 前缀剔除）语义**未变**——它在上述流程之前/之后都只
>    做"无前缀 ⇒ 返回同一段字节"，本节描述的净化边界依然有效。

认账残留：若上游改用**别的前缀**引入同类字段（例如 `deepseek_session_log`），服务端这条抓不到，
只能靠客户端侧闸门 + 升级审计的「上游新增默认行」清单兜住（本次就是靠审计发现的）。

### 3.6 终端（D3 拍板后补的行为判据）

产品口径：**终端该支持就支持** ⇒ `ui-sidebar-terminal` + `terminal-controller` 保持上游默认启用，
不加 `disabled`。但"启用"不等于"能用"，因此补了一条行为探针
`packages/host/desktop/scripts/e2e-terminal.mjs`（`yarn workspace dsh-plugin-desktop e2e:terminal`）：

登录 → 建工作区/会话 → 展开官方右栏 → 点「新建终端」→ 断言右栏出现 `bash` 标签 +
xterm 表面（DOM renderer 的 `.xterm-rows`）拿到提示符 → CDP 真敲
`echo PICO_TERMINAL_OK_2026` + Enter → 断言回显里出现 marker。**12 条断言全 PASS**，
截图在 `packages/host/desktop/.e2e-terminal/shots/`。

链路含义：客户端 `ui-sidebar-terminal`（inject `webTerminals`）→ 宿主
`@deepseek-ai/dsh-api-terminal-controller`（inject `subprocess` / `sandboxPolicy` / `typert`，
经 `subprocess.spawnTerminal` 起 pty）→ xterm 表面。也就是说这条断言同时证明了
**宿主行 ACTIVE 且真的能起进程**，而不只是"入口渲染出来了"。

写探针时踩到的三个坑（都写进脚本头注释，别再简化）：
① `clickLabel` 必须跳过 `disabled` 按钮（禁用按钮也能 `.click()`，「点了但没反应」会记成成功；
工作区选择器的「打开」在目录列表加载完前就是禁用的）；
② 点完「打开」必须断言模态框**真的关了**再往下走，否则后面全部在模态框后面空点；
③ 终端是 xterm 的 DOM renderer（`.xterm-rows` 有文本），不是 canvas，断言直接读文本。

安全口径（要写进发布说明）：**用户终端 ≠ Agent 沙箱** —— 它是登录用户自己的 shell，
不受会话沙箱模式与审批约束（上游设计如此）。

### 3.7 反假绿纪律


- **存在性 ≠ 激活**：`resolve(id)` 拿得到条目配置，不代表插件活着（P0-9 的双重盲区就是这么来的）。
- **补丁按 id 匹配、`name` 只当断言**：`applyEntryPatches` 把 `name` 从补丁里解构掉、只用于
  "name mismatch ⇒ skipping"（`@deepseek-ai/cordis-plugin-include/lib/index.js:69,96-99`）⇒
  **补丁改不了行的包名**，别指望用补丁模拟"包改名"。
- **补丁层的顺序有意义**：目标行是后面的层 `insert` 出来的，早于它的补丁就是"id 不存在 ⇒ 静默跳过"
  （本仓 `.cordis.patch.yml` 语义：id 不存在**只 warn**）。
- **不要与 `yarn check` 并发跑 yarn/vitest**：`prebuildWorkspaceDeps` 会对 `clean: true` 的包
  （如 `@picoaide/dsh-host-home`）先清 `lib/` 再重建，并发构建会读到空 `lib/`，
  表现为莫名其妙的 `TS2305: Module './desktop-home.ts' has no exported member …`。
  本次踩到一次（自证为瞬时竞态：lib 重建后两个符号都在）。

### 3.8 P0-8 的孪生缺陷（issue #130）：关掉的是**客户端 UI 行**，服务来自**宿主行**

**症状（2.8.0 线上）**：`agentPreset=cordis`（界面名「创造模式」）的会话**全部**不可用，会话创建时
报 `agent-presets: preset "cordis" failed to mount: 1 row(s) did not activate:
tool-plugin-manager (@deepseek-ai/dsh-plugin-manager/tools): waiting for pluginManager`。

**根因链**（对照实验：`temp/issue-audit-r1/A-profile/probe-{with,without}.json`，同一份桌面 profile、
同一 pin `ddefc45fbc7f`，唯一变量是 prepare 回调里是否 provide `profileContext`）：

1. §2 的 P0-8 关掉的是**客户端 UI 行** `ui-plugin-manager`（侧栏 Plugins 页）；而 `pluginManager`
   **服务**由**宿主行** `plugin-manager`（`@deepseek-ai/dsh-plugin-manager`）提供 —— 两者是不同的行。
2. base bundle 的 `plugin-manager` 行由 `disabled: !!js "!ctx.get('profileContext')"` 控制
   （`deepseek-harness/packages/bundle/base/cordis.patch.yml:20-22`）。桌面宿主此前**没有** provide
   `profileContext`（`main.ts` 的 prepare 回调只有 `DSH_LAUNCH_ENVIRONMENT_KEY` / `desktopRuntime` / …），
   于是该行被**静默** disable（上游对 disabled 的 required 行连 warn 都没有）⇒ 服务不存在。
3. `cordis` preset 的行 `tool-plugin-manager` `inject: ['tools','pluginManager','sandboxPolicy']`
   ⇒ 永远停在 PENDING ⇒ 该 preset 的**每一条**会话都挂不起来。
4. **只有 cordis 一个 preset 因此挂掉**：`standard`/`ptc` 的同名行是 `disabled: true`
   （`presets/standard/agent.cordis.yml:264-266`、`presets/ptc/…:285-287`），只有 `cordis` 打开它。
   注意 `temp/issue-audit-r1/sweep-preset-deps.mjs` 的静态扫描对三个 preset 都会"命中"该包
   —— **它是引用面扫描，不读 `disabled`**，判定时必须再叠一层"这行到底开没开"。

**修复形状（两件事必须成对做，缺一即从"会话不可用"升级成"客户端起不来"）**：

| # | 改动 | 理由 |
|---|---|---|
| 1 | `src/main.ts` 在 prepare 回调 provide `profileContext`；构造唯一真源 = `src/profile.ts` 的 `desktopProfileContext(prepared)`（`scripts/verify-profile-boot.mjs` 用**同一个函数**） | 没有它 `plugin-manager` 行必被静默 disable；内联字面量会让 CI 冒烟测的不是生产路径 |
| 2 | `cordis.patch.yml` 显式 `- id: hmr` + `disabled: true` | `hmr` 行**共用同一个 profileContext 开关**，提供后它会跟着激活，而 `@deepseek-ai/dsh-hmr` 的 `Service.init` 要求存在 `appReady`（`packages/boot/hmr/src/index.ts:200-208`），`appReady` 只有 `@deepseek-ai/dsh-cmdline` 会 provide（CLI 的"应用就绪"语义）—— 桌面不走 cmdline ⇒ `fatal: plugin tree failed to load … Profile HMR requires application readiness`。桌面不依赖它：插件写面/重载在 `DesktopPluginsService`（`grep -rn "hmr\|reconcileProfilePatches" packages/host/desktop/src` 为空）；代价是插件启停为**重启后生效**（`plugin-manager` 在 hmr 缺席时的既定语义 `restart-required`，不是能力缺失） |

**残留限制（随包不带 pnpm）**：桌面**有意不** provide `ProfileContext.packageManager` —— 随包既没有 pnpm
也没有任何可执行包管理器入口（`package.json` 的 `files`/`asarUnpack` 零覆盖，`tests/package.spec.ts` 还用
`installDesktopPnpmRuntime` 等四条反向断言把"不带包管理器"钉成产品形态）。缺省时 `PluginManager` 用
`pnpmCommand: 'pnpm'`，即回落到 PATH：**插件服务与 `list_plugins`/`list_bundles`/启停照常可用**，
只有 `install_bundle`/`remove_bundle` 这类包操作在无 pnpm 的机器上以 `ENOENT`（exit 127）失败 ——
失败 loud（pnpm 的 stderr 原样经 `plugin-manager/install-log` 交给模型）。要恢复包操作面需随包带 pnpm。

**判据（`scripts/verify-profile-boot.mjs`，已被 `package.json` 的 `check` → CI Gate 串联）**：

- (a) `ctx.get('profileContext')` 有值 **且** `plugin-manager` 行未 disable **且** `ctx.get('pluginManager')` 有值；
- (b) **roster 里每个 preset 都真的 mount 一次**（`agentPresets.standingKeyFor(id)`）—— 遍历
  `list()` 实际返回的集合（Windows 上 `minimal` 被 `src/windows-agent-presets.ts` 隐藏），失败信息里
  原样带出"哪个 preset 的哪一行在等哪个服务"；
- (c) `hmr` 行保持 disable 且 `ctx.get('hmr')` 为空；
- (d) **产品决策行仍关着**：`fs-sandbox` / `session-log-deepseek` / `ui-sidebar-browser` /
  `ui-plugin-manager` / `office-to-pdf` / `ui-settings-plugins` 逐条断言 `disabled === true`（每条在代码里带理由）；
- (e) **运行时行集合 == 完整组合**（"整树被重算"的回归判据）：`ctx.loader.entries()` 必须覆盖
  `composeEntries([prepared.patches])` 声明的每一行，且布尔型 `disabled` 两侧一致（`!!js` 行不参与，
  由 (a)/(c) 逐条判）。这正是"provide profileContext **+ 补 appReady** 让 hmr 跑起来"那条路的失败形态：
  hmr 用 `readProfilePatches(profileContext)` 重算的组合**少掉我方组装期注入的 desktop/enterprise/渠道/
  自研业务层**，会把上面那批刻意关掉的行重新打开（`session-log-deepseek` 一开 = 会话正文出境 P0）。
  ⇒ **不要为了激活 hmr 去 provide `appReady`**；真要打开必须先把注入层的层级信息补进 `profileContext`。

**接线判据**（`tests/profile-context-wiring.spec.ts`，与冒烟分工）：冒烟**自己** provide `profileContext`
（它复刻的是 main.ts 的启动形态），所以只删 `main.ts` 里那一行时冒烟仍绿 —— 本仓吃过同形亏
（`provide(WASM_APPS_AI_RUNNER_SERVICE, …)` 当时无判据）。该 spec 因此直接读 `src/main.ts`
断言"经 `desktopProfileContext` 接线、且不得内联字面量"，并用真实 `prepareDesktopProfile` 断言
`desktopProfileContext` 的每个字段（`installAnchor` 按"真能被 `JSON.parse` 读"判，不是字符串比对）。

**变异验证**（原始输出 `temp/issue-fix-r1/F1/mutations/`；每轮 apply→跑→restore 后三个文件的 sha256 复原一致）：

| 变异 | 结果 |
|---|---|
| 去掉 provide（复刻修复前形态） | **红**：(a) 报 "did not publish profileContext" |
| 去掉 provide + 删 (a) | **红**：(b) 报 `cordis … tool-plugin-manager … waiting for pluginManager` |
| 去掉 provide + 删 (b) | **红**：(a) 报同一件事 |
| 去掉 provide + 删 (a)(b) | **绿** ⇒ 这两条正是拦住该 P0 的判据（其余 300 余行断言对此完全无感） |
| 删掉 `hmr` 的 `disabled: true` | **红**（boot 失败）：`Profile HMR requires application readiness` |
| `hmr` 改 `disabled: false` + 补一个 appReady | **红**：(c) 单独拦下 |
| 同上 + 删 (c) | **绿** ⇒ (c) 不是摆设 |
| 删掉 `main.ts`（生产路径）的 provide | **红**：接线 spec 报 `main.ts … to contain 'hostCtx.provide('profileContext', …'`（冒烟对此无感 ⇒ 两层判据互补） |
| boot 时追加一行把 `session-log-deepseek` 重新打开 | **红**：(e) 报 `composed=true live=false` |
| 往**桌面 patch 文件**里追加同一行（组合与运行时两边都说 enabled） | **红**：(d) 报 `product-decision rows are no longer disabled`（(e) 对这种"组合自身被改"结构性无感 ⇒ 两条都需要） |
| boot 时把 `dsh-memory-evolve` 行从组合里拿掉（= 树跑在更短的 patch 列表上） | **红**：(e) 报 `missing … dsh-memory-evolve` |
| 同上 + 删 (e) | **绿** ⇒ (e) 是这种形态的唯一捕捉者 |

> 判据 (e) 今天恒真（实测 `composed=192 / live=193`，唯一多出的是 Loader 自己的 `include` 行，
> `disabledMismatch=0`）；它拦的是运行时被**重算**的形态。方法学坑：变异 harness 自身出过两次错
> （多步变异各自从原始件出发 ⇒ 三个假绿；多文件变异对"非首个文件"不建备份 ⇒ restore 静默失败并把
> 之后 6 个变异全部污染），现在的 harness 每轮都从冻结基准件出发、还原后再复算 sha256。
