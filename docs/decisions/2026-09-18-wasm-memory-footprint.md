# WASM 应用平台：内存占用与释放（2026-09-18）

> 决策：把「内存四笔账」从编译期常量改为**部署声明的档位**，并给进程内编译模块缓存补上
> **空闲淘汰 + 主动归还 OS** 两条时间路径；同时收紧应用库句柄与 SQLite 页缓存。
> 目标场景：**几百个应用** + 2 GB 级小机器（默认档的 2550 MiB 理论峰值让它连启动自检都过不了）。

## 1. 背景与实测（为什么必须改）

### 1.1 阻挡现象（2 GB 测试机）

启用应用子域（`PICOAI_APPS_BASE_DOMAIN`）会触发 §4.3 的内存四笔账启动自检，默认档：

| 账 | 值 | 来源 |
|---|---|---|
| 实例池 | 2048 MiB | 32 并发 × 64 MiB（`limits.GlobalInstances` × `InstanceMemoryPages`） |
| 编译峰值 | 256 MiB | `WasmMaxBytes`(32 MiB) × 8 |
| 上传峰值 | 118 MiB | base64 单次峰值 |
| 缓存驻留 | 128 MiB | `CompileCacheMaxBytes`(512 MiB) / 4 |
| **合计** | **2550 MiB** | 要求 `MemAvailable ≥ 3.56 GiB` |

2 GB 机器（可用 992 MiB）实测**拒绝启动**：

```
WASM 应用平台启动自检失败：INTERNAL: 理论内存峰值超过可用内存的安全水位，拒绝启动
```

设计文档给出的补救路径只有「扩容机器内存，或由平台管理员下调可用实例数（当前为编译期常量，
需重新构建）」——即**改一次档位要重新构建镜像**，而控制台里根本看不到这一项。

### 1.2 常驻与释放的实测（`temp/wasm-mem-probe/`，20 个 3.45 MiB Go 应用）

用平台同款运行期配置（`WithCloseOnContextDone` + 64 MiB 实例上限 + 磁盘编译缓存）：

| 观测 | 数值 |
|---|---|
| 编译并缓存 20 个模块后的 RSS | **+496 MiB ≈ 25 MB/应用**（= wasm 字节的 **144×**，而记账假设只有 4×） |
| 全部 `Close()` 之后 | RSS **一点没回落**（已归还峰值 **0%**） |
| `Close()` + `debug.FreeOSMemory()` 之后 | 仅回落约 20%（仍 +396 MiB） |
| 模块"存活"部分（heap_alloc） | ≈ **6 MiB/模块**（179 MB/20 → 关停后 121 MB/20） |

结论两条：

1. **常驻成本不在实例上**：实例是每请求新建、请求结束即 `Close`（`runtime.Serve` 的
   `defer mod.Close`）——这部分已经是对的。真正的长期成本是**进程内编译模块缓存**与
   **应用库句柄**（每句柄 2 条 SQLite 连接，默认页缓存 2 MiB/连接）。
2. **"Close 了"≠"还给 OS"**：Go 堆会把刚释放的页留着复用。几百个应用逐个被访问一次，
   RSS 就会拾级而上且不回落——必须**显式归还**。

### 1.3 旧实现里两个会随应用数放大的点

- `moduleCache` 的上限**直接复用磁盘缓存**（512 MiB 记账 / 4096 条），且**只在容量超限时**
  按 LRU 淘汰：容量没满时条目永不过期 ⇒ 几百个应用"各用一次"就能把常驻顶到上限并长期占住。
- 库句柄空闲回收 **10 分钟**，回收只在"下一次同应用请求"时顺手做——没人再访问的应用
  会一直占着连接与页缓存。

## 2. 决策

### 2.1 部署内存档位（`PICOAI_WASM_MEMORY_PROFILE`）

一份数值同时驱动**启动自检**与**运行期强制**（队列并发 / 实例内存上限 / 进程内模块缓存上限 /
应用库句柄上限），因此"自检算的账"与"实际跑的账"不会分叉：

| 档位 | 并发 | 单实例上限 | 模块缓存 | 四笔账合计 |
|---|---|---|---|---|
| `default`（缺省，行为与历史逐值一致） | 32 | 64 MiB | 128 MiB | 2550 MiB |
| `small`（2 GB 级机器） | 3 | 64 MiB | 64 MiB | **630 MiB** |
| `large`（大机器） | 64 | 64 MiB | 256 MiB | 4726 MiB |

- **单实例上限不缩**（`small` 保持 64 MiB）：降的是并发数，不是"每个应用能用的内存"——
  把上限压到 32 MiB 会让应用在平台承诺之内却跑不起来（错误形态是 `RUNTIME_MEMORY`）。
- 档位名未知 ⇒ **拒绝启动**（静默回落默认会让小机器在"以为已降档"的状态下 OOM）。
- 判据本身一点没放宽：仍然是 `理论峰值 ≤ 可用内存 × 70%`，只是账本可按部署声明。

### 2.2 进程内模块缓存：与磁盘解耦 + 空闲淘汰

- 新增 `limits.ModuleCacheMaxBytes`（128 MiB 记账，**默认档与旧"缓存驻留"账等值**）、
  `ModuleCacheMaxEntries`（128）、`ModuleCacheIdleTTL`（10 min）。
- `moduleCache.sweep()`：逐出"空闲超过 TTL 且 `refs == 0`"的条目（在途请求不受影响），
  由 `Server.sweepLoop()` 每分钟跑一次；逐出即 `Close`（释放机器码）。
- `Server.EvictApp(appID)`：**事件驱动**逐出——管理端下架 / 冻结 / 删除、
  发布者自行下架 / 删除时立刻丢掉该应用的模块与库句柄（不等 TTL）。

### 2.3 主动归还 OS（`reclaim.go`）

每次真正释放之后，**限频（≥30 s）**调用一次 `debug.FreeOSMemory()`：FreeOSMemory 触发
STW 的强制 GC + scavenge，逐出是高频事件，不设间隔会把 CPU 打满；间隔内被合并的释放
请求在下次真调用时一并记入日志（不丢"发生过 N 次释放"这个事实）。

### 2.4 应用库句柄与 SQLite 页缓存瘦身

- 句柄空闲回收 10 min → **3 min**（重开成本实测 1.7–3.2 ms），并新增后台 `sweepIdle()`
  （旧实现只在"下一次同应用请求"时顺手回收，没人再访问就永不回收）。
- 每条连接 `PRAGMA cache_size = -1024`（1 MiB，SQLite 默认 2 MiB）⇒ 每应用库句柄
  从 ~4 MiB 常驻降到 ~2 MiB，且随应用数线性下降。

## 3. 影响与代价

- **默认档行为不变**：不设 `PICOAI_WASM_MEMORY_PROFILE` 的部署，四笔账数值与判据逐值相同；
  变化只在"缓存可以空闲过期"与"归还 OS"这两条（都是用户要的方向）。
- 进程内缓存的**冷启动变多**：空闲 10 分钟后再访问要重新编译一次（磁盘缓存命中，实测
  反序列化远快于冷编译）；这是"常驻 vs 延迟"的取舍，TTL 可按需在 `limits` 调整。
- `FreeOSMemory` 有 STW 成本，用 30 s 限频 + 只在真正释放后触发来摊销。
- `small` 档把并发降到 3：小机器上的**吞吐**换**可用性**（应用能跑起来 > 并发高）。
- 未做（明确认账）：`/readyz` 尚未把档位与模块缓存水位做成结构化字段（日志里有）；
  空闲 TTL 目前是编译期常量，未做成部署旋钮（避免旋钮泛滥，先观察真实命中率）。

## 4. 验证

- 单元测试：`memprofile`（档位解析/默认等值/small 在 992 MiB 下通过）、
  `readyz`（默认档逐值等于历史常量、换档真的改四笔账、零值回落、错误信封带档位名）、
  `appserver`（空闲淘汰只清过期且无引用的条目、在途不被逐出、事件驱动逐出只清该应用、
  限频归还只按最小间隔触发）、`cmd/server`（接线断言：档位来自环境、喂给 appserver、
  下架/冻结/删除挂上 `EvictApp`）。
- 部署验证（测试环境，2 GB 机器）：`profile=small` 启动日志
  `total=630MB available=1222MB limit=855MB` ⇒ 通过；`platform ready (subdomain=true …)`。
- 端到端（真实浏览器会话链路，curl + cookie jar）：
  主站员工登录 → 应用子域 302 到 `/app-ticket` → 换票 302 回应用子域并落 `picoaide_app`
  → 应用页面 200（应用自己的标题）→ 应用内功能：
  `POST /api/hello` 写库并在"墙"上可见、`/ai` 调 `ai.chat` 得到模型回复且用量记在**发起用户**
  账上（`usage` 行 cost 非零）、调用事件表 `wasm_call_events` 记 `ok` + `peak≈6 MiB` + `host_calls`。
- 反向对照：未知应用子域 **404 且不回落主站**；主站证书与站点不受影响。
