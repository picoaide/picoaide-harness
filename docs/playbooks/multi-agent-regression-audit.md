# 多子代理回归审计：话术与提示词手册

## 通用一句话（可直接抄，任意仓库/任意两版之间）

> 派多个子代理并行审计 `<上一个版本 tag>..HEAD` 的代码变更引入的新 BUG：按包/模块分片、只读分析、
> 每条发现必须给 `文件:行号` + 引入提交 + 可复跑的命令与输出（既有缺陷不算）；我修完后再派**新**子代理
> 专门证伪这些修复（回退修复必须让对应测试变红，无法变红的断言算缺口），一轮一轮直到某一轮
> **没有任何代理给出 P2 及以上**为止。

极简版（贴给自己看）：

> 多子代理审 `<tag>..HEAD` 的新 BUG → 我修 → 新子代理证伪我的修复（回退即红）→ 循环到一轮 0 个 P2+。

四个不能删的要素：**范围锚定 diff**、**证据可复跑**、**修复要被新代理证伪**、**停止条件是 0 个 P2+（不是"没发现"）**。


> 来源：2026-09-17 对 `v2.7.5-beta.2..HEAD`（25 个提交）的 R9 回归审计，8 轮 / 17 个子代理，
> 共 46 项有效发现（P1×1、P2×17、P3×28），全部修复并带回归用例，最终收敛判定 `CONVERGED`。
> 适用范围：**"这段改动引入了什么新 BUG"** 型审计（发版前回归、大 feature 合入后、修复轮之后的收口）。

---

## 0. 方法论一页（先看这个）

**核心循环**：`侦察分片 → 并行找 bug（R1）→ 汇总去重 → 修复 → 派新代理证伪修复（R2）→ 再修 → … → 收敛判定`

四条让发现"变真"的硬机制：

1. **基线锚定**：一切以 `base..HEAD` 的 diff 为范围，明确"有效发现 = 这段 diff 引入或放大的缺陷"，
   把"既有缺陷 / 风格 / 缺测试"排除在有效发现之外（否则代理会刷一堆噪音）。
2. **证据三件套**：`文件:行号`（HEAD 上）+ **引入它的提交** + **可复跑的命令与输出**。
   没有第三项的发现一律降置信度。
3. **变异自证**：每条新/改的测试都要"把修复回退到副本里 → 该用例必须变红"。
   杀不死的断言 = P3 判别力缺口（本次靠这条抓到 5 次假绿守卫）。
4. **修复也要被审**：修复本身是新代码，**每轮修复后必须由新一轮代理专门证伪**
   （本次 R7 抓到的那条 P2 正是 R6 修复的副作用）。

**调度参数经验**（4 vCPU / 大仓库）：
- 分片数 5~8：按"包 × 职责"切，单代理 diff 上限约 1500 行；超过就再切。
- 一次派 6~7 个（并行读写源码，CPU 不冲突）；复核轮 1~2 个（要深挖，不要摊薄）。
- 每轮结束由**主控自己**复核每条发现（跑一遍对方的命令）再决定修不修——代理会给出"方向对但结论错"的条目。
- 停止条件：**一整轮 0 个 P2 及以上**，且剩余项可归类为"刻意构造的输入 / fail-closed / 已知取舍"。

## 1. 侦察 / 分片提示词（主控自己做，或派一个"规划代理"）

```
你是发布前的回归审计规划员。仓库 /path/to/repo，分支 <branch>，基线 tag <BASE>，HEAD=<HEAD>。
请只输出一个分片方案（不要审代码）：
1) 跑 `git diff --stat <BASE>..HEAD`，按"包/模块 × 职责"聚类，给出每个分片的：名称、覆盖路径、
   改动行数量级、为什么这些文件要一起看（耦合点）；
2) 列出跨分片的**接缝风险**（同一模式在多处出现、事件/契约跨包、构建与产物同步、门禁脚本自身正确性），
   这些必须显式指派给某个分片或单独成片；
3) 给出每个分片的"最可能出问题的 5 个具体模式"（不是泛泛的"检查质量"）。
约束：单分片 diff ≤1500 行；分片数 5~8；只读，不得修改任何文件。
```

## 2. 分片审计代理（R1 型，主力）

```
你是 <仓库> 的回归审计员。先读 <BRIEF 文件路径>（审计目标 / 纪律 / 报告格式），然后严格按它执行。

你的分片：<分片名>（<一句话职责>）。覆盖：
- <路径 1>
- <路径 2>
（不含：<明确排除的路径>，那由其它代理负责）

审计范围 = `git diff <BASE>..HEAD -- <你的路径>`。相关提交用 `git show <sha>` 逐个读。

重点排查方向（每条都要可证伪证据）：
1. <模式 1，例如"半个修复：一个调用点改了，兄弟没改">
2. <模式 2，例如"新守卫在某个入口没被调用 / 时序错（先截断后脱敏）">
3. <模式 3，例如"插值/替换：必须函数替换，禁用字符串替换">
4. <模式 4，例如"并发/时序：CAS、epoch、updatedAt 单调性、恢复早于订阅">
5. <模式 5，例如"时区/日历边界">
6. 新增/修改的测试是否**把错误行为锁成预期**。

纪律：
- **只读**：禁止修改任何被 git 跟踪的文件；临时脚本/日志写 `temp/<audit-id>/<你的分片>/`。
- 允许：git / node / 定向 `vitest run <单个 spec>` / 自写探针。**不要**跑全量构建或全量测试套件。
- 不要 `git checkout/stash/reset/clean`（工作目录可能有并发写者）。
- 结论必须可证伪：`文件:行号`（HEAD）+ 引入提交 + 错在哪 + **什么输入下会错** + 你**实际跑过**的命令与输出。
- 排除：base 上就存在且 diff 没放大的缺陷（可提及但标 `pre-existing`）、风格、纯覆盖度问题。

产出（严格按此格式）：
## 分片：<名称>
### 结论摘要
<一句话：找到 N 个有效发现 / 0 个>
### 发现
#### [P0|P1|P2|P3] <一句话标题>
- 文件：`path:line`（HEAD）
- 引入提交：`<sha> <标题>`
- 现象与触发条件：<具体输入/时序/平台；说明为什么 base 上不会这样>
- 证据：<跑过的命令 + 关键输出，或精确代码路径推理>
- 修复方向：<一句话>
- 置信度：高/中/低（低必须说明还缺什么证据）
### 已核查为干净（简述）
- <你重点看过但确认没问题的点>

没有发现就明确写"0 个有效发现"，并列出核查范围。**宁缺毋滥**：不确定的写低置信度。
```

## 3. 对抗复核代理（R2+ 型，**最重要的一环**）

用途：每一轮修复之后，派新代理去**证伪刚做的修复**。核心话术是"找反例"，不是"确认没问题"。

```
你是第 <N> 轮**对抗复核员**。对象：刚提交的 `<sha>`（<一句话说明改了什么>）。

先读：<BRIEF>、<FINDINGS/前几轮报告>、以及当前实现（`git show <sha> -- <path>`）。前几轮已经找到过
<举 2~3 个例子>，所以这一轮要求你**尽力证伪**，而不是确认。

## 待证伪的改动
<逐条列出：文件、新的判据/顺序/阈值、声称的不变量>

## 必须回答（每条都要实跑证据）
1. **反例搜索**：构造**新的**（前几轮没用过的）输入/时序/平台组合，从这些方向穷举：
   <方向 A>、<方向 B>、<方向 C>。给出：枚举了多少组、命中多少组、每组最小复现，
   并按危害分类（换绑到真实可达对象 / fail-closed / 仅文案困惑）。
2. **不变量复核**：<不变量 1，如"base 非空 → 当前非空，差异 = 0">、<不变量 2>、
   <不变量 3，如"与上一版对拍只应收紧，不得放宽">。给出规模与结果。
3. **变异/判别力**：把新增/修改的测试逐条对应的实现规则做**针对性变异**（≥12 个 mutant），
   给出"哪条断言杀死哪个 mutant"的矩阵；**列出没有任何 mutant 能杀死的断言**（= P3 缺口）。
4. **接线唯一性**：生产路径是否只有一处实现/消费点，有无旁路。

## 纪律
- 只读仓库；实验在 `temp/<audit-id>/<你的名字>/` 的副本里做；不要跑全量构建/套件。
- 报告格式：发现（级别 / 文件:行 / 触发 / 证据命令+输出 / 修复方向 / 置信度）+ 已核查为干净。
- **0 个发现也必须附实跑证据**（枚举规模 + 归因统计 + 变异矩阵）。
- 最后一节给一句**收敛判定**：`CONVERGED`（无 P2+ 且修复正确完整）或 `NOT CONVERGED`（附最小反例）。
```

### 3.1 "只收紧不放宽" 专项话术（针对修复轮）

```
专项检查：与上一轮被审版本 <sha> 对拍 ——
(a) 有没有"上一版接受、当前拒绝"的输入？逐条解释是否可由本轮新判据解释（UNEXPLAINED 必须为 0）；
(b) 有没有"上一版拒绝、当前接受"的输入？**每一条都要单独列出**（这是修复引入的放宽，最容易出事）；
(c) 把这些输入按"真实可达 / fail-closed / 仅文案"分类，指出是否存在 P2 及以上。
```

## 4. 变异自证提示词（可单独派，也可并入 2/3）

```
你的任务是**测试判别力审计**（不评价产品代码）：
1) 找出本次 diff 新增/修改的全部断言，逐条回答："把对应的生产代码改回修复前的样子，这条断言会红吗？"
2) 做法：把仓库复制到 `temp/<audit-id>/mut/`（或只复制相关包），**在副本里**逐条回退修复，
   跑对应单测，记录结果；一次只回退一处（单点变异），必要时做组合回退；
3) 输出矩阵：`断言 ↔ mutant ↔ 红/绿`；
4) 结论：列出**杀不死的断言**（假绿），并说明"这条断言本意守的是什么行为、应该怎么改才能真正守住"。
注意：源码级断言（grep 文件内容）和"存在某字符串"型断言最容易假绿，优先怀疑这两类。
```

## 5. 收敛判定提示词（最后一轮）

```
你是收尾确认轮的对抗复核员。对象：`<sha>`（最后一轮修复）。
任务：
1) 复核上一轮每处修复是否正确、完整、**零放宽、零误伤**（正反两个方向都要跑）；
2) 回答"还有没有 P2 及以上"：标准 = 能把结果指向**真实可达且本该指向别处**的对象，
   且触发形态是**用户/运维可能写出的真实值**（不是刻意构造的同形/编码垃圾）。给出枚举规模与分类统计；
3) 复核三条不变量：<base 兼容>、<强档/关键路径与 base 逐条一致>、<与上一版对拍只收紧>；
4) 明确回答：**这轮之后是否应当停止加固**？给出理由（边际收益 vs 回归风险），
   若建议继续，给出**最小**的下一处改动（一处，覆盖最多剩余形态）。
最后给一句话判定：CONVERGED / NOT CONVERGED。
```

## 6. 修复轮纪律（给主控/修复代理，不是提示词而是检查单）

- **同类问题全仓扫**：修一处就 `grep` 同一模式的所有出现（本次 `replaceAll` 有 9 处、`t()` 有 7 处）。
- **注释与实现同步**：修复后回头改掉"声称逐字节等价""一处覆盖全部"这类**已经变假**的注释
  （本次 R2/R5/R6/R8 各抓到一次）。
- **文档与承诺同步**：报告/发布说明里写"已实施"的，必须真在代码里实施（R8-2 就是文档虚报）。
- **测试要有判别力**：新增用例写完先自问"回退修复它红不红"，红了再提交。
- **行为变化显式化**：与 base 有意不同的行为，写进注释 + 用例 + 报告（不要靠"等价"含糊过去）。
- **提交粒度**：一轮修复一个提交，提交信息写清"修了什么 + 对抗复核证据"；文档同步单独提交。
- **发版前拓扑检查**：`git merge-base --is-ancestor <上一个 tag> HEAD` —— 上一个 tag 可能在旁支，
  直接发新 tag 会**静默丢掉它的修复**（2026-09-17 v2.7.5-beta.4 实战）。

## 7. 反面话术（不要这样问）

| 别这样写 | 为什么 | 改成 |
| --- | --- | --- |
| "全面检查这段代码有没有问题" | 代理会报风格/覆盖度/既有缺陷，淹没真问题 | 锚定 diff + 定义"有效发现" + 排除 pre-existing |
| "确认这个修复没问题" | 确认偏误，代理会顺着作者意图走 | "尽力证伪 / 找反例 / 给出生存的 mutant 列表" |
| "跑一遍测试看看" | 门禁绿 ≠ 安全（假绿守卫已被抓到 5 次） | "把修复回退到副本里，证明用例会红" |
| "找出所有缺陷" | 无边界的清单会掺水 | "给出最小复现 + 危害分类 + 置信度" |
| "0 个发现就直接说 OK" | 代理会偷懒"没找到" | "0 个发现也必须附枚举规模与变异矩阵" |
| 一轮到底 | 修复会引入新回归（R7 的 P2 就是 R6 的副作用） | 每轮修复后都由**新**代理复核 |
