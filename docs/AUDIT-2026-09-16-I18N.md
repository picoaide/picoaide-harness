**机制是对的，覆盖是坏的。**

## 0.5 【P0 独立缺陷】macOS 初次语言判定恒为英文 —— 打包配置少了一个下划线

**症状**（用户 2026-09-16 报告）：macOS 上首次启动恒为英文，**系统语言是中文也一样**；托盘与界面同时中招。手动在「设置 → 通用 → 语言」切换后能生效（因为那会写入 `locale.preference`），但每次全新安装/未设置过偏好的用户都从英文开始。

### 根因

`packages/host/desktop/package.json:313-316`：

```json
"electronLanguages": [
  "zh-CN",
  "en-US"
],
```

electron-builder 的 `electronLanguages` 用来**裁剪 Electron 的本地化目录**，而 macOS 上这些目录是 **`.lproj` 目录**，命名用**下划线**（Chromium 的 locale id 用连字符，macOS bundle 约定用下划线）。Electron 43.4.0 的 mac 包在主 bundle 的 `Contents/Resources/` 下带 **57 个 `.lproj`**，其中中文是 **`zh_CN.lproj`** / `zh_TW.lproj`（实测：读 `electron-v43.4.0-darwin-arm64.zip` 的 zip central directory）。

electron-builder 26.15.3 的匹配逻辑（`app-builder-lib/out/electron/ElectronFramework.js:67-90`）是**字面量比较**，比较对象是目录 basename 的小写形式：

```js
const language = path.basename(file, ".lproj").toLowerCase()   // zh_CN.lproj → "zh_cn"
const isWantedLocale = wantedLanguages.some(wantedLanguage =>
  wantedLanguage === language                     // 精确
  || wantedLanguage.startsWith(`${language}-`)    // 前缀（连字符）
  || wantedLanguage.startsWith(`${language}_`)    // 前缀（下划线）
)
```

代入我们的配置（已小写化）：

| 配置项 | 目录 basename | 判定 | 结果 |
|---|---|---|---|
| `"zh-cn"` | `zh_cn` | `"zh-cn" === "zh_cn"` ✗；`.startsWith("zh_cn-")` ✗；`.startsWith("zh_cn_")` ✗ | **删除** ❌ |
| `"en-us"` | `en` | `"en-us".startsWith("en-")` ✓ | 保留 ✅ |

**连字符 vs 下划线之差 ⇒ `zh_CN.lproj` 被删掉，只剩 `en.lproj`。**

实测产物佐证（本分支刚打出的 `temp/mac-tray/beta-2.7.5-beta.1-mac.dmg`）：

```
PicoAide Harness.app/Contents/Resources/
  en.lproj          ← 唯一幸存，且是空目录
  （其余 56 个 .lproj 全部被删）
```

### 为什么这会导致「界面也是英文」而不只是托盘

macOS 解析 App 语言的规则是：**用户的首选语言列表 ∩ App 声明支持的本地化**。App 只声明了 `en`，中文系统下交集为空 ⇒ 回落到开发区域（默认 `en`）。于是：

```
系统语言 = 简体中文
  → macOS 判定 App 语言 = en（因为 bundle 只声明 en）
  → app.getLocale()        = "en-US"        → 托盘走 desktopLocaleFromLanguageTag → 'en'
  → navigator.languages    = ["en-US","en"] → upstream detectBrowserLocale 命中 'en' → 界面英文
```

一处根因、两个症状。与上游 `deepseek-harness/packages/client/locale/src/client/index.ts:515-521` 的 `detectBrowserLocale` 无关——**那段代码本身是对的**（本机实测：`LANG=zh_CN.UTF-8` 时 `navigator.languages` 正确返回 `["zh-CN","zh"]`，`app.getLocale()` 返回 `zh-CN`）。是喂给它的输入在 macOS 打包时被污染了。

同类已知问题：Electron [#26612](https://github.com/electron/electron/issues/26612)、lobehub [PR #17804](https://github.com/lobehub/lobehub/pull/17804)（标题即 *"resolve UI language from the OS instead of the pruned app locale"*，其提交说明写明打包裁剪 `.lproj` 会让 `app.getLocale()` 与 `navigator.language` 双双报 `en-US`）。

### 修复

**A（已实施 2026-09-16）** —— 用 macOS 目录名的下划线形式：

```json
"electronLanguages": [
  "en-US",
  "zh_CN"
],
```

用 electron-builder 的真实匹配逻辑 + Electron 43.4.0 主 bundle 的真实 55 个 `.lproj` 清单对拍（`temp/i18n-audit/verify-electronlanguages.py`）：

| 配置 | 幸存 `.lproj` | 中文本地化 |
|---|---|---|
| `["zh-CN","en-US"]`（修复前） | `en.lproj` | **不可用** ❌ |
| `["en-US","zh_CN"]`（修复后） | `en.lproj`, `zh_CN.lproj` | **可用** ✅ |

修复前的模拟结果（只剩 `en.lproj`）与本分支 DMG 实测**逐字一致**，说明该模拟忠实、可作为离线回归判据。
根部守卫 `check:layout` / `check:inventories` / `check:workflows` / `check:ci-scripts` 全绿；全仓无任何代码引用 `.lproj`，无其他依赖面。
（未含 `zh_TW`：用户 2026-09-16 定案只要简中 + 英文；将来若需繁体，按同一规则加 `"zh_TW"` 即可。）

> **遗留：缺少回归守卫。** 当前没有任何测试/脚本钉住 `electronLanguages`，而这条缺陷是「静默 + 仅 macOS + CI 被 `--lang=zh-CN` 掩盖」三重隐身，极易再次退化。建议补一条断言：对每个配置项，模拟 electron-builder 的反向匹配（`wanted === basename` 或 `wanted.startsWith(basename + '-' | '_')`），并至少对 `zh_CN` / `en` 两个真实目录名断言命中。**注意**：本审计进行时有另一会话正在同一工作目录编辑 `packages/host/desktop/tests/`（主题 token 任务），落地守卫前需先避让。

**B（可选加固，未实施）** —— 显式声明支持的本地化，不依赖 `.lproj` 扫描结果：

```json
"mac": {
  "extendInfo": {
    "CFBundleLocalizations": ["en", "zh-Hans", "zh-Hant"]
  }
}
```

**C（可选，未实施）** —— 主进程用 `app.getPreferredSystemLanguages()`（读系统设置、**不受 App 本地化裁剪影响**）解析语言，再喂给渲染进程，使任何代码路径都不再依赖被污染的值。lobehub 走的就是这条路（经 `additionalArguments` + preload 传给渲染进程）。

> 注意：主进程已有 `showDirectoryPicker` 在用 `this.currentLocale`（`electron-runtime.ts:262`），A 修好后 `app.getLocale()` 即恢复正常，托盘、原生对话框、渲染进程一并转正。

### 为什么 CI 一直没发现

`packages/host/desktop/scripts/e2e-client.mjs:221` 恒定用 `--lang=zh-CN` 启动被测应用，**强行覆盖了被污染的语言判定**，断言又全是中文 marker。也就是说这条链路在 CI 里从来没有按用户真实路径跑过（本报告 §6 S8）。

### 验证建议

本机无法复现 macOS 的 bundle 语言解析，需在真机验证：

1. 在**系统语言为简体中文**且**从未设置过 App 内语言偏好**的 macOS 上装新包（旧 `~/.picoaide-harness` 里的 `locale.preference` 会掩盖问题，需先删或换新用户）；
2. 首启应直接中文（界面 + 托盘）；
3. 离线判据：`/Applications/PicoAide Harness.app/Contents/Resources/` 下应同时存在 `en.lproj` 与 `zh_CN.lproj`（当前只有前者）；
4. 反向用例：系统语言英文时首启仍应为英文。

## 1. 机制现状（先说好的部分）

### 1.1 已有字典的包，机制是正确的

五个包各自维护 `src/client/locales.ts`：

```ts
export const zh = { 'key': '文案' }                       // zh 是键源
export const en: Record<keyof typeof zh, string> = {...}  // 编译期强制键对齐
let activeLocale: 'zh' | 'en' = 'zh'
export function setActiveLocale(id: string): void {...}
export function t(key, params?): string {...}             // 渲染期取值 + {name} 插值
```

并在 client 入口跟随宿主语言：

```ts
ctx.effect(() => {
  const locale = ctx.locale as unknown as { getLocale?(): {active?: unknown}; subscribe?(fn): () => void }
  const sync = () => { const a = locale.getLocale?.()?.active; if (typeof a === 'string') setActiveLocale(a) }
  sync()
  return typeof locale.subscribe === 'function' ? locale.subscribe(sync) : () => {}
}, 'follow active locale')
```

**关键验证：运行时切换确实生效。** 上游 `ui-renderer/src/client/scoped-slots.tsx:280` 明确写着 *"Every outlet re-renders on a locale switch"*，`:707` 每个 outlet 订阅 locale revision。因此槽位里注册的组件会重渲染，模块级 `t()` 在渲染期重新取值 → 语言即时跟随。五个包的 `index.ts` 都做了 `subscribe`，**不是 apply 时读一次**。

`memory-evolve` 走的是另一条同样正确的路：`ctx.locale.bind(NS)` 在调用期解析语言。

## 10. 方法学备注

1. **grep 的行数 ≠ 字符串数。** 一个整页 HTML 是**一个**字符串字面量节点却含几十条文案：`shell-pages.ts` 85 条文案只占 2 个节点，`auth-gate.ts` 44 条只占 12 个节点。反之 grep 计数会把注释算进去（`loop-notify.ts` 9 处「中文」全是注释、`SkillsBrowser` 1005 个汉字零字面量）。**必须用 AST + 逐消费点判定。**
