## 一、界面里的报错现在真的会被采集（升级客户端才生效）

- **现象**：错误收集后台长期空着——最新一条停留在几个月前部署当天的**联调自测**记录，
  之后真实用户遇到的报错一条也没有。运维很难判断"是真的没出错"还是"根本没在收"。
- **原因**：客户端只采集了**主进程**的异常，而用户实际遇到的报错绝大多数发生在
  **界面渲染进程**（页面脚本异常、未处理的异步失败）——这一类**从来没有被采集过**，
  不是采集坏了。此外，登录流程本身出问题时不产生上报，而那恰恰是最有价值的错误。
- **修复**：新增渲染进程采集通道——页面主世界捕获未捕获异常与未处理的 Promise 失败，
  经受限通道交给主进程统一上报；界面进程崩溃（含内存不足被杀）同样上报并带上原因。
  采集通道**不把上报凭据交给页面**，也不允许页面直接发起网络请求；上报未启用时静默跳过，
  任何情况下都不会影响客户端其它功能。
- **自证**：一条真机门禁会真的起一个窗口、在页面主世界抛错，然后断言主进程确实收到了它
  （而不是只检查"文件存在"或"监听器已注册"）；端到端自动化里也新增了同样的断言。

## 二、"链路是好的" 现在可以被证明

- **现象**：即使采集完全正常，后台也可能一条都没有——因为默认只上报「错误」及以上级别，
  而客户端启动时那句"监控已启用"的自检属于提示级，被等级阈值挡掉了。
  于是**健康与彻底坏掉在后台长得一模一样**，没人能发现异常。
- **修复**：新增一个**独立的心跳开关**（默认关闭，不影响现有的等级设置语义）。
  打开后，客户端会在启动时发送一条带标记的心跳，可据此确认「配置下发 → 客户端 →
  收集服务」整条链路通畅。心跳**只影响带该标记的事件**，普通事件的等级过滤规则完全不变。
- **同批**：客户端会把自身的上报状态（已启用 / 已关闭 / 配置不可用 / 初始化失败及原因）
  回报给服务端，管理后台据此显示「N 个客户端已启用上报、M 个失败及原因」，
  不再需要逐台机器翻日志。

## 三、配置错误不再能被悄悄保存

- **现象**：管理后台可以保存一个**必然收不到数据**的上报地址（例如指向本机），
  并且提示"已保存"。客户端随后按这个地址上报，连接被拒，而管理员看不到任何异常。
- **修复**：
  - 服务端在写库前**校验上报地址**：指向本机 / 链路本地 / 云元数据地址的直接拒绝并给出中文原因；
    内网地址与非加密地址**只提示不阻断**（企业内网自建是合法场景）；
  - 管理后台在提交前做同样的校验，即时给中文报错，不发出无效请求；
  - 新增**「发送测试事件」**按钮：真的向当前配置的地址发一条测试事件，
    并区分为 DNS / 连接 / 加密握手 / 超时 / 服务端 4xx / 服务端 5xx 的可读原因。
    按钮与结果都明确标注这是**服务端视角**的探测——它能证明服务端到收集服务是通的，
    但不能替代客户端上报状态（见第二条）。

## 四、运维侧：自建错误收集服务的地址纠偏

- 自建收集服务在缺少站点地址配置时，会把对外展示的上报地址与事件链接生成为
  `localhost`，照抄这个地址配置客户端**必然失败**。
- 本版附一份自托管运维说明与一个**只读**核查脚本：一条命令即可判断后台展示的地址是否
  指向本机、以及容器是否缺少站点地址配置，并打印需要人工执行的修复命令（脚本本身不代改）。

## 五、回归防线

- 打包后的客户端新增可执行断言：错误上报所依赖的运行时组件必须能被**真正加载**
  （此前只断言文件存在，漏打也全绿）；
- 端到端自动化现在会真实激活上报链路并断言事件到达，且会真的在页面里抛一个错、
  断言它进入链路——把开关关掉或把监听装错位置都会立刻变红；
- 图形门禁在无法运行的环境下**明确失败**而不是静默跳过（跑不了就说跑不了，
  不允许"没验证却显示通过"）。

## 升级与回滚

- **客户端**：Windows / macOS 从管理后台或更新地址下载新版安装包；Linux 使用新的 AppImage。
  界面报错采集需要安装本版客户端后才生效。
- **服务端**：取本版镜像后按 `docs/deploy/AI-DEPLOY.md` 升级（**升级前必须备份**）。
  首次启动会自动执行一次数据库迁移（新增客户端上报状态表，不触碰既有数据）。
- **回滚**：镜像回退到上一个版本即可；新增的表在旧版本中不被读取，不需要回滚数据库。
  客户端回退到旧版只会失去界面报错采集，不会影响其它功能。
