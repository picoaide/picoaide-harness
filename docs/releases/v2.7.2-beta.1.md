# PicoAide Harness v2.7.2-beta.1（2026-09-12）

本版是**内测 beta**，含两处破坏性变更，请只在测试环境验证后再推广：

1. **上游 DSH 升级到 0.1.5-rc.2**（原 0.1.2-rc.1）：桌面端适配新的根布局，**退役
   自带 better-sidebar 插件**（右侧栏改由**官方右栏插件** `@deepseek-ai/dsh-client-ui-sidebar-right`
   占用 `rightbar` 槽；桌面端只自持 frame 几何与 `layout` 服务，官方 `ui-layout` 行被禁用）。
2. **服务端的「钱」只剩账户余额**：员工 token 配额、员工金额配额、部门预算**全部下线**，
   改为「账户余额（唯一闸门）+ 按月发放余额」两层模型。

旧客户端连新服务端、或新客户端连旧服务端都可能出现字段缺失，**服务端与客户端请一起升级**。

---

## 一、余额体系重构（服务端 + 管理端 + 客户端）

### 为什么改

原实现同时存在 4 套并行的额度机制（账户余额 / 员工金额配额 / token 配额 / 部门预算），
互相打架：手动给员工充了钱，仍会被"月度金额配额"拦住；余额在闸门关闭期间不记账、
没有流水，管理员无法对账。本版把它们收敛成**一种钱**。

### 新模型

- **账户余额**＝员工唯一可花的钱：存量、消费即扣、可逐笔对账；闸门开启且余额耗尽时，
  网关返回 429（错误码从笼统的 `QUOTA_EXCEEDED` 改为 `BALANCE_EXHAUSTED`）。
- **按月发放余额**：每月按配置额度自动发放（累加 / 覆盖），**与闸门开关解耦**
  ——可以先只发钱不拦人。
- **开通语义**：员工在**首次入账**（发放或人工充值）时才"开通余额账户"；
  未开通的人既不扣余额也不被闸门拦截。存量部署开启闸门**不会**误拦全员，
  关闭闸门期间的历史消费也不会凭空产生欠款。
- **流水账本**：每次余额变动（发放 / 覆盖清零 / 人工调整 / 消费 / 费用回补）都记一笔，
  管理端可查；账本合计恒等于当前余额（对账不变量）。
- **月末新员工**：发放幂等锚从"整月一次"改为"每人每月一次"，月中入职、停用后重新启用的
  员工会被自动补发，不再等到下个月。

### 管理端（webadmin）

- 用量中心「配额与预算」→ **「余额」**：一个页面完成发放策略（闸门 / 方式 / 每人额度 /
  立即补发 / 本月发放进度）、员工余额表、充值·扣减·设为·**清零**、以及**余额流水**查询。
- 用户管理页只保留余额列，行内「余额」按钮跳到余额页并自动打开该员工的调整窗口
  （**编辑入口唯一**，不再两处重复）。
- 部门管理、部门用量、成员用量、审计页同步去掉预算与配额相关列与标签。
- 用量总览的「渠道余额」更名**「上游账户余额」**，避免与员工余额混淆。

### 员工端（桌面客户端）

- 账户卡只展示**账户余额**；未开通余额账户时显示「余额未开通」，不再出现
  "显示 ¥0.00 却能正常调用"的矛盾界面。
- `/auth/usage` 的字段集合与客户端类型定义现在由**一处契约**（含运行时校验）保证一致，
  服务端测试会与客户端契约文件做键集合对拍，字段漂移不再可能静默通过。

### 迁移与兼容

- 迁移 `0062` 自动完成：新建流水表与逐人发放锚、回填存量余额为期初（账本合计 == 余额）、
  按当月发放批次补锚（**升级后不会重复发放当月额度**）、批次之后入职的新人由下一轮正常补发。
- `quota_tokens` / `quota_money` / `groups.budget_money` 等列与设置键**保留在库中**
  但不再读写，不做破坏性清理；需要彻底清理请另开迁移。
- **回滚注意**：回滚到 2.7.x 时旧代码不认识逐人发放锚，**回滚当日不要手动触发发放**，
  否则可能重复发放一次当月额度。

## 二、上游 DSH 0.1.5-rc.2 适配

- 依赖层从 `0.1.2-rc.1` 升到 `0.1.5-rc.2`；桌面端适配新的根布局与槽位装配规则。
- `better-sidebar` 退役：右侧栏改由**官方右栏插件** `@deepseek-ai/dsh-client-ui-sidebar-right`
  占用 `rightbar` 槽（不是桌面端自己渲染右栏）；桌面端只自持 frame 几何与 `layout` 服务，
  官方 `ui-layout` 行被禁用——子槽声明全局唯一，桌面 frame 与官方 frame 不能同时声明
  `sidebar`/`main`/`rightbar`，二次声明会直接抛错，这正是本版必须整包替换而非热更的原因。
- 真机探针与断言同步更新：会话"新建 → 重启"冒烟、右侧栏真机视觉探针、
  E2E 追加 `e2e:sidebar` 并采集右侧栏截图。

### 客户端数据面（会话格式 v0 → v3）：只前向，不要就地降级

本版客户端把本地会话格式从 v0 升到 v3。迁移是**副本式**的：打开旧会话只在内存里转换，
首次**可写打开**（= 恢复会话继续对话）才在同目录发布 `session.v3.jsonl.zstd`，
**源 v0 文件逐字节保留**，没有开关能控制它。

- **不要就地降级**（装回旧客户端）：rc1 只认 `session.jsonl[.zstd]` —— 本版期间新建的会话
  （只有 v3 世代）在旧客户端里**整体不可见**，被迁移过的会话则回退到旧的 v0 内容并**继续往 v0 追加**；
  再升回本版时只认最高世代 v3，于是**静默丢掉旧客户端期间追加的全部内容**。
- **回滚 = 停写 + 整目录恢复**：先完全退出客户端（含任何在跑的 dsh 进程），再用升级前的备份
  整体恢复 `<DSH_HOME>`（至少 `sessions/` 与 `storages/`），**不是**只换回旧安装包。
  注意投影缓存已是 **per-record 布局**（`storages/session_projcache/sessions/<id>.json`）：
  旧口径里的 `storages/session_projcache.json` 单文件是 rc1 遗留物，只恢复它等于丢掉全部投影缓存
  （会话本身仍在，代价是逐会话冷重建）。
- **预留磁盘 ≈4×**：迁移不改写源文件、也**不会**自动清理（上游没有 prune）。实测 v0 8.25 MiB → v3 33.45 MiB
  （≈4.0×）；上游对 116 MB v0 日志的自测标尺是 6.241s / 峰值 2.107 GB，首次恢复大会话会有可感知卡顿。
  本版不提供清理逻辑，回收空间只能人工确认后删除旧世代文件。

## 四、升级方式

服务端镜像（本版本）随 tag 发布；测试服务器升级见 `docs/deploy/AI-DEPLOY.md` §6。
