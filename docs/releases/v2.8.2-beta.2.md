# v2.8.2-beta.2（2026-09-28）

> **谁必须升级**：所有在用 2.8.1 / 2.8.2-beta.1 及更早版本的环境。
> 本版的主线是**上游 DSH 大版本升级**（`0.1.6-alpha.2` → `0.1.7-rc.2`），
> 外加第二十八至三十三轮审计的修复。
> **不升级的后果**：留在旧版本不会拿到上游 0.1.7 线的任何修复；
> 而**升级到本版之前必须先读 §一.1** —— 那一条会话格式变更会让"装回旧客户端"
> 不再是回滚手段，升级窗口的运维姿势要跟着改。

## 一、主线：上游 DSH 升级到 `0.1.7-rc.2`

固定点从 `dsh-v0.1.6-alpha.2`（`ddefc45fbc7f`）换到 **`dsh-v0.1.7-rc.2`（`477b4f4205`）**，
`upstream.json` 的 `sourceVersion` 与 `runtimePackageVersion` 均为 `0.1.7-rc.2`
（硬规则：submodule 的 tag 必须等于 npm 上真实发布的版本 —— 二者脱节会让"源码里有的能力"
与"实际装到的包"不是同一份）。

### 一.1 会话格式 `v3` → `v4`：升级前必读

这是本次升级**唯一需要提前告知使用者**的变更。实测结论（真跑，日志与判据见
`docs/AUDIT-2026-09-23-FULL.md` §8.9）：

| 问题 | 事实 |
|---|---|
| 什么时候会迁移 | **只有继续一个会话**（发消息 / 让 AI 接着干活）才迁移；列表、查看、搜索、导出都是只读，**不迁移** |
| 怎么迁移 | **副本式**：在同目录**新增** `session.v4.jsonl[.zstd]`，源 `session.v3.*` **逐字节不变**（前后 sha256 相同）；不改写、不删除、不留临时文件 |
| 磁盘代价 | 迁移过的会话在盘上**留两份**（实测 ≈2.01–2.14×）。**不是** 2026-09-12 那次 `v0→v3` 的 ≈4× |
| 旧客户端看到什么 | 该会话**从列表里静默消失**；强行打开会明确报"需要用新版 Harness 打开"。文件完好，旧端**永不追加**（跨进程文件租约会先把并发写拦成明确错误，不会分叉） |
| "装回旧客户端"算回滚吗 | **不算。** 旧端按"最高世代"挑选文件，不会回落到完好的 `v3` ⇒ 迁移过的会话在旧端一样打不开 |
| 正确的回滚 | **停写 + 整目录恢复 `DSH_HOME`**。备份口径是**整个数据根**（不是某一个文件） |
| 预留空间 | 第一次写打开是同步的（1.8 万事件实测 ≈950 ms）⇒ 预留与 `sessions/` 等量的可用空间 |
| 迁移可能被拒绝吗 | 会（源不动、不产生新世代，但**新客户端也打不开它**）。本版**没有**为这种情况提供处理通道（已认账，见 §五） |

**运维纪律**：预发布渠道与正式渠道共用同一个数据根。升级窗口内
**不要在同一台机器上交替使用两代客户端**，也不要让同一个会话被两代同时打开。

### 一.2 模型链路：网关认证重写

- 上游**删除了** `llm-deepseek.protocol`（配了会直接报错），模型请求路径固定为
  `<baseURL>/messages`。0.1.6 线那条"组装期钉 `protocol: chat-completions`"的逃生门
  **整段失效**（留着无害：那条行已被禁用，不会再被解析）。
- 我们的网关只认 `Authorization: Bearer`。本版新增自研行
  `@picoaide/dsh-enterprise/gateway-llm`，用 Bearer `resolveAuth` **每请求**解析令牌；
  取不到令牌时**直接抛错、一个请求都不发**。
- **设置命名空间 `llm-deepseek` → `picoaide-gateway-llm`**；`apiKeyEnv` 不再是 chat 链路的配置面。
- 排障三档（互不混淆）：`缺少认证令牌` = 请求没有 `Authorization` 头；
  `令牌无效或已过期` = 登录态；`缺少本地凭据` = 凭据解析不到。
- **另一档**：`ENDPOINT_MISMATCH` —— 端点不是当前会话的那台服务器。它**不在**上游的可重试
  错误集合里 ⇒ 在「会话尚未就绪」的窗口里，模型请求会**明确失败且不自动重试**，而不是像
  以前那样「带着令牌发给一个不确定的端点」。这是有意的取舍（宁可失败，也不把企业网关令牌
  发到别的地址）；登录完成后再请求即正常。

### 一.3 一处**用户可感**的上游默认值换代（发布说明初版漏报，此处补上）

上游 base bundle 的 `spill-policy` 把溢写阈值从**字节**改成了**token**
（`maxInlineBytes: 50000` → `maxInlineTokens: 12500`），schema 已只认新键。
我们的 profile **没有覆写这一行**（零引用）⇒ 桌面直接采用上游新默认。
**用户可感的后果**：长工具结果「何时落盘 / 何时内联」的时机变了。
两者不等价，等价性未做测量；**如果你的流程依赖旧阈值，请在 profile 里显式覆写。**
（本条由升级后的独立证伪泳道发现：**发布说明漏报本身就是缺陷**，已按此更正。）

### 一.4 设置模型换代

`@deepseek-ai/dsh-settings-file` 被并入 `@deepseek-ai/dsh-settings`：不再有
`ctx.settings.register/get/watch`，**命名空间就是一个 profile 条目 id**。
旧数据根里的 `settings.yaml` 由上游**只导入一次**、随后改名；桌面的启动设置
（模式/端口）改为从组合后的 `desktop-shell` 行读取，`settings.yaml` 只作一次性回落。
⇒ 运维不要在 `settings.yaml` 里继续手写配置，改走设置界面或 profile 补丁。

### 一.5 补丁面：8 个补丁全部重切并逐个重验

0.1.7 里多处目标文件是**带哈希名的构建产物**，所以每次升级都必须重切补丁，
并逐个证明"打得上 **且** 运行期真的有效"。本版 8 个补丁：

| 补丁 | 作用（不生效会怎样） |
|---|---|
| `dsh-subprocess-local@0.1.7-rc.2` | Electron 宿主下给 runner 自己的环境注入 `ELECTRON_RUN_AS_NODE=1`（目标 `lib/runner-launch-B2zsQ1Dz.js`）。不生效 ⇒ Windows / Linux 上**本地命令执行整条失效** |
| `dsh-client-ui-brand-official@0.1.7-rc.2` | 取消上游"官方品牌位"的注册，让渠道白标注入生效 |
| `dsh-client-ui-sidebar-documentpreview@0.1.7-rc.2` | 去掉 Office 转 PDF 那一支（桌面宿主没有 LibreOffice），保留纯客户端的 xlsx 预览 |
| `dsh-mcp-client@0.1.7-rc.2` | 把 `authProvider` 透传进 `StreamableHTTPClientTransport`。**不生效 ⇒ 连接器的令牌续期链路断**（这是承重的那一半，已用记录型 SDK 影子做运行期正反双向对照）。本补丁另外在 Config schema 里补了一行声明：**在 0.1.7-rc.2 上它是冗余的**（实测该版本不会剥掉未声明字段），保留它是为了对上游后续版本更保守。初版发布说明写「两处缺一不可：Schemastery 会剥掉未声明字段」——**那个理由在本 pin 上不成立**，特此更正 |
| `dsh-plugin-package-inventory-deepseek@0.1.7-rc.2` | 单条解析不了的包条目不能作废整个回合 |
| `dsh-sandbox-windows-acl@0.1.7-rc.2` | `SetNamedSecurityInfoW` 失败且 Win32 码 = 5 时给出可操作提示（目标 `lib/types-DxezulnA.js`）。那是工作区所有权 / `WRITE_DAC` 问题，不是偶发 |
| `dsh-web-fetch-http@0.1.7-rc.2` | 地址策略整体放行（见下） |
| `app-builder-lib@26.15.3` | macOS 签名时把 `keychainPassword` 传给 `importCerts` |

**已被上游吸收而删除的补丁**：0.1.6 线的 `dsh-agent-presets` 补丁 —— 0.1.7 把该包拆成
`@deepseek-ai/dsh-agent-preset` + `@deepseek-ai/dsh-agent-preset-registry`，原来的补丁
不再需要。

**⚠️ `web_fetch` 的安全代价（本版唯一一条已知取舍，请知悉）**：
`dsh-web-fetch-http` 的地址策略被整体放行（`ADDRESS_POLICY_ALLOWS_ALL = true`）。
原因是**部署环境用了透明代理的假 IP 模式**（任何域名都解析到 `198.18.0.0/15`），
上游基于 `ipaddr.js` 的公网判定会把**每一个** URL 都判成"非公网地址"⇒ 工具完全不可用。
放行之后**客户端 `web_fetch` 不再做地址层防护**；代理路由、DNS 固定、协议白名单等
其余约束不变。只有经代理才能出公网的部署不受影响，但**内网可达性不再被这一层拦住** ——
需要该防护的环境请单独评估。

### 一.6 客户端组合面

0.1.7 起上游把包解析改成**进程内拦截**（`PluginPackages` + `createRuntimeResolution`），
不装它连一条 bare specifier 都解析不了。本版把它接到桌面宿主，并修好一处升级引入的
**组合面缺陷**：覆盖层补丁（桌面 / 企业 / 各业务插件的 `cordis.patch.yml`）此前只出现在
组合结果里、**没有并入真正被挂载的那棵树** ⇒ 桌面外壳与自研行整片没挂上。
现在这条由能力判据兜底：必需行**必须真的在树上且处于 ACTIVE**，不在就红。

### 一.7 客户端引擎（Electron）pin：`44.4.3` → **`45.0.0-alpha.7`**

这不是"顺手升引擎"，是**被上面那两条硬约束夹出来的唯一解**：

- 0.1.7 的包解析改用原生插件（`node-addon-require-builtin`）去够 Node 内部 loader，
  而这个插件的原生二进制里**硬编码了三个精确的 Electron 指纹**，按 V8 补丁号精确匹配。
  我们原来的 `44.4.3`（V8 `15.2.124.28`）**不在表里** ⇒ 打包版**启动即失败**
  （`host preparation failed: … unsupported Electron runtime fingerprint`）。
- 表里 44 线唯一的受支持版本是 `44.0.0`（V8 `15.2.124.13`），但 `44.0.0`
  **没有** v2.8.1 修的那个 ASAR `bigint` 修复（`dsh-skill-filesystem` 在 asar 根上拿到
  Number 版 Stats ⇒ 整个文件系统技能 provider 被跳过）⇒ 被我们自己的 afterPack 门禁拒包。
- `45.0.0-alpha.7`（V8 `15.4.80`）**两条都满足**：asar 冒烟通过、打包版真机启动并
  通过 41/41 图形 E2E。

**认账**：这是 Electron 的 **alpha 通道**。选它是"唯一同时满足两条约束"的结果，
不是版本偏好；上游的支持表把 45-alpha 显式列为受支持运行时。
**如果贵方有"引擎必须用稳定版"的硬性合规要求，请先不要升级到本版** ——
那需要另行解决（自建该原生插件 / 去掉 ASAR），代价更大，不在本版范围。
升级引擎后必须重跑：`yarn package:dir`（asar 冒烟）+ 打包版启动 + `e2e:client`；
只跑单元门禁会放过这一类（本次就是被真机 E2E 抓到的）。

## 二、第二十八至三十三轮审计修复（用户可见的部分）

- **判据面的"取值域"同族缺陷（第 9 次复发）**：多条守卫的判据面窄于它声称守护的面
  （等锁预算只锁了一张表、仓库级"读失败回写"扫描有 5 种写法能逃逸、
  `hasPermission` 的行内字面量、dex 腿把相对 `Location` 当深链）。
  逐条收窄为"判据的取值域 = 被守护面"，并补正控与变异。
- **真机/集成面**：`integration-tests` 的 dex 腿在正确环境里此前**结构上不可能 PASS**
  （真 IdP 用 302 + 相对 `Location`），修 `urljoin` 后由红转绿；`electron-shots` 的
  "非空但错"观测补齐判据。
- **会话级开关的读失败**：`session-overrides.json`、通知存储、advisord 等**同族**读失败
  一律改为 **fail-closed**（此前一次瞬时 `EACCES` 会静默清空全部会话级开关、
  或抹掉其它会话的通知）。
- **服务端**：迁移启动期的 `ALTER … ADD COLUMN IF NOT EXISTS` 不再跑在池连接上、
  且在等锁预算**之内**；不可逆长期汇总与月报重推回归；`embeddings` 零计费。
- **门禁自身**：登记表收敛到不动点、新增判据执行体/执行点登记、
  渠道包判据与 401 假绿收口、本地 CI 对等清单。
- **迁移内容不可变（本版新增）**：新增 `migrations-checksums.json` 登记表 + 守卫
  （已登记文件被改写 / 新增未登记 / 死条目 / 非法登记表全红），并以**已发布基线 tag**
  为不可变基准（取不到远端校验时**响亮降级**）。它与 §三 的迁移清单锚点是两件事：
  锚点管"本版引入了哪几条迁移"，本表管"已登记的迁移字节不许被人就地改写"。

## 三、升级须知

- **数据库**：本版新增一条**只加列**迁移 `0082_report_subscription_retry.sql`（`report_subscriptions` 的
  `pending_period` / `fail_streak` / `next_attempt_at` 三列，全部带缺省值 ⇒ 不回填、不改写既有数据，
  存量行语义逐字不变）。⇒ **回滚比平时多一步**，见下一条。
- **回滚（口径唯一真源 = `docs/deploy/AI-DEPLOY.md` §7；本节不给第二套处方）**：本版引入了迁移
  `0082`，所以回退到**不含 `0082`** 的版本属**跨代回滚**（库比二进制新）⇒ 按该文档 §7.1 → §7.2 的
  **四步顺序**执行：**① 停服（`docker compose stop server`）→ ② 恢复升级前的 `pg_dump`
  （§6.3 的 `deploy-backup/pg-data-<TS>.dump`）→ ③ 回退镜像（`SERVER_IMAGE` 改回上一版 tag）→
  ④ 客户端回退到与镜像同版本**。**不要只改 `SERVER_IMAGE` 就重启** —— 那是 §7.1 对跨代回滚的
  硬要求。为什么：**本版起**服务端对"库比二进制新"是 **fail-loud** 的（双向对账：`schema_migrations`
  里有二进制不认识的版本号就抛 `SchemaMismatchError`，`cmd/server` 直接 `log.Fatalf`，报
  `schema 与二进制不同代`），带着 `82` 这一行启动**这类二进制**会直接拒绝启动。
- **迁移文件 `0082` 的头部另记了一条更轻的路径**（只删版本登记行、**不**恢复库）：`0082` 属 §7.1 的
  "一般迁移（只加列 / 只建表）"一类 —— 它只加三列且都带缺省值，旧二进制不读它们，所以数据层不需要
  恢复库。是否采用这条、以及它与四步的取舍**以 §7.1 为准**（不可逆迁移必须走四步）。要采用时，
  连接上下文用**你自己部署里的实际取值**（下面是占位符，别照抄）：
  ```bash
  docker exec -i <pg-container> psql -U <db-user> -d <db-name> \
    -c 'DELETE FROM schema_migrations WHERE version = 82;'
  ```
  该步只删版本登记行，**DDL 与三列都留着**（旧代码不读它们 ⇒ 安全）；此后仍需换回旧镜像
  （`SERVER_IMAGE` 改回 + `docker compose up -d server`）。需要彻底清理时再执行
  `ALTER TABLE report_subscriptions DROP COLUMN pending_period, DROP COLUMN fail_streak, DROP COLUMN next_attempt_at;`。
  前滚把那一行写回即可（`INSERT INTO schema_migrations (version) VALUES (82) ON CONFLICT DO NOTHING`；
  DDL 是幂等的 `ADD COLUMN IF NOT EXISTS` 形态）。
- **迁移清单（机器可读锚点，供 `scripts/check-release-notes-migrations.mjs` 与 `git diff` 对拍）**：`0082_report_subscription_retry.sql`
- **客户端与服务端同代**：预发布 tag **只构建 beta 渠道**；品牌渠道要等正式 tag
  或 `workflow_dispatch`。
- **升级前**：备份**整个数据根**（`~/.picoaide-harness`，或你的渠道数据根），
  并预留与 `sessions/` 等量的可用空间（见 §一.1）。
- **升级后**：不要用"装回旧客户端"当回滚；回滚 = 停写 + 整目录恢复数据根。
- **连接器**：本版改了 MCP 客户端的鉴权透传（补丁 4）。已授权过的连接器**应当
  照常工作**；如果某个连接器在升级后要求重新授权，那是它自己的令牌确实过期，
  重新授权一次即可。

  本节把这三条并列为必跑项，而不是"单元绿即可"。

## 五、本版验证边界与仍未闭环

- **真机平台面**：Windows 的沙箱 ACL 提示、macOS 的签名/公证链路需要真实平台才能复验，
  本轮只在 CI 上跑到构建与结构判据。
- **会话迁移被拒绝**的情况没有处理通道（§一.1 最后一行）。
- **企业「共享智能体 preset」安装链路**：0.1.7 起上游不再读取
  `$DSH_HOME/.agent-presets/<id>/`，本版按上游文档的等价语义把这层读取收回自己手里
  （组合期物化），已带真 Cordis 端到端判据。
- **创造模式里的插件管理现在能改到本产品自己的行**（本版修复的直接代价，特此声明）：
  §一.6 那处修复让桌面外壳与自研行回到运行树上，而"行能被插件管理改"与"行在组合复算里
  可见"在上游是同一个事实 —— 两者只能选一个。**后果**：在创造模式里可以让 AI
  禁用这些行，其中 19 条是必需行，禁用后**下次启动会响亮失败并点名是哪几行**
  （不是静默少功能）。**恢复**：删掉数据根 `profiles/<name>/cordis.patch.yml` 里对应
  的 `disabled` 项（或整份删掉，设置回到默认）。缓解方案需要上游提供"受保护模块"注入点，
  已登记、本版未做。
- **网关地址目前只允许"当前会话的那台服务器"**：本版给模型链路加了端点硬边界
  （不允许把网关令牌发到别的地址，见 §一.2）。**当前所有部署都不受影响**
  （渠道内置的服务端地址天然就是它），但"网关部署在另一个域名下"这种形态本版没有入口，
  需要按台账 §8.9.6 第 4 条给的改法新增一个只能由组装期/渠道注入的配置项。
- 审计收敛判据**未达成**：从第一轮到第三十二轮，每一轮都至少掉出一条 P1；
  完整台账、方法论与接手清单见 `docs/AUDIT-2026-09-23-FULL.md` §八。

## 六、第十至二十七轮审计的行为变更登记（升级与运维视角）

> **本节是什么**：以下六个小节登记**第十至二十七轮审计**里"升级后你会看到什么"的变更。
> 它们此前写在 `docs/releases/v2.8.2-beta.1.md`，但那些轮次的改动**不在 beta.1 内**
> （`v2.8.2-beta.1` 的 tag 里没有这些改动）⇒ 属发布说明的归属错位，现按轮次搬回本版。
> 口径与 beta.1 发布说明里的同类小节一致：**只写"你会看到什么"**，不重复修复清单。

### 六.1 第十轮的行为变更登记（客户端）

第十轮（客户端与宿主面）又收口了一批连接器出站头与技能打包的边界。其中五条会让**升级后你看到
的行为发生变化**（第九轮的四条登记见 `v2.8.2-beta.1` §七；本小节只写"你会看到什么"）。

**1) 只写了方案词的 `Authorization` 不再当凭据发出去**

- **谁会受影响**：连接器定义里把 `Authorization` 声明成**裸方案词**（`Bearer` / `Token` / `Basic` /
  `ApiKey` / `JWT` / `SSWS` 等）的环境 —— 这类声明没有携带任何凭据，以前会被原样发到 MCP 端点。
- **观察到什么**：该槽位不再按"声明的凭据"发送——有 provider（OAuth/令牌）时由框架填 `Bearer <活令牌>`；
  **凭据里没有访问令牌**（只配了静态字段）时，这条头**整条被删除**（不再发出 `Authorization: Bearer`）。
  真正的凭据照旧**逐字**上线：`abc123`、`sk-…`、`Token abc123`、`ApiKey ${K}` 都不受影响。
- **要不要动作**：如果某个端点在靠"能收到一个 `Authorization` 头"来判活（而不是判令牌），请改为
  按连接器的连接状态判断。配错字段名（声明了 `${API_KEY}` 而凭据里没有该字段）现在也是同一结果：
  该头被删，并在连接器面板留一条可检索的 warn。

**2) 同一个 HTTP 头的两种大小写拼写只发一条**

- **谁会受影响**：定义里用不同大小写写了同一个头（例如框架注入 `Authorization: Bearer …`，
  定义又声明了 `authorization: ''`）的环境。
- **观察到什么**：头名按 HTTP 语义归一成**一个槽位**，线上只会出现**一条**该头（此前可能出现两条、
  或被合并成 `A, Bearer …` 这种两端都解析不了的值）。大小写不同的**不同**头（`X-Probe` 与
  `X-Probe-Key`）不受影响，仍是两条。
- **要不要动作**：不需要，除非你的端点在依赖"重复头"这一（不规范）事实。

**3) 声明的 `__proto__` 头由"静默消失"变成"显式拒收 + 可检索 warn"**

- **谁会受影响**：定义里恰好声明了名为 `__proto__` 的头（历史上它会被 JavaScript 赋值语义吞掉，
  既发不出去也没有任何提示）。
- **观察到什么**：注册期多一条可检索的 warn（`[unsupported-header] … 声明的头 __proto__ 无法表示，
  已拒绝发送`）；连接器本身照常可用，其余头照常发送。名字形如 `constructor` / `toString` 的头是
  **普通头**，正常发送、也会随凭据更新正常过期。
- **要不要动作**：不需要。看到这条 warn 说明该声明从来就没生效过。

**4) 技能目录是符号链接时，上传被拒收（此前会被打包）**

- **谁会受影响**：技能库里用 `ln -s` 指向别处的"技能"（包括指向**库内另一个真技能**的别名）。
- **观察到什么**：打包（上传到能力中心）现在 fail-loud，文案点名符号链接；技能库**根目录本身**是符号
  链接的部署（合法的挂载/家目录布局）不受影响，照常打包。技能列表本来就不列符号链接条目，所以失去的
  只是一个从未在界面上出现过的上传路径。
- **要不要动作**：把别名换成真实目录（复制或改技能库根指向）。**认账残量**：技能目录内的**硬链接**
  与普通文件在路径上不可区分，打包期的落点断言管不到它（需要本机写权限才能造出，且 `realpath` 结构性
  修不了）；`nlink > 1` 的逐文件拒收会误伤正常部署，本版不做。

**5) 连接器重建前"在途等待"的记账作用域：从"按端点"收到"按正在被换掉的那条传输"**

- **谁会受影响**：同一个 MCP 端点上有**不止一条**传输的环境（同一连接器的多个 server，或多个连接器
  指向同一端点）且会轮换凭据。
- **观察到什么**：一条传输重建时**不再**把同端点其它传输的在途记账一起清掉（此前会让另一条传输的
  下一次重建误判"没有在途调用"而提前掐断它本可在等待窗口内结算完的调用）。代价是：当端点上确实还
  有其它传输时，重建**不会**因为"等待超时"而丢弃记账，于是那次等待会在后续重建里再发生一次，直到
  在途调用结算或到达 120 秒（MCP 调用的工具预算）为止 —— 宁可多等一轮，也不误伤别人正在返回的调用。
- **要不要动作**：不需要。单传输（绝大多数部署）行为不变。

### 六.2 第十一轮的行为变更登记（服务端读数 · 客户端 · 门禁）

第十一轮是"把判据面推进到**执行体的入口**（谁把门禁跑起来）"的一轮。其中六条会让升级后
（或本地开发时）你看到的行为/读数发生变化；口径与上一小节一致：**只写"你会看到什么"**。

**1) `/readyz.usage_retention` 新增三位，"停摆"从一位变两位**

- **谁会受影响**：把 `usage_retention` 接到监控/告警上的环境 —— 尤其是"保留策略是不是停摆了"
  那条规则，以及在**重启比一天一次更频繁**的部署上设计过告警时间线的环境。
- **观察到什么**：对象里多出三个字段 —— `reclaim_stalled`（布尔）与它的一对推导基准/读数
  `oldest_unreclaimed_due_since`（最早那个未回收的到期月**从哪一刻起就该被回收**）、
  `oldest_unreclaimed_age_seconds`（到本轮结束为止已逾期多少秒）。
  `reclaim_stalled=true` 的判据是"最早未回收的到期月已经逾期 ≥24 小时"，它由 catalog 事实 +
  保留期**推导**（纯函数）⇒ **重启后的第一轮就有值**。既有的 `deferred_stalled` 语义**不变**
  （"同一关系连续 ≥5 个调度轮次、约 24h，既没回收也没真失败"），它仍依赖进程内累积、重启归零。
  两位**故意不合并**：既有的"管理端连点保存保留期不得造成分钟级假告警"契约原样有效。
  运维口径因此是 `deferred_stalled || reclaim_stalled`。
- **要不要动作**：把"停摆"告警条件改成 `deferred_stalled == true || reclaim_stalled == true`；
  要"逾期多久"就直接读 `oldest_unreclaimed_age_seconds`。三个字段都是**增量**，其余字段名、
  出现条件与当月写入面的语义一字未改；它们在 `false`/`0`/空时**不出现**（JSON 省略零值），
  所以规则要按"缺省即 false"写（`!= true`，别写成 `== false` 的严格比较）。

**2) `write_blocked_other_months` 从"单向棘轮"变成"当前仍未解决"的读数**

- **谁会受影响**：用 `/readyz` 判"有没有某个月写不进去"的监控（尤其"新出现即告警、一直不消失就升级"）。
- **观察到什么**：非当月写入面的条目现在会**自己消失**，两条收敛判据：①该月**后来写成功**了；
  ②该月的关系**已不在本轮的 catalog 枚举里**（已被回收/删除，写入阻塞这件事没有载体了）。
  此前只有 ①，而被布局阻塞的恰恰是**到期月** —— 写路径只写当月，所以那些条目**永久残留**，
  "列表非空 ⇒ 有月份写不进去"变成一次历史事件之后永远为真（最多靠 12 个月滚动自然淘汰），
  "新出现即告警"因此失效。关系仍在的条目**一律保留**（那才是"现在还有个月写不进去"的真实读数）。
- **要不要动作**：不需要。`write_blocked_other_count`（累计次数）不受影响，趋势/复盘用它。
  当月面 `write_blocked_*`（"当月每一次对话 503"）的语义与告警口径**不因它改变**。
  附一条边界：这类收敛只在"**有证据轮**"（本轮真的枚举到过 catalog）执行，扫描失败的轮次
  不做任何猜测。

**3) `NODE_OPTIONS` 由"按名字拒跑"改成"按内容拒跑"（门禁与本地开发）**

- **谁会受影响**：在本地或 CI 里给门禁设过 `NODE_OPTIONS` 的人。
- **观察到什么**：只有**登记在案**的纯 GC/打印面旗标（`--max-old-space-size=…`、
  `--max-semi-space-size=…`、`--max-http-header-size=…`、`--stack-size=…`、
  `--stack-trace-limit=…`、`--heapsnapshot-near-heap-limit=…`、`--v8-pool-size=…`、
  `--no-warnings`、`--enable-source-maps`、`--trace-warnings`、`--disable-warning=<码>`）
  会被放行并**原样传给每个包**的构建/测试进程；任何一个未登记的旗标（`--import`、`--require`、
  `--loader`、拼错的名字、含引号/空格而被切碎的取值）都会让编排器**拒绝运行**：打印
  "拒绝运行 —— 本进程自己的环境里有…"并随后结束，**不打印通过凭据**（CI 侧以那一行为准，
  不以退出码为准）。此前判据落在**键名**上：`NODE_OPTIONS` 只要非空就算危险，于是
  "给门禁加堆内存"这种正当用法也直接红 —— 而危险形态与正当形态在同一个键里，判据必须落在旗标上。
- **要不要动作**：`NODE_OPTIONS=--max-old-space-size=4096 corepack yarn check` 照常可用；
  看到"拒绝运行"就清掉那个未登记的旗标（例如 `env -u NODE_OPTIONS corepack yarn check`），
  不要去放宽判据。

**4) `.yarnrc.yml` 与安装期钩子进登记制（开发流程）**

- **谁会受影响**：往 yarn 里塞插件/换 yarn 本体、或往根 `package.json` 加安装期钩子的人。
- **观察到什么**：`.yarnrc.yml` 现在**被门禁读内容**（顶级键白名单 + `enableScripts`/`nodeLinker`
  取值判据 + 内容摘要登记）；`yarnPath` 与 `plugins` **出现即红**；根 `package.json` 的
  `preinstall`/`install`/`postinstall`/`prepare`/`prepublish`/`prepublishOnly`/`prepack`/`postpack`
  进登记制（当前登记为空 = 禁新增）；`.yarn/plugins/**` 与 `.yarn/releases/**` 必须为空。
  为什么连"能不能加个插件"都要管：这类入口在 **yarn 进程内部**往每个被 spawn 的脚本环境写
  `NODE_OPTIONS`/`BASH_ENV`，注入发生在根守卫的环境清洗**之后** —— 实测在 workflow 一字未改的
  前提下，`corepack yarn check` 可以从 EXIT=1 变成 EXIT=0、根守卫从"3 通过/14 失败"变成
  "17 通过/0 失败"。守卫本身也不再经 yarn 启动（CI 直接 `node scripts/check-root-guards.mjs`）。
- **要不要动作**：不要往仓内加 yarn 插件或换 yarn 本体；安装期钩子确有需要时先按登记制登记
  （登记表与理由都在 `scripts/check-guard-parser-integrity.mjs`）。本地**未提交**地改这些入口文件时，
  "摘要锚到 HEAD"的那条只在 CI 上硬判、本地只是告警（认账的代价：本地脏树与攻击态在判据的输入面
  上不可区分），所以提交前请把工作树清干净。

**5) 客户端：连接建立期落地的令牌刷新，现在也会写到"传输真正读的那条记录"**

- **谁会受影响**：用 HTTP/SSE 传输的 MCP 连接器 —— 尤其是"打开客户端 / 重连时正好赶上令牌临期，
  后台心跳或连接器面板刷新落在**连接建立过程中**"的场景（开机恢复就是最常见的那一次注册）。
- **观察到什么**：那一刻落地的刷新以前会被吞掉 —— 传输带着**已被替换的**旧令牌上线，注册以
  `重新认证后仍然 401` 收场，而连接器面板的行状态**可能仍显示已连接**（用户看到的是"连上了但
  工具调用全 401 / 需要重新授权"）。现在刷新会写到这条注册**真正读取**的那条记录上；同一份记录
  在 `already in use`（上一世代实例占着名字）重试路径上也会被重新发布。
- **要不要动作**：不需要。这是客户端侧的行为修复，无需改配置。升级后仍遇到 401 时按本版升级说明的排障三档
  区分：`缺少认证令牌` = 请求没带 `Authorization` 头；`令牌无效或已过期` = 登录态本身失效。

**6) 门禁的"通过凭据"口径：只看那一行，退出码不再是凭据；失败行按 `\r` 分段**

- **谁会受影响**：读 CI / 本地门禁日志判断"到底过没过、失败在哪"的人，以及写脚本 grep 这些日志的人。
- **观察到什么**：① 判定权上移到父进程/CI —— **不看退出码、只认行首锚定的通过凭据**
  （`check-workspaces: VERDICT PASS planned=<N> executed=<N>`、`check-root-guards: VERDICT PASS
  guards=<N>`；N ≥ 1）：被拒绝运行、零守卫、以及"判决不可信"的进程都**打印不出**这一行，
  而它们照样能退出 0。② 失败行按 `\r`（光标回第 0 列）**切段**后逐段判定，所以用进度条
  `\r` 覆盖输出的构建/测试工具再也藏不住失败行。③ 判定形态表（`VERDICT_LINE`）从"行内任意
  位置匹配"改成行首锚定，并要求把形态**登记**进去（表被掏空或出现未登记形态即 fail-loud，
  提示是"补登记形态"而不是"放宽匹配"）。
- **要不要动作**：如果你的工具按"一行一条失败信息"解析这些日志，改成先按 `\r` 分段、每段各自
  从第 0 列开始匹配；判断门禁是否通过时请检查那一行凭据（行首锚定），不要只看退出码。

### 六.3 第十二至十八轮的行为变更登记（服务端 · 客户端 · 门禁）

口径同前：**只写"你会看到什么"**。本小节补齐**第十二至十八轮**——那七轮里有三条**客户可见**的
行为变更此前从未登记。

**1) 未定价模型：从"按 0 计费"改成"缺省拒绝调用"（客户可见，本版最重要的一条）**

- **谁会受影响**：模型目录里存在**未配置价格**（或价格 0）的模型的部署 —— 常见成因是渠道同步建出的
  NULL 价行，或管理员新增模型后忘了填价。
- **观察到什么**：这类模型的请求在缺省策略下返回 `429 MODEL_NOT_PRICED`，**不转发、不产生费用记录**；
  此前它们"照常调用、费用按 0 记"（组织付上游的钱、平台零计费零痕迹）。
  另有两条同族判据：**输入价 0/极低但输出价正常**的模型**照常可用**（按输出侧计费，本版修正了上一轮
  把它们一律拒绝的回归）；**这次请求的最小应付额折到账本最小单位（1 微元）仍为 0** 的请求同样被拒
  （否则结算落 0 微元、余额一分不减、可无限重复）。
- **要不要动作**：给真实计费的模型补价；确实是免费/内部模型时，由管理员显式把
  `gateway.unpriced_model_policy` 设为 `allow`。⚠️ 该开关是**全局**的：同名模型挂在多个上游渠道、
  其中只有一家缺价时，会让落到那家的请求也按 0 计费 —— 更稳的做法是给缺价渠道补价或停用它。

**2) 删除已安装的能力内容：跨根同名 ⇒ `422 RESIDUE`，本地有改动 ⇒ `409 LOCAL_CONTENT`**

- **谁会受影响**：在客户端卸载技能/智能体的员工 —— 尤其是技能库里存在**项目级/用户级同名副本**，
  或本地内容被自己改过的环境。
- **观察到什么**：卸载不再无条件成功。同名内容还存在于更高优先级的技能根 ⇒ `422 RESIDUE`
  （如实列出条目名与所在根，需先处理那一份）；本地内容与安装时不一致 ⇒ `409 LOCAL_CONTENT`
  （需要确认覆盖 `?overwrite=1` 才删）。客户端会如实显示服务端 message，不谎报成功。
- **要不要动作**：按提示处理更高优先级的那份副本；确认要丢弃本地改动时再点覆盖。

**3) 网关文件删除与批量清理：新增两条 `409` 与 `skipped` 计数（管理面/开放面）**

- **谁会受影响**：调用 `DELETE /files/:file_id`、`DELETE /api/server/admin/gateway/files/:file_id`
  或 `POST …/gateway/files/purge` 的集成方与管理端。
- **观察到什么**：删除**必然先取得认领**（回收器/另一个删除者持有租约时不再"照样删上游对象"）：
  租约内 ⇒ `409 FILE_BUSY`（对象与行原样保留，刷新后重试）；删除窗口内该行被重新登记 ⇒
  `409 FILE_RECLAIMED`（上游对象已删，台账行留给新的上传者）。批量清理的响应新增
  `skipped`（有意不删的条数：持有权冲突 / **快照之后被续期或转手** / 行已被别的路径收敛），
  且快照现在**带世代号** —— 清理循环期间被主人合法续期的**有效文件不再被误删**。
- **要不要动作**：按 `409` 的语义重试（`FILE_BUSY` 可稍后重试；`FILE_RECLAIMED` 不要重试）；
  解析 purge 响应时把 `skipped` 与 `failed` 分开统计。

**4) 月报订阅的重试节奏与跨月口径（管理面读数）**

- **谁会受影响**：配置了月报 webhook 且推送会失败的环境。
- **观察到什么**：失败后不再"每小时重投同一期，直到成功"（那会让永久坏的 webhook 每天被重投
  24 次/实例）。现在是**首次失败后 1 小时重试一次、之后每天一轮**；失败的那一期被**记住**
  （`pending_period`），**跨月也继续补投它**（此前会静默跳到最新一期，被跨过的那期永不投递）。
  多实例部署下同一期只投一次（投递前按订阅取数据库认领）。
- **要不要动作**：不需要。若你的告警依赖"每小时必然有一次重试"的节奏，按新节奏调整。

**5) 可信反向代理的缺省值：从"硬编码 Caddy 地址"改成"从 `CADDY_IP` 派生"**

- **谁会受影响**：改过 compose 私有网段（`NETWORK_SUBNET` / `CADDY_IP`）的部署 ——
  尤其是只改了 `CADDY_IP` 却没同步 `PICOAI_TRUSTED_PROXIES` 的环境。
- **观察到什么**：启动日志新增一行 `trusted proxies: source=… list=…`；未显式配置
  `PICOAI_TRUSTED_PROXIES` 时它**从 `CADDY_IP` 派生**（改网段只需改一处）。显式配置与
  `CADDY_IP` 不一致时，启动期多一行 `WARNING`（改网段只改一个 = `X-Forwarded-For` 静默失效、
  登录/MFA/OIDC 限流桶坍缩成全组织共桶）。
- **要不要动作**：若你曾显式把 `PICOAI_TRUSTED_PROXIES` 写成固定 IP 且随后改过网段，请核对那一行
  （共享反代部署 —— 宿主机另有 Caddy/nginx —— 的显式值保持原样即可）。

**6) 后台循环的可观测面：模型同步与 LDAP 目录同步进状态表**

- **谁会受影响**：把启动/关停日志或调度器状态接到监控的运维。
- **观察到什么**：启动与关停的 `scheduler status` 行新增 `model_sync` 与 `directory_sync` 两项
  （此前它们既不在状态表里，也没有 ctx/停止信号）；两者都随进程 ctx 退出，关停日志给出
  `runs`/`errors`/`last_error`。
- **要不要动作**：不需要。

**7) 运维面：`input price 0 + output price > 0` 的模型不再被误拒；`allow` 策略的语义与作用范围**

- 同本小节第 1 条的"要不要动作"，此处只是再次强调：**`allow` 是全局逃生门**，不是"按模型白名单"。
  需要按模型放行属于后续版本的产品决策。

### 六.4 第二十轮的行为变更登记（客户端 · 服务端 · 运维）

口径不变：**只写"你会看到什么"**。本小节补**第二十轮**（第十九轮的两条已并入 §六.3 的第 4/5 条）。

**1) 「允许 AI 读取此应用的数据」授权加了账号与服务端维度（客户端，客户可见）**

- **谁会受影响**：用过这道授权开关的员工；以及**同一台机器上换账号 / 换服务端地址**的场景。
- **观察到什么**：授权记录的作用域从"本机 + 这个应用"收紧成"**这个人 + 这台服务端 + 这个应用**"。
  升级后**既有授权一律失效**（落盘格式升到 v2，旧记录按"未授权"处理）⇒ 面板上那个开关会回到
  **关**，需要**重新点一次「允许」**。反向的变化是：换账号、或把客户端指到另一台服务端之后，
  下一个人**不再继承**上一个人的授权（此前会继承）。
- **要不要动作**：升级后按需重新授权一次。这是**有意**的方向：默认关 + 显式授权是产品口径，
  而"换个人照样放行"绕过的正是它。

**2) 卸载确认框的文案不再承诺"一定能删掉"（客户端）**

- **谁会受影响**：在能力中心卸载技能、且本机存在同名副本/本地改动的员工。
- **观察到什么**：确认框现在写明"**可能被拒绝**，被拒绝时**本地内容不会被删除**，请先处理那一份
  （项目/用户/内置等技能根里的同名副本）再重试" —— 与实现一致（跨根同名 ⇒ `422 RESIDUE`；
  本地内容与安装时不一致 ⇒ `409 LOCAL_CONTENT` 需显式覆盖）。此前文案承诺"会连同你的文件
  一起移除"，与实现的两种拒绝出口相反。
- **要不要动作**：不需要（纯文案纠正）。

**3) 技能安装/卸载的拒绝文案跟随界面语言（客户端）**

- **谁会受影响**：英文界面的员工。
- **观察到什么**：`RESIDUE`（同名残留）与"临时区身份校验失败"两类拒绝由**中文整句**改为按界面语言取
  中英；中文界面文案不变（并保留"本次没有删除任何东西 / 该去哪儿改 / 再试一次"三段可行动信息）。
- **要不要动作**：不需要。

**4) 技能安装/卸载在两种"拿不准"的环境上改为**拒绝**（客户端 · 运维视角）**

- **谁会受影响**：① Linux 上读不到挂载表（`/proc/self/mountinfo` 不可读，例如被挂载覆盖或强沙箱）
  的机器；② 文件系统不提供 inode 号（`ino` 恒 0）的机器。
- **观察到什么**：这两种环境下安装/卸载会被**拒绝**并如实说明原因（"挂载表读不到，无法确认落点
  是不是另一个文件系统的挂载点"/"身份未知"），而不是**照常执行**。此前的行为是"判据静默缺席 →
  照删照装"，在"库内临时区被换成指向库外的挂载点/符号链接"的攻击形态下会把**库外**的那一份
  删掉或搬走。另外，库内临时区在**每一个**破坏性动作（两次 rename、删除备份、失败回滚）之前
  都会重新校验身份，不一致即拒绝（`LIBRARY_TEMP_UNSAFE`）且**宁可留残骸也不误删**。
- **要不要动作**：正常部署（`/proc` 可读、常规文件系统）无需任何动作。若你的机器真属于上述两类，
  请在宿主上放开 `/proc/self/mountinfo` 的读取，或改用常规本地文件系统的工作区。

**5) 月报 webhook 不再被重复投递（服务端 · 运维视角）**

- **谁会受影响**：**多副本 / 滚动重叠发布 / 双活**跑服务端，且配置了月报订阅的环境。
- **观察到什么**：同一期月报此前可能被**投递多次**（两个实例各自判定"欠投"、各自生成、各自
  投递；实测同库同接收器、启动相差 150ms ⇒ 同一期被投 50~100 次）；现在每个订阅只投一次
  （判定、生成、认领收进同一个临界区：取锁 → 锁内新读 → 重判 → 投递 → 同锁落账）。
  单实例部署本来就不触发，行为不变。
- **要不要动作**：不需要。若你的接收方按"收到几次"记过账，注意历史重复投递造成的偏差；
  修后不会再新增。

**6) 应用打开的长期日汇总：跨 DST 时区不再少算，并给出历史坏行的修复入口（服务端 · 运维视角）**

- **谁会受影响**：部署 TZ 的夏令时跳变发生在**本地零点**的时区（例如 `America/Santiago`、
  `America/Havana`）；`Asia/Shanghai` 等无 DST 时区**不受影响**。
- **观察到什么**：这类时区里，"保留期边界那一天恰好是跳变日"时，应用打开的日汇总会**整日少算**
  （实测少 2/10，且明细已被清理 ⇒ 不可逆）。现在日边界取"该日历日**真实存在**的第一个瞬时"，
  日阶梯、保留期清理、看板趋势与今日窗口全部走同一实现；判据是"日汇总总量守恒 + 逐日归属"。
  另外新增只读运维模式 `picoaide-server --opens-rollup-repair-plan FROM[,TO]`：**不连库、不写任何
  东西**，只打印"从明细重建日汇总"的离线修复计划（两段 SQL + 执行纪律），且分日时区取自
  **部署 TZ**（不再手抄硬编码的 `Asia/Shanghai`）。
- **要不要动作**：换了 TZ 的部署**不要**沿用旧的手写修复 SQL（day 键会与线上错位）；用上面的命令
  生成计划。已经少算的历史行**不会自动恢复**：需要按计划在离线副本上重算再覆盖上线（先备份 +
  审计留痕），且只能覆盖"备份里仍有明细"的那些天。

### 六.5 第二十一至二十五轮审计批次的行为变更登记（客户端 · 服务端 · 运维 · 门禁）

口径同前：**只写"你会看到什么"**。这五轮共 5 轮审计 / 14 条修复泳道；下面是**客户与运维能感知**的变更。

**1) 技能安装/卸载：装不上的形态不再"装成功"（客户端）**

- **谁会受影响**：上传或安装 SKILL.md 的作者。
- **观察到什么**：结束分隔符不是**整行** `---`（例如 `--- ` 多了个空格）、frontmatter 带**旧调用键**
  （`disableModelInvocation`/`modelInvocable`/`userInvocable`）、SKILL.md 含 **NUL 或非法 UTF-8**、
  `name` 带首尾空白 —— 这四类此前会"预检 0 问题 → 安装 200/`ok:true` → 面板显示已安装，但模型永远
  看不到"（零报错、反复装每次都被回成功）。现在**发布预检与安装都会拒绝**（分别回
  `422 FRONTMATTER_INVALID` / `422 SKILL_MD_NOT_TEXT`），面板不再列出装不上的技能。
- **要不要动作**：按报错提示修正 SKILL.md（结束行必须是整行 `---`；调用策略用官方键；
  文件必须是 UTF-8 文本）。带 UTF-8 BOM 的 SKILL.md 现在**能正常安装并在面板列出**（此前运行时能加载、
  面板却看不见、也删不掉）。

**2) 技能库的安全加固：库外文件不再被误删/误写（客户端 · 运维视角）**

- **谁会受影响**：`<DSH_HOME>/skills` 下存在符号链接/挂载点/并发写入者的机器。
- **观察到什么**：安装器的临时区、墓碑目录（`.skill-removed`）、锁目录（`.skill-locks`）现在都在
  **每一个破坏性动作之前**重新校验身份，任一处不可信即**拒绝**并如实记日志（宁可留残骸，也不越界）；
  在"读不到挂载表 / 文件系统不提供 inode / 身份未知"的环境上会**拒绝**安装或卸载而不是照常执行。
- **要不要动作**：正常部署无需动作；若你的机器属于上述"拿不准"的环境，日志会点名原因。

**3) 认证配置：保存失败不再静默（服务端 · 运维视角）**

- **谁会受影响**：在 webadmin 保存 LDAP/OIDC 配置的管理员。
- **观察到什么**：若 IdP discovery 失败等导致**新配置无法生效**，保存**不再回 200**（改回
  `500 INTERNAL`，消息写明"设置已保存但未生效"），并写审计 `apply_failed` 与 ERROR 日志；
  **旧的可工作 provider 不会被摘除**（此前会被静默换掉，登录页 SSO 按钮点到 404）；
  `/auth/methods` 的 `configured` 现在反映**运行期真实可用性**（设置里开着但实际没起来 ⇒ false）。
- **要不要动作**：看到 500 时按消息修配置再保存；不需要重启。

**4) LDAP：未配 `group_filter` 不再清空组归属（服务端 · 运维视角）**

- **谁会受影响**：LDAP 登录启用、但**没有**配 `group_filter` 的环境。
- **观察到什么**：此前每次登录都会把该用户的**全部组归属清空**（含管理员手工分配的部门），
  且不自愈。现在"未配置组过滤器"= **不做组同步**（不动既有归属）；配了过滤器而目录返回空组时
  仍按既有语义回收。
- **要不要动作**：无需动作。若你此前"莫名丢了部门归属"，可让管理员按审计/备份恢复。

**5) 月报补投：跨月不再丢期（服务端 · 运维视角）**

- **谁会受影响**：webhook 连续失败跨过月界的环境（密钥轮换/机器人被删/出口被拦）。
- **观察到什么**：此前只补"最早一期"、中间各期**永久丢失**；现在按序**逐期补齐**
  （每小时一轮、每期恰好一次），且投递地址改回正确值后** 下一轮自愈**（"修好 webhook 后
  最多 1 小时补投"这条承诺重新成立）。异常期号（未来期号/越界期号）按**不可信输入**处置：
  不投、留痕、不设退避。
- **要不要动作**：若你的接收方按"收到几次"记过账，注意历史重复/漏投造成的偏差；修后按上表收敛。

**6) 用量与报表：更宽分区不再少计（服务端 · 运维视角）**

- **谁会受影响**：把 `usage` 月度分区换成季度/整年布局的部署。
- **观察到什么**：这类布局下**报表与用量中心会静默少计**（实测某月 10 vs 真值 17）；
  现在"某月是否有明细"由**分区边界**推导（不再只认同名月分区）。读源口径 = "窗口被叶子分区覆盖 ∧
  明细侧知道得更多"。

**7) `/v1/files` 上传上限回到声明的 64 MiB（服务端 · 客户端）**

- **谁会受影响**：通过 `/v1/files` 上传附件（multipart 或 chunked）的客户端。
- **观察到什么**：同一份字节此前被内存闸门收两次 ⇒ 实际上限只有 **24 MiB**、且超限回**可重试**的
  503「网关繁忙」（客户端会重试到死循环）。现在上限就是声明的 **64 MiB**，超限回
  **413 `VALIDATION`「上传文件超过上限（单文件最大 64MiB）」**（不可重试、文案指向真因）。

**8) 应用（WASM）命名：与平台路由静态段同名的新名字会被拒（服务端 · 运维视角）**

- **谁会受影响**：发布应用的人。
- **观察到什么**：`app_id` 与平台路由静态段同名（如 `uploads`）此前能发布、但应用**永远打不开**
  （路由被静态段吃掉）且名字永久占位。现在这类名字在**发布侧**被拒（`400 INVALID_APP_ID`
  + `reason=route_static_segment`）。
- **存量应用**：**运行与读取不受影响**（服务侧刻意不套用这条写侧规则，`rows` 等既有名字照常服务
  —— 这是本轮修掉的一条"修复引入的回归"）。但**"发布新版本"不受这条豁免**：本版（以及其后的每一个
  预发版）把 WASM 前缀下**任意深度**的静态段全部收进保留集合 —— 共 17 个（`catalog`/`proof`/
  `validate` 三个同层叶子段 + `rows`/`schema`/`releases`/`request`/`open` 等 13 个深层段 +
  `uploads`）—— 其中 16 个在真实路由匹配树上**完全可达**，却一律被写侧拒 ⇒ 叫这 16 个名字的
  **存量应用在本版发不出新版本**（发布与标识查重都回 `400 INVALID_APP_ID`
  + `reason=route_static_segment`）；只有 `uploads` 是真的会遮蔽应用路由的那一个。
- **本版之后**：保留集合的口径已收窄为"**恰好等于真遮蔽集合**"（在这些静态段里只有 `uploads`
  会遮蔽 `:app_id`），上述 16 个名字恢复可用。**这条修复尚未随本版发布**，它作为一条行为变更
  会在后续版本的发布说明里登记。

**9) webadmin 管理会话：依赖故障不再当登录失效（服务端 · 运维视角）**

- **谁会受影响**：PG 抖动期间在 webadmin 操作的管理员。
- **观察到什么**：管理会话校验的**依赖故障**此前一律回 401（前端切登录态）；现在回
  **500**（前端保留登录态、可刷新恢复）。真正的会话无效/过期/吊销仍是 401。

**10) 内置浏览器：默认工具集与凭据脱敏（客户端）**

- **谁会受影响**：所有用户（这类默认值此前被一次修复改坏过，见下）。
- **观察到什么**：内置浏览器的 31 个工具在**生产装配**下必须全部注册（此前一次修复把它变成 0 个，
  本版已修复并补了"生产形态"判据）；`browser_eval` 与 `browser_get_text` 的**凭据脱敏口径统一**：
  认证头（任意方案名，含 `SSWS`/`SNOWFLAKE_JWT`/Zendesk）、`k=v` 凭据对、URL userinfo 一律掩码；
  普通正文（`width=100; height=200`、`?keyword=`、`?zipcode=` 等）**逐字节保留**（此前会被整串抹成
  `****`）。局域网用**主机名**访问内置浏览器的地址会 403（IP 字面量照常）—— 出路是 `--trusted-host`。

**11) 门禁（仅影响开发/CI，不影响客户）**

- 生成物脚本位、判决见证、CI 被钉步骤的**载荷与可达性**判据继续收紧（"改写仓内脚本再执行"这一类
  绕过在 CI 上必红）。
- **需运维知晓的一条历史事实**：2026-09-24 的 `0054`/`0055` 迁移曾**被就地改写**，那批修复
  **对已升级的库不可达且不可自动恢复**；处置见 `server/docs/06-database.md`（含只读检测 SQL）。

### 六.6 第二十六至二十七轮审计批次的行为变更登记（客户端 · 服务端 · 运维 · 门禁）

**1) 打包版客户端：调试开关的拦截面变宽，且 `--inspect*` 改用打包期 fuse（客户端 · 安全）**

- **谁会受影响**：①任何用命令行参数启动**安装版**客户端的人；②用 `--inspect`/`--inspect-brk`
  调试**安装版**的开发者（`yarn dev` 开发态不受影响）。
- **观察到什么**：
  - **单横线形态现在也被拒**：`-remote-debugging-port=9222`、`-js-flags=…` 此前能绕过闸门
    （Chromium 真的认单横线，实测会打开 DevTools 监听），现在与双横线一视同仁。
  - **`--inspect` / `--inspect-brk` 在安装版上彻底不可用**，报错由打包期 Electron fuse
    `EnableNodeCliInspectArguments=false` 在**参数解析期**产生（不再依赖 JS 闸门）。
    **这是有意的能力移除**：这两个参数会在应用主脚本执行**之前**挂起/接管主进程，
    任何写在 JS 里的检查都拦不住 —— 真机实测过攻击者能在拒绝文案出现**之前**拿到
    `root` 与任意文件读。**没有环境变量逃生门**。
  - 排查安装版问题请改用 **CDP**（`--remote-debugging-port` + `PICOAI_ALLOW_DEBUG_SWITCHES=1`，
    六个 E2E/探针脚本已如此）或 `yarn dev`。
- **不要误读**：请不要把"六类调试开关都被拒绝"当成安全结论 —— `PICOAI_ALLOW_DEBUG_SWITCHES=1`
  是自动化便利，不是边界（同机同用户的攻击者两者都能设）。

**2) 客户端：跨服务端/跨会话的"迟到响应"不再改写当前会话（客户端 · 安全）**

- **谁会受影响**：快速登出再登录**另一台**服务端的人（含切渠道、切账号）。
- **观察到什么**：模型目录、默认模型、Web 搜索地址、错误上报目标、渠道品牌这五处投影
  **不再被上一台服务端的迟到响应覆盖**。此前最坏情形是一次网页搜索会把**新会话的令牌**
  发到**旧服务端**的 `/v1/messages`（跨租户凭据外发），或登出后错误上报被静默重新打开。
  现在每个 await 之后都会复核"还是不是同一位"，不是就丢弃、不写盘、不发事件。

**3) 定时任务面板：不再显示他人的任务名（客户端 · 安全）**

- **谁会受影响**：多账号共用一台机器、或服务端有多个员工时。
- **观察到什么**：`skippedOccurrences`（"跳过了哪些次"）此前会把**别人**的任务名带进面板横幅；
  三条出口（状态查询、动作响应、实时推送）现已同时按归属过滤。

**4) 连接器：凭据读失败不再被当成"没有凭据"（客户端 · 数据完整性）**

- **谁会受影响**：凭据文件被权限/长度/格式问题挡住时（此前**静默**）。
- **观察到什么**：此前一次瞬时读失败（如 EACCES）会让"刷新令牌"把整份凭据**覆盖写成空**，
  且**无日志无异常**，access/refresh token 与 client id/secret 一起消失。现在：
  **只有"文件不存在"才算没有凭据**，其余读失败一律 fail-closed —— 拒绝改写并**如实报错**、
  往宿主日志写一条可检索记录。出路：修好该文件，或「断开」连接器后重新授权。
- **一处需要知晓的连带影响**：内置浏览器解析连接器凭据的接口在遇到读失败时**由"返回空"改为抛出**，
  因此 `browser_fill_credentials` 会给出明确的读失败错误（而不是"没有存储的凭据"）。
  错误文本只含连接器 id 与系统错误码，**不含任何文件路径**。

**5) 连接器：切换账号后的"需要重新授权"不再卡死（客户端）**

- **谁会受影响**：后台正在扫掠/刷新凭据时切换服务端或账号的人。
- **观察到什么**：此前后台任务会把排队中的"会话切换"顶掉，导致凭据作用域闸门**永久**返回 409
  （连接/断开/授权/刷新全部失败），只能重启客户端。现在后台任务不再抢占会话切换，
  且切换任务的收尾**必定**解除闸门；即使撞上进退出窗口，也会在 ≤30 秒内自愈。

**6) 白标渠道构建：缺品牌素材不再静默回落厂商品牌（运维 · 交付物）**

- **谁会受影响**：维护品牌渠道包的人。
- **观察到什么**：品牌渠道若缺 `assets.logo` 或 `app-icon.png`，此前**照常构建成功**，
  交付物里是**厂商品牌**的安装器/Dock/任务栏图标（客户可见）。现在**构建期直接失败并点名字段**。
  另外 `assets.logo` 的取值必须是 `logo.svg`（它是托盘位图与随包图标的唯一派生源）。
  公共渠道（official/beta）缺素材时**仍回落官方**，但会打印一条明确日志。

**7) 发布链：中转前缀去掉 run attempt；取回要求三平台齐全（运维）**

- **谁会受影响**：发版与渠道交付。
- **观察到什么**：
  - R2 中转目录前缀不再编入 `GITHUB_RUN_ATTEMPT` ⇒ **重跑不再产生第二份前缀**，
    失败 attempt 的品牌安装包不再永久留在**公开读**桶里；`clean` 会顺带清掉旧格式残留。
  - `pull` 阶段新增**逐平台齐全**判据：缺任一平台（macOS/Windows/Linux）即失败并点名
    —— 此前重跑只补失败平台时，会以"半套客户端"全绿交付。
  - **需运维知晓**：本次改动**之前**已结束的 run 留下的旧前缀无法由代码枚举，
    需按 REPORT 给出的命令人工清理；长期建议给桶加一条 `_transfer/` 生命周期规则。

**8) 文档更正：预发 tag 出不了品牌渠道包，没有手工入口（运维）**

- **观察到什么**：站点部署文档此前写"要提前出品牌渠道包只能用 `workflow_dispatch`"，
  而 CI **根本没有**这个触发键。已改为事实陈述（品牌渠道包只能等正式 tag），
  并加了常驻守卫逐行对拍"文档提到的触发键必须真实存在"。

**9) 门禁（仅影响开发/CI）**

- 新增：会话代际守卫的**接线判据**（新增未经守卫的会话入口即红）、打包产物 **fuse 回读**判据
  （`EnableNodeCliInspectArguments` 必须为关，否则打包失败）、渠道素材必需集（输入侧 + 打包侧）、
  三平台客户端清单**唯一真源**（`CLIENT_PLATFORM_ASSETS`，被中转、镜像、CI 三处对拍）、
  文档与工作流触发键的对拍守卫。
- 改写了 `tests/channel-prepare.spec.ts` 中一条**把缺陷钉成预期**的用例
  （"品牌渠道缺 `logo.svg` ⇒ 回落官方"），并补 3 条负例 + 1 条公共渠道正向对照。

## 七、附件与校验

- **服务端**：`picoaide-server-2.8.2-beta.2-amd64.zip`（同目录 `SHA256SUMS`）。
  下载后先 `sha256sum -c SHA256SUMS`，再 `docker load`。
  预发布 tag **只构建 beta 渠道**的镜像与客户端；品牌渠道要等正式 tag 或
  `workflow_dispatch`。
- **客户端**：随镜像分发（镜像内 `/opt/picoaide/client/`），由部署后的门户与
  `/api/client/v2/updates/manifest` 下发。校验口径：从**部署后的域名**实拉安装包，
  `sha256` 与 manifest 里对应平台的取值**逐字相同**。
- **本版有一条数据库迁移（`0082`）**，所以回滚按 `docs/deploy/AI-DEPLOY.md` §7 的**四步顺序**
  （**先停服 → 恢复升级前的 `pg_dump` → 再回退镜像 → 客户端回退到同版本**）——
  `0082` 头部那条更轻路径的适用边界、彻底清理与回滚前滚的写法见 §三；
  **客户端回滚见 §一.1** —— 数据根的整目录恢复是唯一手段，不是换二进制。
