# PicoAide Harness v2.5.9（2026-09-01）

本版本从一个看似很小的界面问题开始——「能力中心的市场卡片显示技能的目录名，装完却显示中文名」——顺着查下去，发现了一条贯穿服务端、客户端与上游运行时的系统性缺陷链：**某部署实例的 30 个市场技能里，有 27 个装到用户机器上后会被运行时静默忽略，模型永远调用不到，全程没有任何报错**。

于是本版本不只是修显示名，而是把技能资产的发布、审核、分发与安装整条链路按「应用商店」的方式重建：**应用（App）是长期身份，版本（Release）是不可变快照，包内容是元数据的唯一真源**。

> 本版本合并了开发期 v2.5.9–v2.5.16 的全部工作（那批 tag 因 CI 缺陷未产出正式发布，已删除）。

---

## 一、核心问题与根因

### 1. 27/30 技能装了用不了 🔴

- **现象**：技能在能力中心显示「已安装」，但模型从不加载它，也不报错。
- **根因**：上游 `@deepseek-ai/dsh-skill-filesystem` 以 `SKILL.md` 的 frontmatter `name` 作为技能的**运行时唯一身份**，且强制 kebab-case（`/^[a-z0-9]+(?:-[a-z0-9]+)*$/`）。不合规的技能会被整条跳过，只在日志里留一行 warn。而线上技能普遍把中文展示名写在 `name` 里。
- **实测**：把 30 个市场技能真实下载、解包、用桌面端实际依赖的上游 provider 跑发现流程，**只认出 3 个**。失效分为三类：25 个 `name` 非 kebab、2 个 SKILL.md 带 UTF-8 BOM（frontmatter 解析失败）、1 个可加载但运行时名与目录名不一致。
- **为什么一直没被发现**：三道关卡全部放行——服务端只校验「有 SKILL.md + 路径安全」，客户端安装器明确「已有 frontmatter 一律不动」，界面照常显示「已安装」。

### 2. 市场卡片显示目录名 🔴

- **根因**：市场域的 `skills` 表**没有展示名字段**，聚合面只能回退成目录名；而「我的」分区直接读磁盘 frontmatter，于是显示中文。同一份技能在两个分区显示两个名字。

## 二、破坏性变更（发布技能前必读）

### 严格发布契约：不合规的包一律拒绝上架

即日起，技能与智能体的**全部上传入口**都会在发布期做严格校验，不合规直接拒绝并给出可操作的错误码与修复指引。

**六个字段全部必填，且必须写在包内**（技能写在 `SKILL.md` frontmatter，智能体写在 `preset.yml`）：

```yaml
---
name: team-knowledge-wiki         # 必填｜= 技能文件夹名｜小写 kebab-case｜运行时身份
title: 团队知识库助手              # 必填｜展示名，中文写这里
version: 1.2.0                    # 必填｜semver，每次发布必须递增
description: 内部知识库的索引与强制读取规则，覆盖常见制度与流程问题。  # 必填｜10–2000 字
author: zhangsan                  # 必填｜署名
category: 通用                     # 必填｜单值字符串（不是数组）
tags: [知识库, 制度, 流程]          # 可选｜≤30 个
changelog: 补充报销流程章节。       # 非首个版本必填
---
```

**最容易踩的三个坑**：

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `name` 写中文/大写/带空格 | 技能装上后被运行时**静默忽略**，模型永远用不到 | `name` 必须等于文件夹名，中文名放 `title` |
| 文件存成「UTF-8 带 BOM」 | frontmatter 解析失败，同样被静默忽略 | 另存为 **UTF-8 无 BOM**，LF 行尾 |
| 版本号没升就重新发布 | 版本是不可变快照，同版本号（含被拒过的）永久占用 | 每次发布前递增 `version`；内容没变则无需发布 |

其它硬性要求：正文不少于 50 字（拒绝空壳）；调用策略字段（`user-invocable` 等）必须合法；归档不得自带 `.picoaide/` 目录或 `metadata.picoaide` 段（那是安装器写的来源标记，自带视为伪造归属）。

**上限按真实数据放宽**：`description` 是模型侧的触发文本（上游本无长度限制），实测真实技能的中位数约 240 字、最长近 1000 字，因此上限定为 2000 字而非最初的 500；`tags` 上限 30 个。

### 版本即不可变快照

- 同版本号一经提交即**永久占用**，含被拒绝和已删除的版本，不可复用——被拒后必须升版本号重新提交；
- 新版本号必须**严格大于**该应用现有最高版本；
- 审核、质量标记、上下架只改状态位，**永不触碰已发布版本的内容**。

### 市场技能的 git 源模式已移除

`skills` 表的 `git_url` / `git_ref` / `source` 三列删除，克隆构建代码与后台的「Git 地址」表单一并移除。**归档上传成为唯一内容入口**——git 模式在创建时没有归档可校验，与「包内即真相」根本冲突，且它导致了「创建时填了版本 → 首次上传同版本被自己的校验挡死」的缺陷。生产核实：唯一的 git 行是测试残留，无真实技能依赖。

### 发布接口不再接受元数据参数

名称、版本、标题、描述、作者、分类一律由服务端从包内解析。管理后台表单不再手填这些字段（表单值与包内容不一致时，装到用户机器上的是包内容、界面显示的是表单值——这正是显示名错位的同款根因）。

## 三、新增能力

### 应用锁定（仅管理员可发布）

管理员可把某个技能/智能体标记为锁定，员工发布命中时返回 `403 APP_LOCKED` 并**原样回显管理员填写的理由**。支持对**尚不存在**的名字预先锁定（占名），防止员工抢占官方命名。锁定与授权、上下架、质量标记正交；管理员发布不受限制。webadmin「能力中心」页新增锁定管理面板。

### 审批可预览

- 市场技能新增后台预览：文件清单 + `SKILL.md` 全文 + 逐文件查看（越界路径拒绝），契约与组织共享库一致，webadmin 复用同一个预览组件；
- 审计明细统一为 `name@version 「展示名」 sha256:前8位`，**审计页可直接打开归档预览**，审批人无需再去技能页翻找。

### 客户端溯源与本地改动检测

安装时写入 `.picoaide/release.json`（应用 ID / 版本 / 渠道 / 来源服务端 / 内容哈希），取代旧的单值 `.install-version`。客户端据此回答「这份技能来自市场哪个应用的哪个版本」，并通过重算内容哈希标记「已本地修改」。重新打包时自动排除该目录。

### 发布前本地预检

客户端在打包后立即执行与服务端**同一套规则的前 7 步**（纯包内校验、不查库），**错误码与服务端逐字一致**——不合规在点「上传」之前就报出来，不必等一次网络往返。

### 卡片显示运行时调用名

当技能的运行时名与应用 ID 不一致时（例如 `workspace-cli` 实际注册为 `dws`），卡片会显式提示「调用名: dws」。此前用户只能装完才发现该 @ 什么。

### 存量技能一键规范化

管理后台新增规范化端点：把不合规的存量包改写为合规内容并作为 **patch+1 的新版本**发布（剥 BOM、中文 `name` 迁移到 `title`、补齐缺失字段、剥离自带溯源块）。**拒绝编造 `description`**——它决定模型何时加载技能，缺失时明确报错要求人工补写。对已合规的包是幂等空操作，不产生噪音版本。

## 四、架构：统一应用模型

技能资产此前分散在三张语义不同的表里（市场单版本原地覆盖 / 组织多版本带审核 / 智能体多版本带审核），各自一套授权表与端点。本版本统一为：

- **`apps`**（长期身份：`kind` + `app_id` 唯一、标题、归属、渠道、上下架）
- **`app_releases`**（不可变版本快照：`(kind, app_id, version)` 唯一、归档、审核状态、软删）
- **`app_grants`**（授权，三张旧授权表合并，按 `kind` 区分）

配套的 **统一发布内核**（`internal/appstore`）让锁定、版本语义、跨渠道同名互斥、归属保护与待审配额只实现一次，**三条上传路径（管理后台 / 客户端能力中心 / 客户端智能体预设）共用同一份实现**。

由此带来的实质变化：

- **市场获得多版本快照能力**——归档上传由「原地覆盖」改为「新增 Release」，有了版本历史与回滚基础；
- **跨渠道同名冲突结构性消失**——一个 `(kind, app_id)` 只能属于一个渠道，旧的「冲突标记 + approve 时 409 阻断」不再有产生条件；
- **智能体补齐了此前完全缺失的管控**——锁定、版本递增、归属保护、待审配额此前对智能体**完全不生效**（管理员锁了也拦不住员工上传），现已与技能一致。

迁移方式采用**适配层**而非重写 handler：`serverstore` 保留原有函数签名、内部改读写统一表，使 4 个业务包上百个调用点无需改动即可切换存储，行为由既有测试套件逐条保证。回填后旧表保留一段时间作为回滚依据，随后由迁移 `0055` 下线。

## 七、部署与升级

- **客户端**（三平台）：mac DMG / win x64 Setup / linux AppImage，附 `SHA256SUMS.txt` 校验
- **服务端镜像**：`ghcr.io/picoaide/picoaide-harness-server`（`v2.5.9` / `latest`）
- **数据库迁移**：`0050`–`0055` 自动执行，含统一模型建表、三张旧表回填与旧表下线。**迁移不可逆，升级前请备份数据库**

### 升级注意

1. **发布链路有破坏性变更**：升级后，不符合上述契约的技能包**无法上架**。存量不合规技能仍可正常安装与使用（旧版本不受影响），但发布新版本前必须先合规化——管理后台的「规范化」按钮可一键处理大部分情况。
2. **技能作者需要更新发布规范**：如果你的团队有自己的技能发布文档或脚本，请同步更新为「`name` = 文件夹名、中文名放 `title`」，否则产出的包会被拒绝（错误信息会写明原因与修复方式）。
3. **服务端与 webadmin 需同步升级**：本版本含数据模型与接口契约变更。
4. **git 源技能**：如仍有依赖 git 模式的技能，升级前请先上传归档转为上传模式（本次生产核实无此类技能）。
