## 一、应用打不开：界面报 `错误码: OPEN_PROOF_REQUIRED`（阻塞级）

- **现象**：员工在应用中心点「打开」，界面报
  `打开失败：本页面无法证明自己属于这个客户端窗口`；服务端日志是
  `POST /api/client/v2/apps/wasm/proof` → `400`，紧跟 `POST …/open` → `401 proof_required`。
- **影响**：**应用功能整体不可用** —— 打开、分享深链、应用窗口、应用内 AI 四条链路全部掐断，
  与员工操作无关。
- **这不是"重放"**：本机对同一枚本机凭据做过五组对拍（A–E），确认是**签发请求的形态**与服务端
  真源不一致，而不是凭据被重复使用。
- **修复**：客户端宿主签发"安装证明"的三处形态与服务端真源不一致 —— 多带一个字段、公钥用
  SPKI/DER（44 字节）而非**原始 32 字节**、签名消息用规范化 JSON 而非
  `appproof-install-v1` **五段换行串**。现按服务端单一真源重写，并补**跨端判据**：判据**直接读
  Go 源码**，钉死前缀、五段字段顺序、请求体字段集与 32 字节公钥（旧判据只断言"签名是 base64"，
  换个形状也是绿的 ⇒ 属假绿）。
- **自证**：本机真机 `open` 由 `401` 变 `200`，宿主日志中 `400` 归零；契约判据可被变异打坏。

## 二、点了「打开」返回成功，屏幕上却没有窗口（阻塞级）

- **现象**：`open` 返回 `opened`，但没有窗口出现；再点一次也不会聚焦。
- **影响**：同 §一，属产品主功能不可用。
- **原因（三处同时成立，缺一即坏）**：真实 Electron 窗口适配器**只有接口声明、从未实现**；
  桌面壳**没有 provide** 该服务；应用窗口的数据目录**没有注入**。三者叠加后代码走了"没有窗口
  实现"的分支，只发出一条**没有任何消费者**的事件。
- **修复**：实现真实窗口适配器（应用 origin、标题冻结、**同应用 origin 的导航闸门**、
  窗口存活与工作区判定），桌面壳接线并注入 `userData`。
- **顺路修掉应用页"窗口开了却永远显示连不上服务端"**：宿主按契约给平台请求合成
  `Origin: <scheme>://<app_id>`，而浏览器栈会**先发 CORS 预检**（平台没有 OPTIONS 路由 ⇒ `404`
  ⇒ `net::ERR_FAILED`，服务端日志里只有 `OPTIONS … 404`）。平台出站改走 `net.request`
  （**仍走同一 session** ⇒ 证书固定与代理策略不变；已解压的响应体不再带 `content-encoding`）。
- **自证**：真机 open 后调试目标出现 `picoaide-app://<app>/`，窗内渲染的是平台里的**真实应用
  内容**（含登录身份）；`opened → focused →（关窗）→ opened` 三态通过；13 条变异全部可打红
  且还原前后哈希一致。
- **同时加固（第二轮独立审计发现，本版一并修）**：
  - **导航闸门覆盖重定向**：原先只拦直接导航，应用页发起的 **302 仍可把窗口换到外站或另一个
    应用的 origin**（"换壳"）。现让重定向与直接导航**共用同一个判据**；真机验证：外站/跨应用
    302 ⇒ 窗口 URL 不变，同应用 302 照常放行。
  - **应用窗口改到按用户分区**：原先跑在**默认 session**（与主窗口同一存储面）。现与内置浏览器
    使用**同一个按用户分区**，应用页读不到默认 session 的存储；同时补上"跨应用内嵌 iframe 一律
    拒绝"与"跨源重定向一律中止（凭据不外流）"两条。"默认 session 不共享"是纵深防御的加强 ——
    审计未发现实际凭据泄漏路径。

## 三、运营看板「打开趋势」的 UV 比同页「今日 UV」大（口径错误）

- **现象**：同一天「今日 UV = 2」，而「打开趋势」的 UV 是 `3`。
- **原因**：趋势的 UV 由**各应用的日 UV 相加**得到 —— 同一个人开了两个应用就被计两次。
  日汇总表按"应用 × 天 × 部门"存储，从它取跨应用去重人数**只有相加一条路**，而那正是口径禁止的。
- **修复**：趋势**按天同源** —— 明细还在的天，PV 与 UV 都从明细取（一次聚合同时得到打开次数与
  去重人数）；只有**明细已过期**的天才把 PV 回落日汇总（UV 如实为 0）。日期集合取"明细天 ∪
  日汇总天"，因此**首个 5 分钟汇总 tick 之前曲线也不会漏掉"今天"**。日边界由服务端**单一实现**
  算好后一次性传给 SQL，**不在 SQL 里二次定义"日"**（DST 的 23/25 小时日因此不会串日）。
- **不变量**：每个趋势点恒有 **UV ≤ PV**。第一版修复曾把"PV 读日汇总、UV 读明细"混用，实测出现
  `UV=27 > PV=26`（去重人数大于打开次数，语义上不可能）—— 本版已修，并把该不变量写成判据。
- **自证**：同一份数据，旧口径 `SUM(uv)=6`、真去重 `=2`、本版接口给 **`2`**，与同页
  「今日 UV」「总计 UV」一致；不变量与"tick 前不漏今天"两条判据都可被变异打坏。
- **认账**：早于 **90 天**明细保留期的日期，趋势 UV **如实给 0**（PV 仍真实）；**不会**用相加顶替。
  长期保留需要新增数据库迁移，本版未做。

## 四、管理端：限制项误操作会静默清空、拒绝申请可以不给理由

- **限制项（运维→应用平台）**：把字段**扁平**提交（漏了 `limits` 外层）原先会**静默回落部署
  档位**、返回成功、且不写审计 —— 管理员以为改了限制，其实被清空。现在这类形状一律 `400` 并
  告知正确形状与允许的键；「恢复部署档位」改为**显式**提交 `{"limits":null}`。
  校验发生在**落库之前** ⇒ 误用零副作用（不改运行时、不写审计、不落库）。
- **拒绝申请**：`reason` 现在**必填**（空白/纯空白都拒），管理端提交按钮同步禁用并标「必填」。
  理由会写进审计、管理端"最近被拒"清单与**作者客户端** —— 作者据此改后再发。
- **另修**：「来源」标签重复显示（`控制台保存（wasm.limits）（wasm.limits）`）。

## 五、被冻结的应用不再被当成"应用不存在"

- **现象**：管理员**冻结**某应用后，员工打开它看到"应用不存在"。冻结是**只读快照（数据保留）**，
  正确呈现应是「已被管理员停用」。
- **修复**：平台错误的 `reason` 固定为两档 —— `app_frozen`（冻结）与 `app_not_found`
  （软删与"从未登记"同档；**下架仍由 HTTP 410 承载**）；**宿主与客户端两处都读它**：
  冻结 ⇒ **保留窗口与缓存**并显示「已被管理员停用」；软删/不存在 ⇒ 关窗清缓存。
- **另修**：同事点开分享的应用深链时，宿主日志会出现一条误导性的
  `ignored malformed deep link` —— 应用链接与登录回调共用同一个事件、两个监听器都打告警。
  现在按 **scheme/host 分流**：应用深链静默让行（由应用侧处理器消费），其余情形保留告警但**带上
  可判别的原因**，排障不必靠猜。

## 已知限制（本版认账，未修）

- **应用窗口内的外链落点**未实现：应用里的外部链接当前一律拒绝打开（计划中）。
- **应用内 AI 的控制权交互与"按应用寻址"**属下一批（计划中）；应用内 AI 的模型链路本身可用。
- **趋势 UV 的长期（>90 天）保留**需要新增迁移，本版未做（当前口径见 §三）。
- 每次打开会因一次性凭据多**一次 `401` + 重签往返**（用户无感，属设计）。
- **三平台只在 Linux 实测**：Windows/macOS 的窗口行为与自定义协议注册待真机复核（计划中）。
- **仓库隐私守卫的覆盖面**：判据覆盖**已跟踪文件与提交信息**；GitHub 的 **Release 正文**与
  **PR 标题/正文不是文件 ⇒ 不在判据内**（本版已人工清理存量泄漏，后续靠流程约束）。

## 升级与回滚

- **服务端**：取本版镜像压缩包 → 按 `docs/deploy/AI-DEPLOY.md` 升级（**升级前必须备份**，
  不要使用 `latest`，不要 `down -v`）。
- **客户端**：随服务端镜像分发；服务端升级后员工从自己登录的服务器取包，无需访问外网。
  **本版服务端与客户端请一并升级**（应用打开链路的证明契约在两端）。
- **回滚**（本版**无新增迁移**，属平级版本）：
  - 服务端：把 `SERVER_IMAGE` 改回上一版 tag（`…:beta-2.7.6-beta.5`）+
    `docker compose up -d server` 即可，**不需要**恢复数据库。
  - **混版口径**：把**服务端**回退到 beta.5 时，本版客户端**仍能正常打开应用**（证明契约的修正
    在客户端一侧，而 beta.5 服务端要求的正是规范形态）—— 但会失去本版服务端侧的口径与校验修复
    （§三/§四）。反过来把**客户端**回退到 beta.5（服务端保持本版）则应用**打不开**，
    现象与 §一 完全一致。
