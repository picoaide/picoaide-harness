# 发布说明规范（docs/releases/&lt;tag&gt;.md）

GitHub Release 页是**公开面**：客户、运维与同事都在这里判断「这个版本是什么、我要不要升级」。
本文件是发布说明的约定与模板。**发布 tag（正式版与预发版）上 CI 一律强制要求**
`docs/releases/<tag>.md` 存在。

## 一、命名与位置

- 文件：`docs/releases/<tag>.md`，与 git tag 逐字一致（含 `v`，例如 `v2.7.1.md`）。
- **Release 名 = tag 本身**（`v2.7.1`），不加产品名前缀。
  Releases 页左侧列表宽度固定，`PicoAide Harness v2.6.9-beta.5` 这类长名会被截断成
  `PicoAide Harness v2.6…` —— 一页十几个版本号全都看不见，只剩重复的前缀。
  产品名由仓库名与页面标题承载，Release 名只回答一个问题：**是哪个版本**。
- **正式 tag 与预发 tag 一律要求**（2026-09-23 定案）：缺 `docs/releases/<tag>.md` 时
  1) `gate` 第一步直接失败（不必等三平台构建 40 分钟），2) `release` job 在**任何对外上传
  之前**再拦一道，3) `Create GitHub Release` 步骤是第三道。
  **没有"回退自动变更日志"这条路径**：自动变更日志的正文由提交信息 + PR 标题/正文生成，
  而 **PR 标题/正文不是文件 ⇒ 不在任何守卫判据内**（公开面纪律的唯一防线是"人写"）。
  历史上正是这条回退路径把真实域名/IP 带进了公开 Release 正文 —— 预发版因此不再例外。

## 二、写作口径

- **先写读者要做的决定**：谁必须升级、不升级会怎样、影响哪些平台，放在最前面；实现细节放后面。
- **一节一件事**：现象 → 影响 → 本版怎么修 →（可选）怎么验证。避免按提交或文件罗列。
- **两个固定小节**（名称照抄模板，后续版本直接套用，位置也固定）：
  - **访问模型变更**：只在「用户访问产品的方式」有实质变化时写（例：应用只在客户端内打开）。
    必须写清四件事 —— 变化是什么；浏览器/旧入口还能不能用；**服务端与客户端是否必须同版本升级、
    不同版本一起用会怎样**；升级前要做什么、哪些旧配置不再需要。
  - **已知限制**：只列**仍未修**与**本版新引入**的限制（谁遇到 → 现象 → 现在怎么办），
    已修项不要搬进来；没有就写「本版无新增认账项」，不留空标题、不写「无」占位。
- **面向客户与运维写**，不写内部黑话（CI 步骤名、脚本名、门禁编号、fail-loud/告警措辞可以出现，
  但要先说清楚它对人意味着什么）。工程侧读者需要的深度用链接给出，不塞进正文。
- **公开面纪律**：不写客户名与客户品牌、密钥、内部地址、内部排期与投放机制。渠道相关一律中性表述。
- **结尾必须给**：附件清单与校验方式、升级步骤（指向 `docs/deploy/AI-DEPLOY.md`）、回滚方式。
- 版本间的差异要写清楚：与上一版**产品代码是否相同**、是否只需要换镜像。

## 三、模板

````markdown
# vX.Y.Z（YYYY-MM-DD）

> 一句话：这个版本做了什么、谁必须升级。

| 项目 | 说明 |
| --- | --- |
| 版本类型 | 正式版 / 预发布（beta·rc） |
| 升级建议 | 必须升级 / 建议升级 / 可选 |
| 影响面 | 服务端镜像 / macOS 客户端 / Windows 客户端 / 管理后台 |
| 产品代码变化 | 有（相对 vX.Y.(Z-1)）/ 无（仅打包与分发链） |

## 访问模型变更（升级必读）

<!-- 只在访问方式有实质变化时保留本节；有本节时它排在所有功能小节之前 -->

- **变化**：谁会感觉到什么不同（例：应用只在桌面客户端内打开，浏览器不再可用）。
- **必须同版本升级**：服务端与客户端**必须同版本**；旧版客户端会怎样（例：打不开应用）。
  一句话结论，照抄式：**若你使用旧版客户端，请先升级到本版再使用应用功能。**
- **不再可用的路径**：旧入口/旧地址/旧配置一律不再可用（说清「不是配置问题、没有开关」），
  以及存量数据与设置的兼容口径（历史取值如何处理）。
- **运维要做什么**：升级前必做，以及本版**不再需要**的配置（逐条，可照抄）。

## 一、<用户能感知到的那件事>

- **现象**：用户/运维实际看到什么。
- **影响**：谁受影响、不修会怎样。
- **修复**：本版怎么做，如何自证（门禁/实测）。

## 二、<下一件事>

## 已知限制（本版认账，未修）

<!-- 只列仍未修与本版新引入的限制；已修项不写在这里，没有就写「本版无新增认账项」 -->

- **<限制>**：谁会遇到 → 现象 → 现在怎么办。安全类限制写清影响面（例：仅影响日志/SIEM，
  不影响审计链），并说明下版是否处理（不确定就写「计划中」，不要写成承诺）。

## 升级与回滚

- 服务端：取镜像（更新服务器附件）→ 按 `docs/deploy/AI-DEPLOY.md` 升级（**升级前必须备份**，
  不要使用 `latest`，不要 `down -v`）。
- 客户端：随服务端镜像分发，服务端升级后员工从自己登录的服务器取包，无需访问外网。
- **回滚**：先写明本版迁移属于哪一类，再给回滚方式 —— 不要只写"改回镜像 tag"：
  - **只加列 / 只建表**：保留上一版镜像 tag，改回即可。
  - **含 `DROP` / 数据改写（不可逆）**：必须写清 **停服 → 恢复升级前的 `pg_dump` → 回退镜像 →
    客户端重装/回退**，并写明"只回退镜像会报什么错"（例：旧二进制逐请求 `42P01`，
    迁移器只跳过已应用版本、**启动期不报错**）。
  - 若本版**不提供降级通道**（新旧模型不能并存），必须显式写出来。

## 附件与校验

- `picoaide-server-X.Y.Z-amd64.zip`：服务端镜像压缩包（`docker load` 后使用）；
- `SHA256SUMS`：`sha256sum -c SHA256SUMS` 校验后再解压。
````
