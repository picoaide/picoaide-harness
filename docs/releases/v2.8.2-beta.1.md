# v2.8.2-beta.1

> **谁必须升级**：所有在用 2.8.1 及更早版本的环境。本版是一次**全仓审计（十八轮）后的修复版**，
> 以**修 bug 与补判据**为主，无新功能；其中包含一条**发布面不可用的生产级缺陷**（见下）。
> **不升级的后果**：WASM 应用平台在编译缓存超上限后会**永久拒绝发布/校验**且不自愈；
> 商店技能可能被"更新"静默覆盖掉本地改动；随包技能被卸载后下次开机会自己装回来。

## 一、这一版修了什么（按"用户会怎么碰到"排序）

**1) 发布面与可用性（含一条生产现场 P0）**
- **WASM 编译缓存自锁**：磁盘编译缓存超过上限后，发布/校验闸门会一直 503，而回收只在编译作业之后跑 ⇒ 永不恢复。现在有周期回收 + 闸门命中"缓存超上限"时先同步回收再判，并新增"每个阻塞理由都必须登记自愈路径"的常设判据。
- **发布链守卫**：CI 触发器与"被钉住的步骤"现在不可被静默摘除（`if: false` / `continue-on-error` / 删 `push:` 之类会直接红）。
- **补丁实效**：`patches/` 若一处都没生效，门禁现在必然失败（旧行为只打一行 warning，且判据见证依赖 yarn 缓存）。

**2) 能力中心 / 技能库**
- 商店技能被本地修改后，"更新"不再静默整树覆盖用户改动；内置技能的"卸载"会持久生效（不再下次开机被装回）。
- 随包技能换入的临时目录挪到第二层私有目录（修掉窗口期内可能索引到"幽灵目录"的问题）；随包技能升版后溯源版本号不再停留在旧值。
- 版本先后语义收敛为一份算法 + 一份仓内共享语料（修掉"把降级当升级"的双端分叉）。

**3) 客户端宿主**
- 连接器对"永久拒绝"类 OAuth 错误不再无限重发；cron 在"应用关闭期间错过触发点"时现在可观测（不改触发时刻、不补跑）。
- 浏览器工具的预算不再被内部等待/排队吃掉（返回可读的具体错误）；深链打开应用与面板打开走**同一个**打开闸门。
- 回收器/账本/锁/临时文件若干处一致性与失败清理。

**4) 服务端与计费**
- 文件回收在"复检 → 上游删除"之间不再误删他人对象（引入世代号）。
- 模型取参、账本与明细切分、审计批写失败、余额对账读失败等若干处改为**确定序 / 如实报错**。
- 管理面路由守卫从"前缀字面量"改为命名空间级；审计保留策略现在有周期执行者。

**5) 工程与门禁（不直接影响用户，但决定以后能不能少踩坑）**
- 五轮审计共发现并在本版修复：6 P0（含一条生产现场 P0）+ 108 P1（逐轮：66/15/19/8/15，其中部分为门禁自身的判别力缺陷），以及数量更多的 P2/P3；每条修复都带回归用例与变异验证，且由**另一名子代理独立复审**。
- 对"假绿"（扫不到就当通过、只钉文本不钉能力、可空转的注入接缝、检测与计票共用一条通道）做了系统性收口；发布链新增三类"静默零发布"判据（tag 缺 `v` 前缀、tag 打在旁支、预发缺发布说明）。

**6) 打包面与第六轮审计（发布前最后一轮）**
- **macOS / Windows 安装包此前根本打不出来**（本版修好）：`build/assistedMessages.yml` 没有被 `build.files` 的正向清单覆盖，而 Linux 因为平台专属配置把应用根放宽成 `**/*` 而"看起来正常" ⇒ 只有 macOS/Windows 在打包末尾被 afterPack 拒包。本版补齐清单，并新增"必需项必须被正向清单覆盖"的**不跑打包**就能咬住的静态判据。
- **连接器凭据按（账号, 服务端）隔离**：同一账号切换到另一台服务端后，不再把上一台服务端的密钥交给同名连接器（内置浏览器的"填充凭据"读的是同一份目录，也一并跟随）。
- **用量保留策略不再整轮停摆**：单个月份分区删除失败只跳过该条并记录，其余到期月份照常清理（此前一条失败即中止整轮，且每个周期在同一处再中止）；清理"孤儿/错界"关系前先把它们实际持有的明细**并入补账**再删，不再静默丢金额。
- **额度发放与月报调度器**：补齐装配判据与运行状态出口（此后被摘掉会有判据变红；额度发放是唯一的自动发放路径）。
- **迁移文件形状自检**：版本号重复或文件名不合规现在会 fail-loud 并点名文件（此前重复版本号会在第二次启动时静默跳过其中一条迁移）。
- **OIDC 登录**：因"单 IP 在途流程配额已满"产生的拒绝不再计入失败预算（此前会把整个 NAT 出口二次封锁 5 分钟）。
- **能力中心 / 应用中心**：本机已安装、但当前账号在服务端看不到的技能，不再被推断成"已被管理员下架"并给出删除本机那一份的动作；归属不可证明时一律不出破坏性动作。冻结的应用对**发布者本人**重新可见并可自助解冻（其他员工仍然看不到，与"不存在"同形）；归属人名下的市场内容也出现在"我的"里（含已下架标记）。
- **门禁自身**：`advisory` 守卫改成登记制（含到期日格式校验，两条通道各自独立复核）、"守卫失败 ⇒ Gate 红"的唯一链路改成逐字 + 步骤体可失败判据、workflow 文件与登记表双向对拍、R2 发布的三处完整性校验补上按对象名注入的回归网；同时修掉一条**我们自己的守卫造成的常红**（把"零用例级 skip"套在 CI 上必然拿不到 bwrap 的 5 条端到端用例上）。
- **连接器的登录态续期**：会话中途令牌被服务端作废时，同一条连接上的并发 401 现在**合并成一次续期**（此前两条 401 会各自续期一次，对启用「刷新令牌轮换」的授权服务器会触发复用检测、把整条授权吊销，用户侧表现为随机的「重新认证后仍然 401」）。同一次续期结果会前移到当前会话持有的凭据视图，重试即用新令牌。

## 二、升级须知

- **数据库**：本版只有一条**只加列**的迁移（`gateway_files` 的世代号字段），不回填、不改写既有数据；回滚只需换回旧镜像（列留着无害）。
- **客户端**：与服务端版本需保持同代（0.1.6 线）。预发布 tag 只构建 beta 渠道；品牌渠道要等正式 tag。
- **运维**：如果你的环境里有"定期删编译缓存文件"的临时脚本，**升级后请停用** —— 新版本由进程内回收统一负责（直接删文件会与编译写并发）。人工清空请走 `/readyz` 指引或进程内回收入口。
- **运维（读数与锁语义）**：本版改了 `/readyz.usage_retention` 两处读数的含义（`last_round_at` 改为**结束**时刻、新增 `configured_months_known`），并让**计量写入路径**在自愈时执行 DDL（短时取 `usage` 的 `ACCESS EXCLUSIVE`）；接监控/告警的环境请按 **§七** 逐条核对一遍。连接器重建前的在途等待是**有界 5 秒**，超时后仍照常重建（§七 第 4 条）。
- **连接器需要重新授权一次**：凭据目录现在带服务端维度。升级前保存的凭据**不会被采用**（也**不会**被删除，原文件保留原处），请在客户端 → 连接器里对需要用的连接器重新授权一次。同一账号重新登录**同一台**服务端后凭据仍然保留；本地执行（stdin 命令）的审批记录同样按服务端隔离，换服务端后需要重新确认一次。
- **已知未修（本版仍然存在，均已登记）**：cron 在同进程换代时会把在跑的 run 记为 cancelled（与既有"封笔世代拒绝迟到结算"断言冲突，需产品拍板）；编译缓存上限仍是编译期常量（后台暂不可配，本版已让回收/水位不再依赖编译子系统）；`/readyz` 仍未鉴权（本版已把驱动错误原文从对外响应移出，只留分类与可 grep 的服务端日志）；两个新加运行状态的调度器（额度发放 / 月报）的运行读数目前只进启动与关停日志（未挂到 `/readyz` 或管理端，接缝已留好）；市场渠道的"我的"分区在**未装在本机**时不会显示自己拥有的市场行（服务端作者面已完备，客户端宿主侧仍是缺口）；门禁侧还有两条已登记的判据残余（`needs-result` 的步骤体只做语法级判定，`|| exit 1` 左侧恒成功时仍会绿；electron-shots 的"非空但错"的观测静态判据看不见，只有真机跑才判得了）。
- **连接器 401 恢复链的代价**：为了让 401 的续期走我们的单飞（避免刷新令牌被重复出示而吊销授权），交给传输层的凭据面不再声明动态注册能力 ⇒ 需要 step-up（403 `insufficient_scope`）或运行期动态注册的 MCP 服务器会以明确错误失败而不是静默降级；刷新请求本身失败时仍是「SDK 只重试一次」的窗口。
- **平台验证的边界**：macOS 与 Windows 的安装包构建已由 CI 在真实 runner 上跑通（本版修复的直接受益者），但**真机图形 E2E**（真实桌面交互、托盘、公证后双击）仍未在本轮验证。

## 四、第七轮与第八轮审计修复（同版本内继续收口）

本版在第六轮之后又跑了两轮独立审计（第七轮 0 P0 / 4 P1；第八轮 0 P0 / 8 P1，另加修复复审新增 2 P1），
两轮的发现**全部修完**并各自带回归用例与变异验证；其中三条 P1 是**上一轮修复自身**的回归面，已按同一判据重测。

**1) 用量保留与账本（服务端）**
- **多级分区（年 → 月 的中间父表）下不再误删活分区、也不再重复计账**：分区归属改按**分区树传递根**判定（此前只看直接父），
  并在删除前增加 fail-loud 预检；孤儿关系的补账不再把同一批明细算两遍。
- **多级布局覆盖当月时不再 503**：写入就绪判据同样改按传递根，月分区会建在**最深覆盖窗口的中间父表**下；
  端到端实测由 `503 METERING_FAILED`（当月对话全部不可用）变为正常交付。
- **保存保留期不再偶发 500**：并发/重叠清理轮次里"关系已被别人删掉"从失败改为良性（与同函数内既有的良性判定同口径）。
- **单个异常月不再拖垮整个窗口的账本自愈**：逐月隔离，坏月照旧 fail-loud 并点名，健康月照常补齐。
- **保留期内仍持有明细的非叶子关系不再被 DETACH/DROP**（按行事实判定），并在日志与状态里给出原因。
- **可观测性**：新增进程内保留状态并并入 `/readyz` 的 `usage_retention` 字段（轮次/失败轮次/跳过原因/未回收关系；
  不新增路由、状态码与响应头逐字不变）。

**2) 连接器（客户端宿主）**
- **401 续期不再被自己掐断**：续期成功后触发的"凭据已变更"事件此前会重注册**整条**连接器，从而关掉**正在重试的那条传输**，
  用户这次调用以 `Connection closed` 失败。现在该事件**只重注册 stdio 子集**（HTTP/SSE 传输由 provider 每请求读取活令牌）。
- **声明了自定义 `Authorization` 的连接器不再被误删该头**：只删除框架自己烘焙的那一枚（来源键控），并在注册期打一次可检索的 warn。
- 产物守卫补齐：随包传输桥的 `requestInit.headers` 与 `authProvider` **必须在同一处**（正反例都钉住）。

**3) 门禁与发布链（不直接影响用户，但决定"门禁还能不能信"）**
- **判据从"文本形态"改到"执行视角"**：被钉住的判据步骤现在有 **argv 钉子**（`--list`/`--help`/`--version`/`--dry-run` 等一律红）、
  **shell 钉子**（非 `bash`/`sh` 即红）与**覆盖下限**（登记的策略 id 少一个即红）；带根守卫命令被注释、收尾 `exit 1` 被注释、
  `exit 00`/`0x0`/`$((0))`、`exi\`+换行断词、`case …) exit 0 ;;`、函数定义包装、`shell: python`、workflow 顶层 `env:` 注入
  `--allow-advisory`、拼接字面量等形态**全部由"绿灯"变为"红灯"**（修复前逐一复现、修复后逐一判红）。
- **根守卫的 argv 与脚本名同级登记**（此前只校验名字）：把 16 条守卫的 argv 改成 `--version` 曾能让"16 个根守卫：16 通过"
  在 3 秒内零执行通过，现在直接判红。
- **渠道仓取源日志不再回显凭据**：脱敏正则跨不过 `/` 的缺陷已修（`user:pa/ssWORD` 曾原文进公开日志，而日志还宣称"不会回显"），
  且 **clone 路径**（生产真正走的那条）与回退 fetch 一并收进唯一出口；私钥落盘前先 `umask 077`；
  空白 `CI_CHANNELS_URL` 不再遮蔽可用的 deploy key；启动打印本次选用的凭据形态（不含内容）；git 输出钉 `LC_ALL=C`。
- **渠道集可静默缩小**的问题补了兜底下限（正式 tag 跌破即红、非 tag 告警）与权威清单双向对拍（私有仓提供清单时生效），
  并收紧 `CI_CHANNELS_PIN` 的形状判据（多行值不再能过）。
- `--require` 关键用例**绑包**、go 测试报告判定补**退出码矩阵**（0/1/2 三态）与**自检完整性下限**（自检样本被清空曾仍报"通过"）。

## 六、第九轮审计修复（同版本内继续收口）

第九轮（四路独立，绑提交 `06331a4884`）又发现 **1 P0 / 9 P1**，全部修完并各自带回归与变异验证：

- **发布链阻断（本次 tag 的第一次失败就死在它）**：上传用的 `aws s3api put-object --body "fileb://…"` 在现代 AWS CLI 上直接参数校验失败（实测 2.37.1：`file://`/`fileb://` 都被拒，必须给纯路径）。现改为纯绝对路径，并让仓库里的假 CLI 与真 CLI **同形拒绝**（单测不再掩盖契约），另加"上传前 1 字节探测"，把形态/端点/校验和问题挡在 500MB 上传之前。
- **连接器**：声明的 `Authorization` 解析为空时不再遮蔽服务端刷新的活令牌（此前会 4 次请求全空令牌且行状态仍显示已连接）；provider-backed HTTP 传输上的其它注册期请求头改为**每请求视图**（此前一次令牌轮换后永久 401，并每次失败多烧一枚刷新令牌）；`retire` 前等**在途非 GET 请求**归零（此前会掐断正在重试的调用）。
- **门禁**：判据面推进到**进程环境层** —— `NODE_OPTIONS`/`BASH_ENV`/`NODE_PATH`/`LD_PRELOAD` 等能让"永不跳过"的根守卫作业静默变绿（真跑会打印"16 通过/0 失败"而守卫实际在失败）；同时把守卫步骤与发布链步骤改**命令位**判据、`trap` 动态动作 fail-loud、`shell:` 整串登记。三条上一轮新引入的误报也已复绿。
- **服务端**：保留期清理的"读—判定—删"竞态会在判定后把**已提交**的计量行连带删掉（明细与账本双失），现在整段收进事务并**持锁复检**（拿不到锁即 fail-loud 全回滚）；多级分区下"声明边界 ≠ 有效边界"会让**当月每一次对话 503**，现改用有效边界；祖先被 DETACH 后遗留的同名孤儿会被**单事务领回**（领不回则结构化报错 + `/readyz` 可读的写入阻塞状态）。

## 七、第九轮的行为变更登记（升级与运维视角）

上一节（§六）写的是"改了什么"，这一节写**升级后你会看到什么** —— 四条**行为/读数语义**变化，
都已随本版生效；每条给出"谁会受影响 / 观察到什么 / 要不要动作"。它们本身不是缺陷，但如果
你的监控、告警阈值或运维脚本按旧口径写死了，就会读错。

**1) `/readyz.usage_retention.last_round_at` 的语义：从"本轮开始时刻"改成"本轮结束时刻"**

- **谁会受影响**：把 `usage_retention` 接到监控上的环境，尤其是用"距上一次轮次多久"来判断
  保留清理调度器是否卡死的告警（`now - last_round_at > <轮次预算>`）。
- **观察到什么**：同一个字段现在写**本轮跑完**的时刻。正常轮次是毫秒级，读数整体后移一个
  "轮次时长"；如果某一轮长时间阻塞（例如清理撞上锁竞争），读数**不再**提前跳到本轮的开始时刻 ——
  这正是改动目的：它要与 `rounds`/`failed_rounds` 一起回答"调度器还活着吗"，写开始时刻会答错。
- **要不要动作**：按"结束时刻"重新评估一次轮次预算类阈值（一般无需改数值）；字段名、出现条件、
  其余字段都没有变。

**2) `/readyz.usage_retention` 新增 `configured_months_known`**

- **谁会受影响**：读 `configured_months` 判断"保留期是否开着"的监控。
- **观察到什么**：多一个布尔字段 `configured_months_known`，回答"这个 `configured_months` 是
  **观测值**还是**零值**"。此前两种含义共用一个字段：本域里 `0 = 永不删除`，而进程跑过第一轮
  之前（或某一轮读不到生效保留期时）它**也是** `0`；失败轮次不再把观测值覆盖成 0，而是保留上
  一次的观测值并由 `failed_rounds`/`last_error` 表达。
- **要不要动作**：把"保留期被关掉"的告警条件从 `configured_months == 0` 收紧成
  `configured_months_known == true && configured_months == 0`。老监控不改不会误报，只是仍可能把
  "还没跑过第一轮"读成"保留期关闭"。

**3) 计量写入路径现在会执行 DDL，并短时取 `usage` 的 `ACCESS EXCLUSIVE`**

- **谁会受影响**：跑多级分区布局（年 → 月中间父表）或曾被人工 `DETACH` 过 `usage` 子树的环境；
  以及对计量写入延迟敏感（有 P99 写入延迟告警）的环境。
- **观察到什么**：当月分区缺失时，**写入路径**不再直接以 503 `METERING_FAILED` 失败，而是自愈 ——
  普通情况建分区；"同名孤儿"（分区随祖先被 `DETACH` 摘走、名字仍占着当月分区名）则在**一个事务**
  里 `DETACH` + `ATTACH` 领回。PG 的 `CREATE/ATTACH/DETACH PARTITION` 需要父表 `usage` 的
  **ACCESS EXCLUSIVE** 锁 ⇒ 自愈那一刻，**并发的计量写入会短暂排队**（毫秒级；锁持到 DDL 事务
  提交为止），随后照常落账。自愈失败仍是 fail-loud：结构化错误 + `/readyz` 的
  `write_blocked`/`write_blocked_month`/`write_blocked_kind`/`write_blocked_error`/
  `write_blocked_action`，该月每一次对话仍按原语义 503 且不交付。
- **要不要动作**：不需要。如果写入延迟告警对毫秒级尖刺敏感，把"分区自愈"那一次纳入采样窗口/
  白名单。**不要**改回"写路径不做 DDL"：那等于回到"该月永久 503 且所有观测面报绿"。
  （此前恒 503 的月份现在会自愈；"失败即不可写"没有被弱化，只是变得可见。）

**4) 连接器重建前的在途等待是"有界 5 秒"（超时后仍照常重建）**

- **谁会受影响**：用 HTTP/SSE 传输的 MCP 连接器（stdio 子进程不走这条路径），以及会更新凭据、
  重新注册的连接器。
- **观察到什么**：重建传输前会等**在途的非 GET 请求**归零，上界 **5 秒**；超时后**仍然按新凭据重建**，
  并留一条可检索的 warn（"重建等待在途调用超时（5000ms），仍按新凭据重建"）。也就是说
  "被掐断"的残余窗口**仍然存在**（几微秒的起步窗口 + 超过 5 秒的长调用），只是从"必然掐断"变成
  "有界等待后仍可能掐断"，两种情形都留日志。
- **要不要动作**：不需要。若某个连接器有**单次超过 5 秒**的调用，凭据轮换触发重建时那次调用仍可能
  以 `Connection closed` 失败 —— 重试即可；这属于本版明确认账的残留，不宣称"绝不掐断"。

## 八、第十轮的行为变更登记（客户端 · 与 §七 同口径）

第十轮（客户端与宿主面）又收口了一批连接器出站头与技能打包的边界。其中四条会让**升级后你看到
的行为发生变化**（§七 登记的是第九轮四条，本节补第十轮；每节只写"你会看到什么"）。

**1) 只写了方案词的 `Authorization` 不再当凭据发出去**

- **谁会受影响**：连接器定义里把 `Authorization` 声明成**裸方案词**（`Bearer` / `Token` / `Basic` /
  `ApiKey` / `JWT` / `SSWS` 等）的环境 —— 这类声明没有携带任何凭据，以前会被原样发到 MCP 端点。
- **观察到什么**：该槽位不再按"声明的凭据"发送——有 provider（OAuth/令牌）时由框架填 `Bearer <活令牌>`；
  **凭据里没有访问令牌**（只配了静态字段）时，这条头**整条被删除**（不再发出 `Authorization: Bearer`）。
  真正的凭据照旧**逐字**上线：`abc123`、`sk-…`、`Token abc123`、`ApiKey ${K}` 都不受影响。
- **要不要动作**：如果某个端点在靠"能收到一个 `Authorization` 头"来判活（而不是判令牌），请改为
  按连接器的连接状态判断。配错字段名（声明了 `${API_KEY}` 而凭据里没有该字段）现在也是同一结果：
  该头被删，并在连接器面板留一条可检索的 warn。

**2) 同一个 HTTP 头的两种大小写拼写只发一条**

- **谁会受影响**：定义里用不同大小写写了同一个头（例如框架注入 `Authorization: Bearer …`，
  定义又声明了 `authorization: ''`）的环境。
- **观察到什么**：头名按 HTTP 语义归一成**一个槽位**，线上只会出现**一条**该头（此前可能出现两条、
  或被合并成 `A, Bearer …` 这种两端都解析不了的值）。大小写不同的**不同**头（`X-Probe` 与
  `X-Probe-Key`）不受影响，仍是两条。
- **要不要动作**：不需要，除非你的端点在依赖"重复头"这一（不规范）事实。

**3) 声明的 `__proto__` 头由"静默消失"变成"显式拒收 + 可检索 warn"**

- **谁会受影响**：定义里恰好声明了名为 `__proto__` 的头（历史上它会被 JavaScript 赋值语义吞掉，
  既发不出去也没有任何提示）。
- **观察到什么**：注册期多一条可检索的 warn（`[unsupported-header] … 声明的头 __proto__ 无法表示，
  已拒绝发送`）；连接器本身照常可用，其余头照常发送。名字形如 `constructor` / `toString` 的头是
  **普通头**，正常发送、也会随凭据更新正常过期。
- **要不要动作**：不需要。看到这条 warn 说明该声明从来就没生效过。

**4) 技能目录是符号链接时，上传被拒收（此前会被打包）**

- **谁会受影响**：技能库里用 `ln -s` 指向别处的"技能"（包括指向**库内另一个真技能**的别名）。
- **观察到什么**：打包（上传到能力中心）现在 fail-loud，文案点名符号链接；技能库**根目录本身**是符号
  链接的部署（合法的挂载/家目录布局）不受影响，照常打包。技能列表本来就不列符号链接条目，所以失去的
  只是一个从未在界面上出现过的上传路径。
- **要不要动作**：把别名换成真实目录（复制或改技能库根指向）。**认账残量**：技能目录内的**硬链接**
  与普通文件在路径上不可区分，打包期的落点断言管不到它（需要本机写权限才能造出，且 `realpath` 结构性
  修不了）；`nlink > 1` 的逐文件拒收会误伤正常部署，本版不做。

**5) 连接器重建前"在途等待"的记账作用域：从"按端点"收到"按正在被换掉的那条传输"**

- **谁会受影响**：同一个 MCP 端点上有**不止一条**传输的环境（同一连接器的多个 server，或多个连接器
  指向同一端点）且会轮换凭据。
- **观察到什么**：一条传输重建时**不再**把同端点其它传输的在途记账一起清掉（此前会让另一条传输的
  下一次重建误判"没有在途调用"而提前掐断它本可在等待窗口内结算完的调用）。代价是：当端点上确实还
  有其它传输时，重建**不会**因为"等待超时"而丢弃记账，于是那次等待会在后续重建里再发生一次，直到
  在途调用结算或到达 120 秒（MCP 调用的工具预算）为止 —— 宁可多等一轮，也不误伤别人正在返回的调用。
- **要不要动作**：不需要。单传输（绝大多数部署）行为不变。

## 九、第十一轮的行为变更登记（服务端读数 · 客户端 · 门禁）

第十一轮是"把判据面推进到**执行体的入口**（谁把门禁跑起来）"的一轮。其中五条会让升级后
（或本地开发时）你看到的行为/读数发生变化。§七 登记第九轮四条、§八 登记第十轮五条，
本节补第十一轮；口径与前两节一致：**只写"你会看到什么"**。

**1) `/readyz.usage_retention` 新增三位，"停摆"从一位变两位**

- **谁会受影响**：把 `usage_retention` 接到监控/告警上的环境 —— 尤其是"保留策略是不是停摆了"
  那条规则，以及在**重启比一天一次更频繁**的部署上设计过告警时间线的环境。
- **观察到什么**：对象里多出三个字段 —— `reclaim_stalled`（布尔）与它的一对推导基准/读数
  `oldest_unreclaimed_due_since`（最早那个未回收的到期月**从哪一刻起就该被回收**）、
  `oldest_unreclaimed_age_seconds`（到本轮结束为止已逾期多少秒）。
  `reclaim_stalled=true` 的判据是"最早未回收的到期月已经逾期 ≥24 小时"，它由 catalog 事实 +
  保留期**推导**（纯函数）⇒ **重启后的第一轮就有值**。既有的 `deferred_stalled` 语义**不变**
  （"同一关系连续 ≥5 个调度轮次、约 24h，既没回收也没真失败"），它仍依赖进程内累积、重启归零。
  两位**故意不合并**：既有的"管理端连点保存保留期不得造成分钟级假告警"契约原样有效。
  运维口径因此是 `deferred_stalled || reclaim_stalled`。
- **要不要动作**：把"停摆"告警条件改成 `deferred_stalled == true || reclaim_stalled == true`；
  要"逾期多久"就直接读 `oldest_unreclaimed_age_seconds`。三个字段都是**增量**，其余字段名、
  出现条件与当月写入面的语义一字未改；它们在 `false`/`0`/空时**不出现**（JSON 省略零值），
  所以规则要按"缺省即 false"写（`!= true`，别写成 `== false` 的严格比较）。

**2) `write_blocked_other_months` 从"单向棘轮"变成"当前仍未解决"的读数**

- **谁会受影响**：用 `/readyz` 判"有没有某个月写不进去"的监控（尤其"新出现即告警、一直不消失就升级"）。
- **观察到什么**：非当月写入面的条目现在会**自己消失**，两条收敛判据：①该月**后来写成功**了；
  ②该月的关系**已不在本轮的 catalog 枚举里**（已被回收/删除，写入阻塞这件事没有载体了）。
  此前只有 ①，而被布局阻塞的恰恰是**到期月** —— 写路径只写当月，所以那些条目**永久残留**，
  "列表非空 ⇒ 有月份写不进去"变成一次历史事件之后永远为真（最多靠 12 个月滚动自然淘汰），
  "新出现即告警"因此失效。关系仍在的条目**一律保留**（那才是"现在还有个月写不进去"的真实读数）。
- **要不要动作**：不需要。`write_blocked_other_count`（累计次数）不受影响，趋势/复盘用它。
  当月面 `write_blocked_*`（"当月每一次对话 503"）的语义与告警口径**不因它改变**。
  附一条边界：这类收敛只在"**有证据轮**"（本轮真的枚举到过 catalog）执行，扫描失败的轮次
  不做任何猜测。

**3) `NODE_OPTIONS` 由"按名字拒跑"改成"按内容拒跑"（门禁与本地开发）**

- **谁会受影响**：在本地或 CI 里给门禁设过 `NODE_OPTIONS` 的人。
- **观察到什么**：只有**登记在案**的纯 GC/打印面旗标（`--max-old-space-size=…`、
  `--max-semi-space-size=…`、`--max-http-header-size=…`、`--stack-size=…`、
  `--stack-trace-limit=…`、`--heapsnapshot-near-heap-limit=…`、`--v8-pool-size=…`、
  `--no-warnings`、`--enable-source-maps`、`--trace-warnings`、`--disable-warning=<码>`）
  会被放行并**原样传给每个包**的构建/测试进程；任何一个未登记的旗标（`--import`、`--require`、
  `--loader`、拼错的名字、含引号/空格而被切碎的取值）都会让编排器**拒绝运行**：打印
  "拒绝运行 —— 本进程自己的环境里有…"并随后结束，**不打印通过凭据**（CI 侧以那一行为准，
  不以退出码为准）。此前判据落在**键名**上：`NODE_OPTIONS` 只要非空就算危险，于是
  "给门禁加堆内存"这种正当用法也直接红 —— 而危险形态与正当形态在同一个键里，判据必须落在旗标上。
- **要不要动作**：`NODE_OPTIONS=--max-old-space-size=4096 corepack yarn check` 照常可用；
  看到"拒绝运行"就清掉那个未登记的旗标（例如 `env -u NODE_OPTIONS corepack yarn check`），
  不要去放宽判据。

**4) `.yarnrc.yml` 与安装期钩子进登记制（开发流程）**

- **谁会受影响**：往 yarn 里塞插件/换 yarn 本体、或往根 `package.json` 加安装期钩子的人。
- **观察到什么**：`.yarnrc.yml` 现在**被门禁读内容**（顶级键白名单 + `enableScripts`/`nodeLinker`
  取值判据 + 内容摘要登记）；`yarnPath` 与 `plugins` **出现即红**；根 `package.json` 的
  `preinstall`/`install`/`postinstall`/`prepare`/`prepublish`/`prepublishOnly`/`prepack`/`postpack`
  进登记制（当前登记为空 = 禁新增）；`.yarn/plugins/**` 与 `.yarn/releases/**` 必须为空。
  为什么连"能不能加个插件"都要管：这类入口在 **yarn 进程内部**往每个被 spawn 的脚本环境写
  `NODE_OPTIONS`/`BASH_ENV`，注入发生在根守卫的环境清洗**之后** —— 实测在 workflow 一字未改的
  前提下，`corepack yarn check` 可以从 EXIT=1 变成 EXIT=0、根守卫从"3 通过/14 失败"变成
  "17 通过/0 失败"。守卫本身也不再经 yarn 启动（CI 直接 `node scripts/check-root-guards.mjs`）。
- **要不要动作**：不要往仓内加 yarn 插件或换 yarn 本体；安装期钩子确有需要时先按登记制登记
  （登记表与理由都在 `scripts/check-guard-parser-integrity.mjs`）。本地**未提交**地改这些入口文件时，
  "摘要锚到 HEAD"的那条只在 CI 上硬判、本地只是告警（认账的代价：本地脏树与攻击态在判据的输入面
  上不可区分），所以提交前请把工作树清干净。

**5) 客户端：连接建立期落地的令牌刷新，现在也会写到"传输真正读的那条记录"**

- **谁会受影响**：用 HTTP/SSE 传输的 MCP 连接器 —— 尤其是"打开客户端 / 重连时正好赶上令牌临期，
  后台心跳或连接器面板刷新落在**连接建立过程中**"的场景（开机恢复就是最常见的那一次注册）。
- **观察到什么**：那一刻落地的刷新以前会被吞掉 —— 传输带着**已被替换的**旧令牌上线，注册以
  `重新认证后仍然 401` 收场，而连接器面板的行状态**可能仍显示已连接**（用户看到的是"连上了但
  工具调用全 401 / 需要重新授权"）。现在刷新会写到这条注册**真正读取**的那条记录上；同一份记录
  在 `already in use`（上一世代实例占着名字）重试路径上也会被重新发布。
- **要不要动作**：不需要。这是客户端侧的行为修复，无需改配置。升级后仍遇到 401 时按 §一/§二 的
  判据区分：`缺少认证令牌` = 请求没带 `Authorization` 头；`令牌无效或已过期` = 登录态本身失效。

**6) 门禁的"通过凭据"口径：只看那一行，退出码不再是凭据；失败行按 `\r` 分段**

- **谁会受影响**：读 CI / 本地门禁日志判断"到底过没过、失败在哪"的人，以及写脚本 grep 这些日志的人。
- **观察到什么**：① 判定权上移到父进程/CI —— **不看退出码、只认行首锚定的通过凭据**
  （`check-workspaces: VERDICT PASS planned=<N> executed=<N>`、`check-root-guards: VERDICT PASS
  guards=<N>`；N ≥ 1）：被拒绝运行、零守卫、以及"判决不可信"的进程都**打印不出**这一行，
  而它们照样能退出 0。② 失败行按 `\r`（光标回第 0 列）**切段**后逐段判定，所以用进度条
  `\r` 覆盖输出的构建/测试工具再也藏不住失败行。③ 判定形态表（`VERDICT_LINE`）从"行内任意
  位置匹配"改成行首锚定，并要求把形态**登记**进去（表被掏空或出现未登记形态即 fail-loud，
  提示是"补登记形态"而不是"放宽匹配"）。
- **要不要动作**：如果你的工具按"一行一条失败信息"解析这些日志，改成先按 `\r` 分段、每段各自
  从第 0 列开始匹配；判断门禁是否通过时请检查那一行凭据（行首锚定），不要只看退出码。

## 十、第十二至十八轮的行为变更登记（服务端 · 客户端 · 门禁）

§七–§九 分别登记第九/十/十一轮；本节补齐**第十二至十八轮**（本文件此前停在第十一轮，而那七轮里
有三条**客户可见**的行为变更从未登记）。口径与前几节一致：**只写"你会看到什么"**。

**1) 未定价模型：从"按 0 计费"改成"缺省拒绝调用"（客户可见，本版最重要的一条）**

- **谁会受影响**：模型目录里存在**未配置价格**（或价格 0）的模型的部署 —— 常见成因是渠道同步建出的
  NULL 价行，或管理员新增模型后忘了填价。
- **观察到什么**：这类模型的请求在缺省策略下返回 `429 MODEL_NOT_PRICED`，**不转发、不产生费用记录**；
  此前它们"照常调用、费用按 0 记"（组织付上游的钱、平台零计费零痕迹）。
  另有两条同族判据：**输入价 0/极低但输出价正常**的模型**照常可用**（按输出侧计费，本版修正了上一轮
  把它们一律拒绝的回归）；**这次请求的最小应付额折到账本最小单位（1 微元）仍为 0** 的请求同样被拒
  （否则结算落 0 微元、余额一分不减、可无限重复）。
- **要不要动作**：给真实计费的模型补价；确实是免费/内部模型时，由管理员显式把
  `gateway.unpriced_model_policy` 设为 `allow`。⚠️ 该开关是**全局**的：同名模型挂在多个上游渠道、
  其中只有一家缺价时，会让落到那家的请求也按 0 计费 —— 更稳的做法是给缺价渠道补价或停用它。

**2) 删除已安装的能力内容：跨根同名 ⇒ `422 RESIDUE`，本地有改动 ⇒ `409 LOCAL_CONTENT`**

- **谁会受影响**：在客户端卸载技能/智能体的员工 —— 尤其是技能库里存在**项目级/用户级同名副本**，
  或本地内容被自己改过的环境。
- **观察到什么**：卸载不再无条件成功。同名内容还存在于更高优先级的技能根 ⇒ `422 RESIDUE`
  （如实列出条目名与所在根，需先处理那一份）；本地内容与安装时不一致 ⇒ `409 LOCAL_CONTENT`
  （需要确认覆盖 `?overwrite=1` 才删）。客户端会如实显示服务端 message，不谎报成功。
- **要不要动作**：按提示处理更高优先级的那份副本；确认要丢弃本地改动时再点覆盖。

**3) 网关文件删除与批量清理：新增两条 `409` 与 `skipped` 计数（管理面/开放面）**

- **谁会受影响**：调用 `DELETE /files/:file_id`、`DELETE /api/server/admin/gateway/files/:file_id`
  或 `POST …/gateway/files/purge` 的集成方与管理端。
- **观察到什么**：删除**必然先取得认领**（回收器/另一个删除者持有租约时不再"照样删上游对象"）：
  租约内 ⇒ `409 FILE_BUSY`（对象与行原样保留，刷新后重试）；删除窗口内该行被重新登记 ⇒
  `409 FILE_RECLAIMED`（上游对象已删，台账行留给新的上传者）。批量清理的响应新增
  `skipped`（有意不删的条数：持有权冲突 / **快照之后被续期或转手** / 行已被别的路径收敛），
  且快照现在**带世代号** —— 清理循环期间被主人合法续期的**有效文件不再被误删**。
- **要不要动作**：按 `409` 的语义重试（`FILE_BUSY` 可稍后重试；`FILE_RECLAIMED` 不要重试）；
  解析 purge 响应时把 `skipped` 与 `failed` 分开统计。

**4) 月报订阅的重试节奏与跨月口径（管理面读数）**

- **谁会受影响**：配置了月报 webhook 且推送会失败的环境。
- **观察到什么**：失败后不再"每小时重投同一期，直到成功"（那会让永久坏的 webhook 每天被重投
  24 次/实例）。现在是**首次失败后 1 小时重试一次、之后每天一轮**；失败的那一期被**记住**
  （`pending_period`），**跨月也继续补投它**（此前会静默跳到最新一期，被跨过的那期永不投递）。
  多实例部署下同一期只投一次（投递前按订阅取数据库认领）。
- **要不要动作**：不需要。若你的告警依赖"每小时必然有一次重试"的节奏，按新节奏调整。

**5) 可信反向代理的缺省值：从"硬编码 Caddy 地址"改成"从 `CADDY_IP` 派生"**

- **谁会受影响**：改过 compose 私有网段（`NETWORK_SUBNET` / `CADDY_IP`）的部署 ——
  尤其是只改了 `CADDY_IP` 却没同步 `PICOAI_TRUSTED_PROXIES` 的环境。
- **观察到什么**：启动日志新增一行 `trusted proxies: source=… list=…`；未显式配置
  `PICOAI_TRUSTED_PROXIES` 时它**从 `CADDY_IP` 派生**（改网段只需改一处）。显式配置与
  `CADDY_IP` 不一致时，启动期多一行 `WARNING`（改网段只改一个 = `X-Forwarded-For` 静默失效、
  登录/MFA/OIDC 限流桶坍缩成全组织共桶）。
- **要不要动作**：若你曾显式把 `PICOAI_TRUSTED_PROXIES` 写成固定 IP 且随后改过网段，请核对那一行
  （共享反代部署 —— 宿主机另有 Caddy/nginx —— 的显式值保持原样即可）。

**6) 后台循环的可观测面：模型同步与 LDAP 目录同步进状态表**

- **谁会受影响**：把启动/关停日志或调度器状态接到监控的运维。
- **观察到什么**：启动与关停的 `scheduler status` 行新增 `model_sync` 与 `directory_sync` 两项
  （此前它们既不在状态表里，也没有 ctx/停止信号）；两者都随进程 ctx 退出，关停日志给出
  `runs`/`errors`/`last_error`。
- **要不要动作**：不需要。

**7) 运维面：`input price 0 + output price > 0` 的模型不再被误拒；`allow` 策略的语义与作用范围**

- 同 §十 第 1 条的"要不要动作"，此处只是再次强调：**`allow` 是全局逃生门**，不是"按模型白名单"。
  需要按模型放行属于后续版本的产品决策。
