# PicoAide Harness v2.6.9（2026-09）

本版本核心是**交付与升级方式的架构改造**：服务端与客户端**同包发版**（客户端安装包随服务端镜像分发），
更新通道从 GitHub Releases 迁到**自有更新服务器**，部署与升级改由**一份给 AI 代理执行的说明文档**驱动。

---

## 一、客户端与服务端同包发版 ⭐

- **客户端安装包打进服务端镜像**：三平台安装器（Windows NSIS / macOS DMG / Linux AppImage+deb）由 CI 三平台 job 产出后随镜像发布，镜像启动后由 entrypoint 落到持久卷 `/data/releases/<版本>/client/`；
- **客户端升级源 = 它登录的那台服务器**：客户端从服务端取包（`GET /api/client/v2/updates/manifest` + `/updates/client/<file>`，支持断点续传），企业内网员工机器**不需要访问任何外网**；
- **版本错配在结构上不可能发生**：客户端包物理存在于服务端镜像中，服务端不升级、客户端就保持配套旧版；升级服务端即同时升级客户端；
- `client.version == server.version` 由 CI 强制断言（`scripts/version.mjs` 同源），防止"镜像里的客户端"与"镜像版本"漂移。

## 二、更新通道迁至自有更新服务器

- **彻底移除 GitHub Releases 更新通道**：匿名 API 限流（60 次/小时/IP，企业出口共用一个 IP 必然触发）与国内不可达是两个绕不过去的硬伤；
- 服务端 `updatecheck` 改为只读自有更新服务器 `https://update.picoaide.com`（Cloudflare R2 静态对象）的版本清单 `latest.json`；渠道用 `PICOAI_UPDATE_ENDPOINT` 指向自己的目录，`off`/`none` 可关闭检查；
- webadmin「服务器信息」页的"发现新版本"横幅现在显示**升级目标镜像 tag**与更新清单来源；
- 客户端 `update-checker` / `update-download` 同步改为清单协议（安装包地址与 SHA-256 均来自清单），移植期后不再有 GitHub 资产名匹配与独立 `SHA256SUMS.txt` 旁路；
- **更新服务器必须直接返回 200**：检查请求显式拒绝重定向（`redirect: 'error'`），避免前置跳转把"通道断了"伪装成"没有新版本"。

## 三、渠道隔离（beta / 官方 / 品牌互不升级）

- **三种渠道类型**：`beta`（预发布，我们自己内测）、`official`（正式）、`<brand-id>`（企业定制）；
- **清单强制声明 `channel_id` 且必须与本安装所属渠道精确相等**：缺失或不匹配一律拒绝。混渠道最坏的后果是品牌客户端接受官方清单、升级后被"洗"成官方版、品牌丢失 —— 因此这是**正确性校验**，不是配置项；
- 客户端 `checkForUpdate` / `downloadDesktopUpdate` 均要求 `channel`，默认 base 由渠道推导（`release.picoaide.com/<channel>`）；服务端 `updatecheck` 同样校验，不一致时报"检查不可用"而非"无更新"（让人看见并修，不静默跨渠道升级）；
- 服务端部署新增 `PICOAI_CHANNEL`；与 `PICOAI_UPDATE_ENDPOINT` **都留空**时会从端点路径首段推导渠道，三处配置（渠道 / 端点目录 / 清单 channel_id）因此默认自洽；
- **品牌渠道发布故意 fail-loud**：CI 目前只支持 `beta`（含 `-beta`/`-rc`/`-alpha` 段的 tag）与 `official`（纯 `vX.Y.Z`），其他 tag 直接失败并提示原因 —— 静默发成官方比"发不出去"严重得多。品牌渠道依赖尚未实施的渠道配置包管线。

## 四、部署方式改为 AI 执行说明

- **移除全部部署脚本**：`server/scripts/deploy.sh`、`server/scripts/install-server.sh` 与 `make release-export` 已删除；
- **唯一交付物 = 一个镜像 + 一份说明**：镜像内自带 compose、Caddyfile（三证书模式模板）与客户端安装包，一条命令即可导出到部署目录：
  ```bash
  docker run --rm -v /opt/picoaide:/out -e PICOAI_UNPACK_STACK=/out \
    ghcr.io/picoaide/picoaide-harness-server:v2.6.9
  ```
- 部署说明 [`docs/deploy/AI-DEPLOY.md`](https://github.com/picoaide/picoaide-harness/blob/master/docs/deploy/AI-DEPLOY.md)
  含首次部署、升级、回滚、排障、执行清单与**四条数据安全铁律**（禁止 `down -v`；禁止 `latest`；升级前必须备份；不得覆盖已有 `.env`），可直接交给 AI 代理执行；
- 说明中的部署、备份、升级、回滚流程已在真实 compose 栈（caddy + server + postgres）上端到端实测通过。

## 五、修复

- **`TLS_MODE=internal` 从未真正可用**（P0）：compose 拼接的挂载源是 `./Caddyfile.internal`，而 internal 模式的模板文件名实际是 `Caddyfile` —— caddy 容器创建即失败，且 Docker 会在宿主上创建一个同名目录。三种模式现统一为 `Caddyfile.<mode>`（`Caddyfile` → `Caddyfile.internal`）；
- 镜像构建必须显式声明 `ARG VERSION`（ARG 不跨构建阶段继承，否则镜内 `VERSION` 文件为空）；
- 客户端取消更新时不再被归类为"网络错误"（清单阶段与安装包阶段统一按 `aborted` 上报）。

## 六、升级提示

- **服务端**：可出网时 `docker pull ghcr.io/picoaide/picoaide-harness-server:v2.6.9`；GHCR 不可达时从更新服务器下载镜像压缩包后 `unzip -p 包 image.tar | docker load`，随后按部署说明升级（**升级前必须备份**）；
- **客户端**：安装包随本次服务端镜像发布；服务端升级后，客户端会在下次检查时提示升级到配套版本；
- **Release 附件**：本版本的 GitHub Release 附件为**服务端镜像压缩包**（`picoaide-server-<版本>-amd64.zip` + `SHA256SUMS`）——更新服务器只保留最近 3 个版本，更老的镜像以 GitHub Release 为长期存档；
- 客户端安装包下载与首次安装：见 [Releases](https://github.com/picoaide/picoaide-harness/releases/latest) 或直接问它登录的那台服务端要包；
- **更新面域名**：`release.picoaide.com`（与路径 `/<channel>/releases/<版本>/` 同名；旧称 `update.picoaide.com` 未使用，无需迁移）。
