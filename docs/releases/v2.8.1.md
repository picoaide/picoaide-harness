# v2.8.1（2026-09-23）

> 一句话：修掉「客户端打开对话即认证失败」（每个模型请求都返回
> `401 缺少认证令牌`，重新登录无效）的现场事故，并补齐服务端网关的 Files API、
> 容量与限流口径。**使用 v2.8.0 客户端的部署必须升级客户端** —— 该问题一旦触发，
> 模型链路整条报废，且服务端升级救不了旧客户端。

## 访问模型变更（升级必读）

### 客户端不再使用系统代理（本版新增的默认行为）

- **变化**：桌面客户端**一律直连**，不再使用系统代理设置、代理环境变量
  （`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NODE_USE_ENV_PROXY`）、PAC/WPAD 自动发现，
  也忽略命令行 `--proxy-server`。覆盖范围包括客户端主窗口、内置浏览器、应用窗口、
  客户端的 Node 进程，以及它派生的子进程（AI 执行的 `curl` / `git` / 连接器 stdio 子进程）。
  本机自身的界面通信仍走本地回环，不受影响。
- **为什么**：此前宿主机上的代理配置会静默改变客户端的出网路径 —— 让企业内网的
  流量审计、证书固定与出站策略在不同机器上表现不一致。直连是**确定**的行为，
  代理选择交还给运维在网络层决定。
- **不受影响**：登录、模型请求、连接器、内置浏览器、应用窗口的**功能**都不变；
  变的只是"流量从哪里出去"。本机回环、局域网直连、以及不依赖代理即可出公网的部署
  完全无感。
- **受影响**：**只有经代理才能访问服务器或上游模型的部署**。这类部署必须启用退路
  （见下），否则客户端升级后连不上服务器。
- **退路（随包生效，不依赖服务端下发，两者取其一）**：
  1. 渠道包中设置 `desktop.allow_system_proxy: true`（随安装包分发）；
  2. 在**真实进程环境**中设置 `PICOAI_ALLOW_SYSTEM_PROXY=1`。
  ⚠️ 写在数据目录的 `.env` 分层里**不生效**（该文件加载太晚）；客户端启动日志会明确
  打印代理策略（`proxy direct` 或 `proxy system/<来源>`），并在此情形下提示该开关已被忽略。
- **服务端与客户端是否必须同版本**：**建议同版本升级，两端本版都有改动**。
  服务端接口保持向后兼容，旧客户端仍能登录与调用；但**旧客户端（v2.8.0）不会获得
  第一节的 401 修复**。反之，只升级客户端不升级服务端也可用（服务端本版改动是
  超时/容量/文件能力，不影响旧行为）。
- **不需要的旧配置**：客户端侧原有的代理相关环境变量与启动参数**不再需要**，可以清理；
  若此前为绕开代理而配置过例外，升级后同样可以清理。

## 一、客户端「打开对话即认证失败」：每个模型请求 401（本版起因）

- **现象**：客户机上打开客户端与 AI 对话，每个模型请求都返回
  `401 {"error":{"code":"AUTH_REQUIRED","message":"缺少认证令牌"}}`；
  **重新登录无效**，换会话、重启客户端都无效；客户端界面本身能正常登录。
- **影响**：模型链路整条报废（客户端可用但"不能聊天"）。触发它的是一组**条件组合**，
  现场已实际发生；只要命中，就会长期存在且不会自愈。
- **根因（三层缺一不可）**：
  1. **协议默认值变了**：本产品所用的上游在 0.1.6 线给模型适配器新增了
     `protocol` 配置，**缺省值是 `messages`**；该协议路径只发 `x-api-key`，
     **不发 `Authorization`**。而本产品的网关只认 `Authorization: Bearer …`，
     于是每个请求都缺凭据。
  2. **旧设置里没有这个键**：数据目录的 `settings.yaml` 是上一代客户端写的，
     从来没有 `protocol` 这个字段 —— 于是缺省值生效。
  3. **本该修好它的那次写入被挡住**：客户端里唯一会写入正确协议的是运行期的设置同步，
     它需要**写盘**；而数据目录里残留了一个**0 字节的写锁孤儿**
     （`settings.yaml.lock`），上游的原子写**故意不删别人的锁**，于是此后每一次设置写入
     都以"等待写者锁超时"失败，异常被各插件吞进日志 ⇒ "本该修好链路的那一行"永远写不进去。
     佐证：`settings.yaml` 的修改时间停在事故前一天，而同目录的凭据文件照常更新。
- **修复**：
  1. **协议在组装期钉死**（不经过任何落盘）：客户端的组合配置直接声明
     `protocol: chat-completions`，与设置解析同源。即使设置再次写不进去、即使运行期同步
     整条失效，模型请求依旧携带 `Authorization: Bearer`。
  2. **启动期回收孤儿写锁**（见第五节），让"设置静默变成只读"不再永久。
- **验证**：门禁里同时钉住三件事 —— 上游缺省值确实是 `messages`（证明这层 pin 为什么必需）、
  组装结果深等 `{protocol: chat-completions}`、以及**现场形态**（磁盘上的设置段没有
  `protocol`）解析后仍是 `chat-completions` 且该段其它字段一字未丢；反向对照（摘掉 pin）
  解析回 `messages`。另有一条真组合树能力冒烟：造一个 0 字节锁 ⇒ 设置写入超时失败 ⇒
  回收后同一写入成功。
- **升级提示**：命中该问题的机器**只需升级客户端**即可恢复（无需改服务端配置、
  无需清数据目录）。若日志里仍看到 `缺乏认证令牌` 之外的两种形状，请按下面区分：
  `令牌无效或已过期` 是登录态问题；`缺少本地凭据` 是本地密钥问题 —— 三者互斥，不要混判。

## 二、服务端：大请求体不再被误判为「请求体格式错误」

- **现象**：会话日志里出现 `请求体格式错误`，同一张图或同一段长上下文**反复失败**，
  客户端按"不可重试"处理，用户只能重发。
- **影响**：长上下文、多工具定义或带图片的请求，在慢链路上读满 60 秒被截断 ——
  服务端把"读失败"当成"格式错"，回了不可重试的 400。
- **修复**：读请求体的时间预算按路由放宽到 **1 小时**（与防慢速攻击的解耦），
  超时改回 **`503` 可重试**，只有真正读失败才 400。
- **同时对齐官方容量的口径**：chat / FIM / messages / responses 的请求体上限
  由 16 MiB 提到 **64 MiB**（embeddings 4 MiB，文件上传 64 MiB）；
  网关限流缺省改为 **0 = 不限制**（并发仍由每用户 in-flight 闸门兜底）。
  ⚠️ **升级注意**：老库里已保存的限流值**不会被代码缺省覆盖**；要按官方口径放开，
  需在管理后台「网关」页把它显式改成 0。

## 三、服务端：Files API 直通、文件归属隔离与自动回收

- **新增 `/v1/files`**（含无 `/v1` 变体）：上传 / 列表 / 取元数据 / 删除，直通上游。
- **归属隔离**：上游按 API key 划分文件，而全组织共用一把 key，因此网关自己记归属 ——
  **列表只返回自己的文件**，他人的 `file_id` 一律按"不存在"处理；在聊天里引用他人的
  `file_id` 直接 404（不泄露存在性）。
- **保留上限与回收**：新设置 `gateway.file_expiry_days`（缺省 **7 天**，1~30 可配）。
  上传时网关重写 `expires_after`（没带就补、超过上限就收敛），超期由回收器每 5 分钟
  在上游删除（上游配额是全组织共享的）。回收采用**标记认领**，进程中断也不会留下
  "永无凭据"的上游对象。
- **管理后台新增「网关文件」页**：按员工看占用（文件数 / 字节 / 其中已过期 / 最早过期），
  支持按员工过滤、`file_id` 搜索、排序与分页；单条删除 + 按条件批量清理
  （危险范围要求输入确认词，全部动作写审计）。
- **出站请求体的稳定性与安全**：按员工注入官方用户标识（覆盖客户端自带值）；
  请求体不是合法 JSON 对象时本地 400（不再"解析失败就原样转发"）；
  新增进程级**在飞请求体字节**闸门（缺省 128 MiB，可配），打满返回 `503` 可重试；
  单请求 `file_id` 引用上限缺省 **600**（对齐官方"单请求最多 600 张图"，可配）。

## 四、客户端发布包不再夹带自有源码（安全面）

- **修复**：打包输入改为「运行期白名单」——只有真正随包运行的产物进入安装包，
  客户端自身的 `src/` / `tests/` / `scripts/` 与 **内嵌原始 TypeScript 源码的 sourcemap**
  在进包前就被排除（不是打包后删除）；**发布版同时关闭调试工具**，开发态保持可用。
  自动化测试与诊断链路走独立的调试端口协议，不受影响。
- **效果**：安装包内 asar 条目 14 385 → 12 334、`148.05 MiB → 129.38 MiB`；
  自有源码与 sourcemap 条目 **471 → 0**，包内 `.ts/.tsx` 条目 **1 975 → 0**。
- **注意：本版不以缩小安装包为目的**。新引擎的运行时更大，三平台**下载体积反而略增**
  （Linux +2.0 MB / macOS +4.0 MB / Windows +9.8 MB）。
- **认账范围**：第三方依赖包自带的源码与类型声明**仍在包内**（那是上游 npm 包的公开
  内容，不属于本产品源码）。

## 五、桌面引擎升级与启动期回收孤儿写锁

- **引擎升级**：桌面客户端引擎升至 **Electron 44.4.3**（Chromium 152 / V8 15.2），
  含上游安全修复。44 线的破坏性变更已逐条核对，不影响本产品的交付范围与剪贴板/网络行为。
- **孤儿写锁回收**：主进程在启动早期检查数据目录里的两个写锁
  （`settings.yaml.lock` / `.credentials.yaml.lock`）：
  - **只删有证据的孤儿**：锁里记的就是本进程 PID（上一轮的 PID 复用）、属主进程已确认
    不存在、或"无属主且已超过 45 秒"；
  - **一律保留并上报**：锁读不出来、内容不是合法 PID、路径不是普通文件、属主仍存活或
    存活状态未知；
  - 删除前会复检文件身份（设备/Inode/大小/修改时间）并**逐字节比较内容**，防止误删
    另一个写者刚落下的新锁；失败只记日志，**绝不阻断启动**。
  - 结论都写进客户端日志（`reclaimed…` / `held by live pid…` / `left … in place (reason)`），
    界面不弹提示（有意如此）。
- **为什么不更早发现**：该问题表现为"设置静默变成只读"，各插件的写入失败都被
  `.catch` 吞进日志，没有 UI 信号。本版并未增加 UI 提示（见已知限制）。

## 六、工程与门禁

- CI 的运行环境显式钉在 `ubuntu-24.04`（避免镜像漂移导致的构建差异），
  GitHub 脚本动作升到 Node 24 运行时；此外新增两条打包期自证：安装包内不得出现自有源码 /
  sourcemap / 开发期产物（命中即拒包），归档内每个模块的相对引用必须在归档内存在
  （缺 chunk 会在打包阶段就报错，而不是等用户启动时白屏）。

## 已知限制（本版认账，未修）

- **Windows 与 macOS 安装包未在对应平台本机复核**：打包与验证在 Linux 上完成
  （含完整客户端自动化），Windows 安装程序与 macOS 磁盘映像由 CI 三平台构建
  （macOS 走签名 + 公证 + 装订）。**请在对应平台的首次升级后反馈启动与登录情况。**
- **孤儿写锁回收的残余不自愈**：属主 PID 恰好被**另一个活进程**复用、或锁文件读不出来时，
  只记录日志、需人工删除；"崩溃后立刻重启"的那一次运行不会回收刚留下的 0 字节锁
  （年龄门槛 45 秒），但模型链路已由组装期协议钉死兜住，下一次启动即回收。
  该回收的保证范围限于**同一台机器、同一个 PID 命名空间**；多个客户端经容器或网络
  家目录共享同一数据根的部署不在保证范围内。
- **发布版调试工具不可用**：这是**有意**的行为变化。需要现场排查时，请使用客户端自带的
  「导出诊断包」入口。
- **文件回收的窗口与计费口径**：上游删除对象与台账收尾之间存在一个极短窗口，若恰好发生
  并发重新上传，客户端会按既有路径回落到内联图片重传；`chunked` 上传无法在读取前预判
  体量，内存闸门只能在读完后计费（带 `Content-Length` 的上传在读取前即被拒绝）；
  调小保留上限**不会追溯**已落库的文件（管理员可在「网关文件」页按员工清理）。
- **客户端自动更新按版本号递增触发**：已装 v2.8.0 的机器会收到更新提示；
  升级不需重新登录（预发布与正式版共用同一数据目录）。

## 升级与回滚

- 服务端：取镜像（更新服务器附件）→ 按 `docs/deploy/AI-DEPLOY.md` 升级
  （**升级前必须备份**，不要使用 `latest`，不要 `down -v`）。
- 客户端：随服务端镜像分发，服务端升级后员工从自己登录的服务器取包，无需访问外网。
  **使用 v2.8.0 客户端的部署，请优先推动客户端升级**（第一节的 401 修复在客户端侧）。
- **迁移类别**：本版三个迁移都是**只建表 / 只加列**
  （`gateway_files` 建表 + 两个索引、加 `size_bytes` 列、加 `reaping_at` 列），
  不含 `DROP`、不改写既有数据。
- **回滚**：保留上一版镜像 tag，改回 `.env` 的 `SERVER_IMAGE` 后
  `docker compose up -d server` 即可，**不需要恢复数据库**（新表新列对旧二进制无害）。
  客户端回滚需要重装上一版安装包 —— 但请注意：**回滚客户端会把第一节的 401 问题带回来**
  （若该机器已命中触发条件），因此客户端不建议回滚。
