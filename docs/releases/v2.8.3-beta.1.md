# v2.8.3-beta.1（2026-10-08）

> 一句话：桌面客户端**自带 node / pnpm / python 运行时** —— AI 可以直接写代码并运行，
> 创造模式里「把能力打成 bundle 再安装」的路径也不再因为客户端没有包管理器而失败；
> 同时**连接器支持标准 MCP 配置** —— 管理端粘贴厂商文档给的那份 `mcpServers` JSON 即可，
> 认证由端点自己声明（探测 → 发现 → 动态注册 → PKCE），不再需要逐条手填授权端点。
> **不升级的后果**：让 AI 跑脚本仍然没有解释器（找不到 `node`/`python3`），用
> `plugin_manager` 安装能力包仍然报包管理器不存在（`ENOENT: pnpm`）；新增 MCP 连接器
> 仍然要手写 `authorizeUrl`/`tokenUrl`/`registrationEndpoint`，且静态端点形态不会带上
> RFC 8707 的资源指示。

## 一、客户端自带 node / pnpm / python（本版主要变化）

- **现象**（升级前）：让 AI 写点代码并运行，命令直接失败（没有 `node`/`python3`）；
  按创造模式文档把能力打成 bundle 后用 `plugin_manager` 安装，报的是包管理器不存在
  （`ENOENT: pnpm`）。
- **影响**：这是"在客户端上把能力做出来"的整条路径 —— 写代码、跑脚本、装能力包 —— 都走不通。
  它不影响对话与模型调用，所以只看聊天功能不容易发现；现场反馈的"创造模式不能用"就是它。
- **本版怎么修**：
  - 客户端随包分发三套**官方预编译**运行时（Node.js 24、pnpm 11、CPython 3.12），
    启动时把它们前置到**应用自己的** `PATH` —— 只影响应用启动的子进程（AI 的 shell 命令、
    MCP stdio 服务、打包能力包用的 pnpm），**不改系统环境**，也不需要运维在机器上装任何东西；
  - 能力包的安装器指向随包 pnpm（这是"装 bundle 不再 ENOENT"的那一处）；
  - Python 的 `pip install` 与 `.pyc` 缓存重定向到应用数据根 —— 不写进安装目录，
    也不破坏 macOS 的签名封装。
- **支持的系统下限**（由随包 Node 决定）：Linux glibc ≥ 2.28（Ubuntu 20.04+ / Debian 10+ /
  RHEL 8+；**不含** CentOS 7、Ubuntu 18.04）、Windows 10 / Server 2016 及以上、
  macOS 13.5 及以上（沿用现有 macOS 客户端产线）。
- **怎么自证**：打包期门禁在真实产物里逐个执行 `node -v` / `pnpm -v` / `python3 -V` 并与
  钉死的版本逐字比对，另外让随包 node 自报平台与架构（拿错平台的载荷当场失败）；
  macOS 发布版还逐个入口做严格验签后再执行。

## 二、Linux 交付件里的一份重复载荷被删掉

- **现象**：Linux 客户端的归档里此前**另存了一份**语音识别模型（与随包资源目录下的那份
  重复），按未压缩计约 230 MiB，白占安装体积。
- **本版**：Linux 侧从归档里排除随包资源目录。本机 `--dir` 产物实测：归档由 376.8 MB 降到
  135.4 MB（去掉的是那份 230 MiB 未压缩的重复载荷）。它与第一节的增量方向相反，
  且只影响 Linux 客户端。
- **影响面**：仅 Linux 客户端，功能无变化（运行时读的仍是 `resources/` 下的那一份）。

## 三、连接器支持标准 MCP 配置（服务端 + 客户端）

- **现象**（升级前）：按厂商文档新增一个 MCP 连接器时，管理端要求逐条填 `authorizeUrl`、
  `tokenUrl`、`registrationEndpoint` 等字段，而厂商给的配置只有一行 `{"type": …, "url": …}`；
  端点填错或搬迁后连接器静默失效。默认的第三方 MCP 连接器用的正是这种手写端点形态，
  它也绕过了 MCP 授权规范里的资源指示（RFC 8707），授权请求还只申请了端点声明的第一个 scope。
- **本版怎么修**：
  - 管理端「从 JSON 导入」直接接受**标准 MCP 配置**
    （`{"mcpServers": {"<名称>": {"type": "streamableHttp", "url": "…"}}}`，也接受省略外层包装的写法；
    `stdio` 形态用 `command`/`args`/`env`）。保存时服务端统一归一成内部定义 —— 数据库里只存一种形状，
    客户端不多开一条解析路径。未登记的键、`type: "sse"`、同时给出 `url` 与 `command` 一律
    **报错并点名**，不静默丢弃（少写一个字母不会被无声忽略）；
  - 新增认证模式「自动」：连接时探测端点 —— 2xx 即公开端点；401 按 `WWW-Authenticate` 的声明走
    RFC 9728 → RFC 8414 发现 + 动态客户端注册 + PKCE 回环回调；声明了凭据表单（`tokenFields` +
    请求头里的 `${字段}`）则走凭据表单；既无端点又无表单即免凭据。**已声明静态端点的旧配置行为不变**
    （自动模式不会给它叠加发现）；
  - 授权请求改为申请端点声明的**全部 scope**，并在授权服务器声明 `offline_access` 时一并申请
    （原来只取第一个：多 scope 的端点会拿到缺权限的令牌，表现为随后某个工具调用 403，且难以归因）；
  - 默认的第三方 MCP 连接器改由端点自述授权（手写端点移除）。该迁移**只改与建库种子逐字节相同的那一行**，
    管理员改过的行一个字不动。
- **本地 stdio MCP 的既有约束不变**：首次运行仍需本地确认（命令、参数、环境变量逐条披露），
  `PATH`/`NODE_OPTIONS` 一类进程引导变量永不注入。

## 四、运维要做什么

- **需要升级服务端**：本版有两条数据库迁移（见下方机器可读锚点），服务端镜像要与客户端同步升级；
  升级前按 `docs/deploy/AI-DEPLOY.md` 备份。只升客户端不升服务端时既有功能不受影响，但管理端不会
  接受标准 MCP 配置（服务端仍是旧的写入校验）。
- **不需要改客户端配置**：随包运行时默认启用，没有开关。
- **Windows 安装包变大**：CI 把 Windows 打包的 7z 压缩级别由 9 降到 3（换约 70% 的打包时间），
  安装包由 345 MiB 涨到约 415–425 MiB；只影响下载体积，功能与安装流程不变。
- **内网只放行认证代理的环境**：影响的是"从公开 registry 安装依赖"这一步（与往年口径相同，
  本版没有新增出网行为）；离线安装请用工作区里的本地目录 bundle。

## 已知限制（本版认账，未修）

- **从 registry 装依赖仍需出网**：随包只解决"客户端没有包管理器"。离线环境可以安装工作区内
  的本地 bundle，不能从公开 registry 拉取依赖。
- **pnpm 的下载存储仍在用户主目录**：`pnpm install` 的全局 store 还在用户主目录
  （`~/.local/share/pnpm/store` 一类），没有重定向到应用数据根；只影响"完全自包含卸载"这个
  场景，不影响使用。
- **macOS / Windows 的安装体验仍由 CI 与发布人验证**：三平台载荷的存在性、可执行性与版本由
  打包期门禁逐个真跑，macOS 发布版另有逐入口验签；本机只在 Linux 上做过端到端打包与真机探针。
- **连接器不支持 `sse` 传输**：标准配置里写 `type: "sse"` 会被当场拒绝并点名（客户端只实现了
  `stdio` 与 `streamable-http` 两种传输）。把这个值当远程端点接进来只会得到一个说不清原因的失败。
- **不接受标准 OAuth 的端点仍需管理员声明凭据字段**：自动模式解决的是"端点自己说清楚了授权"这一类；
  只认一个静态 API Key 的 MCP，需要管理员在连接器里声明凭据表单（`tokenFields`）并在请求头里用
  `${字段}` 引用它 —— 客户端不会凭空向用户索要未经声明的凭据。

## 升级与回滚

- 服务端：本版相对 `v2.8.2` 有两条迁移（0083/0084）与连接器写入路径改动 → 取镜像
  （更新服务器附件）→ 按 `docs/deploy/AI-DEPLOY.md` 升级（**升级前必须备份**，
  不要使用 `latest`，不要 `down -v`）。
- 客户端：随服务端镜像分发，服务端升级后员工从自己登录的服务器取包，无需访问外网。
- **迁移类别**：链上相邻两版（`v2.8.3-beta.1` ↔ `v2.8.2`）之间**没有**破坏性迁移 ——
  0083 只放宽 `connectors.auth_mode` 的 CHECK 约束（存量行全部是旧四值，校验通过），
  0084 只改写**与建库种子逐字节相同**的那一行连接器定义（管理员改过的行不受影响）；
  两版都**不含** `DROP`、也不删列。
- **回滚**（两步，缺一不可 —— 只换镜像会起不来：迁移执行器对"库比二进制新"是 fail-loud 的）：
  ① 删掉本版写入的 `schema_migrations` 版本行（`DELETE FROM schema_migrations WHERE version IN (83, 84);`，
  DDL 与数据都留着：旧二进制不写 `auto`、也不读新定义形状 ⇒ 安全）；
  ② 把服务端镜像 tag 改回上一版并重启。已升级的客户端安装包可以继续使用（多出的随包运行时
  与新连接器模式对旧服务端无害），也可以让员工装回旧安装包，**不会**影响本地会话
  （本版不动数据根、不改会话格式）。
- **迁移清单（机器可读锚点，供 `scripts/check-release-notes-migrations.mjs` 与 `git diff` 对拍）**：`0083_connectors_auth_mode_auto.sql`、`0084_sales_easy_endpoint_discovery.sql`
  - 该锚点比较的是**发布链上相邻两版**（`v2.8.3-beta.1` ↔ `v2.8.2`）之间新增的迁移文件。

## 附件与校验

- `picoaide-server-2.8.3-beta.1-amd64.zip`：服务端镜像压缩包（`docker load` 后使用），
  内含该渠道的三平台客户端安装包；
- `SHA256SUMS`：`sha256sum -c SHA256SUMS` 校验后再解压。
- 客户端安装包在镜像内（`/opt/picoaide/client/`），员工也可从自己服务器的更新页面下载。
  品牌渠道的镜像与客户端只在该渠道自己的更新目录里，不随公开 Release 发布。
