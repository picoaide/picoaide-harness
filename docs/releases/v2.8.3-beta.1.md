# v2.8.3-beta.1（2026-10-08）

> 一句话：桌面客户端**自带 node / pnpm / python 运行时** —— AI 可以直接写代码并运行，
> 创造模式里「把能力打成 bundle 再安装」的路径也不再因为客户端没有包管理器而失败。
> 本版**只动客户端**：服务端镜像与数据库都没有变化，可以只换客户端安装包。
> **不升级的后果**：让 AI 跑脚本仍然没有解释器（找不到 `node`/`python3`），
> 用 `plugin_manager` 安装能力包仍然报包管理器不存在（`ENOENT: pnpm`）。

| 项目 | 说明 |
| --- | --- |
| 版本类型 | 预发布（beta） |
| 升级建议 | 建议升级（客户端能力补齐；不升级不影响既有会话、也不影响服务端） |

| 交付件体积 | 每个平台安装包约 +50–60 MB（随包三套运行时：展开 180–240 MiB，按安装包压缩口径推算） |

## 一、客户端自带 node / pnpm / python（本版主要变化）

- **现象**（升级前）：让 AI 写点代码并运行，命令直接失败（没有 `node`/`python3`）；
  按创造模式文档把能力打成 bundle 后用 `plugin_manager` 安装，报的是包管理器不存在
  （`ENOENT: pnpm`）。
- **影响**：这是"在客户端上把能力做出来"的整条路径 —— 写代码、跑脚本、装能力包 —— 都走不通。
  它不影响对话与模型调用，所以只看聊天功能不容易发现；现场反馈的"创造模式不能用"就是它。
- **本版怎么修**：
  - 客户端随包分发三套**官方预编译**运行时（Node.js 24、pnpm 11、CPython 3.12），
    启动时把它们前置到**应用自己的** `PATH` —— 只影响应用启动的子进程（AI 的 shell 命令、
    MCP stdio 服务、打包能力包用的 pnpm），**不改系统环境**，也不需要运维在机器上装任何东西；
  - 能力包的安装器指向随包 pnpm（这是"装 bundle 不再 ENOENT"的那一处）；
  - Python 的 `pip install` 与 `.pyc` 缓存重定向到应用数据根 —— 不写进安装目录，
    也不破坏 macOS 的签名封装。
- **支持的系统下限**（由随包 Node 决定）：Linux glibc ≥ 2.28（Ubuntu 20.04+ / Debian 10+ /
  RHEL 8+；**不含** CentOS 7、Ubuntu 18.04）、Windows 10 / Server 2016 及以上、
  macOS 13.5 及以上（沿用现有 macOS 客户端产线）。
- **怎么自证**：打包期门禁在真实产物里逐个执行 `node -v` / `pnpm -v` / `python3 -V` 并与
  钉死的版本逐字比对，另外让随包 node 自报平台与架构（拿错平台的载荷当场失败）；
  macOS 发布版还逐个入口做严格验签后再执行。

## 二、Linux 交付件里的一份重复载荷被删掉

- **现象**：Linux 客户端的归档里此前**另存了一份**语音识别模型（与随包资源目录下的那份
  重复），按未压缩计约 230 MiB，白占安装体积。
- **本版**：Linux 侧从归档里排除随包资源目录。本机 `--dir` 产物实测：归档由 376.8 MB 降到
  135.4 MB（去掉的是那份 230 MiB 未压缩的重复载荷）。它与第一节的增量方向相反，
  且只影响 Linux 客户端。
- **影响面**：仅 Linux 客户端，功能无变化（运行时读的仍是 `resources/` 下的那一份）。

## 三、运维要做什么

- **不需要升级服务端**：本版没有数据库迁移，服务端镜像内容与 `v2.8.2` 相同。客户端安装包
  随镜像分发，员工从自己登录的服务器取包。
- **不需要改客户端配置**：随包运行时默认启用，没有开关。
- **内网只放行认证代理的环境**：影响的是"从公开 registry 安装依赖"这一步（与往年口径相同，
  本版没有新增出网行为）；离线安装请用工作区里的本地目录 bundle。

## 已知限制（本版认账，未修）

- **从 registry 装依赖仍需出网**：随包只解决"客户端没有包管理器"。离线环境可以安装工作区内
  的本地 bundle，不能从公开 registry 拉取依赖。
- **pnpm 的下载存储仍在用户主目录**：`pnpm install` 的全局 store 还在用户主目录
  （`~/.local/share/pnpm/store` 一类），没有重定向到应用数据根；只影响"完全自包含卸载"这个
  场景，不影响使用。
- **macOS / Windows 的安装体验仍由 CI 与发布人验证**：三平台载荷的存在性、可执行性与版本由
  打包期门禁逐个真跑，macOS 发布版另有逐入口验签；本机只在 Linux 上做过端到端打包与真机探针。

## 升级与回滚

- 服务端：本版服务端与 `v2.8.2` 相同（无迁移），可以只换客户端；若整体升级，取镜像
  （更新服务器附件）→ 按 `docs/deploy/AI-DEPLOY.md` 升级（**升级前必须备份**，
  不要使用 `latest`，不要 `down -v`）。
- 客户端：随服务端镜像分发，服务端升级后员工从自己登录的服务器取包，无需访问外网。
- **迁移类别**：链上相邻两版（`v2.8.3-beta.1` ↔ `v2.8.2`）之间**没有**数据库迁移；
  本版不含任何 `DROP` 或数据改写。
- **回滚**：把服务端镜像 tag 改回上一版并重启即可（无迁移，不需要恢复库）。已升级的客户端
  安装包可以继续使用 —— 它只是多了随包运行时，与旧服务端兼容；也可以让员工装回旧安装包，
  **不会**影响本地会话（本版不动数据根、不改会话格式）。
- **迁移清单（机器可读锚点，供 `scripts/check-release-notes-migrations.mjs` 与 `git diff` 对拍）**：无
  - 该锚点比较的是**发布链上相邻两版**（`v2.8.3-beta.1` ↔ `v2.8.2`），两版之间没有数据库迁移。

## 附件与校验

- `picoaide-server-2.8.3-beta.1-amd64.zip`：服务端镜像压缩包（`docker load` 后使用），
  内含该渠道的三平台客户端安装包；
- `SHA256SUMS`：`sha256sum -c SHA256SUMS` 校验后再解压。
- 客户端安装包在镜像内（`/opt/picoaide/client/`），员工也可从自己服务器的更新页面下载。
  品牌渠道的镜像与客户端只在该渠道自己的更新目录里，不随公开 Release 发布。
