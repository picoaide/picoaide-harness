# 应用构建（WASM 应用）

**一句话定位**：用户只需要说出"我想做个 XX 登记表"，**底层设计由你全做完** —— 数据模型、
页面、权限、错误处理、边界、打包、发布、交付深链，一步都不留给用户；用户只在**设计访谈**
里回答业务问题。

产物形态固定为**前后端分离**：一份静态前端（HTML/CSS/JS，随包资源，由宿主按路径直出）
＋ 一个 wasm 后端（只回 JSON API）。**不要在 wasm 里拼 HTML 字符串。**

平台把"能做什么"限死了：一个应用库（每个应用一个）、一份随包静态资源、一行日志。
**这不是配置问题，是能力不存在** —— 照着下面的九阶段走，不要试图绕过。
（**服务端 wasm 侧没有任何 AI 能力**；应用里的 AI 走**客户端 AI loop**，见下文专节。）

## 什么时候用 / 不要用

用：

- 用户要一个内部小工具：共享便签、登记表、值班表、报销备注、清单勾选、小型计算器。
- 数据量小（几千行以内）、界面简单（一两个页面）、只给一小撮同事用。
- 用户说"能不能在这个平台上做个应用 / 发布到应用中心 / 我们自己搞一个"。

不要用（能力不存在，硬做只会卡住）：

- 需要访问外部系统 / 调外部接口 / 打开外部网页 → 应用**不能主动发起网络请求**
  （`fetch`/`XHR` 一律被拦）。⚠️ **不要对外说成"平台不能联网"**（见硬约束里「不能主动发起网络请求」那一条）。
- 需要读写文件、跑命令行、起后台任务、开定时器 → 平台没有这些能力。
- 需要图片/视频/大文件处理、需要几十 MiB 以上的数据 → 体积与内存上限都很小。
- 需要"到点自动跑"的定时任务 → 平台没有后台任务与定时器（定时任务属于客户端另一个能力，不在应用里）。
- 需要 Python/Java/Node 生态 → 官方支持的语言只有 Go（Rust/Zig 可用但不承诺）。
- 需要"每个用户只看自己的数据" → 同一应用内数据是共享的（见硬约束第 3 条）。

## 九阶段流程（照顺序走，不要跳）

| 阶段 | 你做什么 | 结束时手里有什么 |
| --- | --- | --- |
| 0 只听想法 | 让用户把想做的事说完，**一句技术都不提** | 一段业务原话 |
| 1 设计访谈 | 分三轮提问，每轮三到五个问题（给选项 + 推荐项） | 用户的逐条回答 |
| 2 设计卡 | 用**业务语言**写一页设计卡，回读给用户确认 | 用户确认过的设计卡 |
| 3 多角色评审 | 依次扮演五个角色审设计卡，把缺口变成追问 | 缺口清单 → 用户的补充回答 |
| 4 技术方案 | 定路由、数据表、权限判定、错误信封、三态 | 一页技术方案（给用户看的是白话版） |
| 5 脚手架与实现 | 拷 `examples/` 改成自己的应用 | 可编译的工程 |
| 6 编译与自测 | 编译 wasm + 本地假宿主预览 | 通过预览的产物 |
| 7 打包与发布 | 一条命令链：打包 → 预检 → 发布 | 发布成功的版本号 |
| 8 交付与验收 | 给深链、核对名单、讲清四种状态 | 用户能点开的应用 |

### 第 0 阶段：只听想法

- **只做一件事：听**。用户说"我想做个设备借用登记"，就让他说完：谁用、登记什么、给谁看。
- **此时禁止做的事**：谈技术栈、谈数据表、谈字段名、谈"前端后端"、给平台术语、
  问"要不要用 wasm"、让他选 access 模式。用户是不懂技术的业务同事 —— 术语只会让他
  把决定权推回给你或者随便答一个。
- 允许的动作：复述一遍他的话确认没听错（"所以是给行政部的五个人登记办公用品借用，
  借出和归还要有记录，月底要能看谁还没还 —— 对吗？"）。
- 想法里明显缺失的关键信息（例如"谁审批"）**留到第 1 阶段问**，第 0 阶段不要打断。

### 第 1 阶段：设计访谈

**这是本技能最重要的部分：至少三轮，不要问一句就开工。** 每一轮三到五个问题，
每题都给**选项 + 一个推荐项**，并明确告诉用户"你可以只回 '1A 2B 3 同意' 这样一句话"。

**提问的三条硬规则**

1. **一轮三到五个问题，不要一次抛十几个**（用户会敷衍）。
2. **每题给选项 + 推荐项**，并给出推荐理由的一句话（例如"推荐 '全部登录的同事都能看'：
   登记表是内部信息，但不需要保密到名单级别"）。
3. **用户答完一轮再问下一轮**，并把上一轮的答案用**业务语言**复述一遍
   （让他有机会推翻："你刚说'谁都能改'，但记录类数据一般只有本人和行政能改，要改吗？"）。

**三轮的分工**

| 轮次 | 主题 | 目标 |
| --- | --- | --- |
| 第一轮 | 人与事 | 谁用、有多少人、要记什么、最常用的动作是什么 |
| 第二轮 | 规则与边界 | 怎么流转、谁能看谁能改、要多保密、要不要通知 |
| 第三轮 | 兜底与验收 | 出错了怎么办、多久不用会过期、什么算做完了、明确不做什么 |

**问题库（八类，按需取用；完整版含选项与推荐见 `references/design-interview.md`）**

| 类别 | 必问什么 |
| --- | --- |
| 使用者与规模 | 谁用（一个组还是全公司）、大概多少人、有没有"外部的人"（客户/供应商） |
| 核心对象与字段 | 要登记的那个东西叫什么、有哪些必填信息、有没有附件/图片、一条记录多大 |
| 流转与状态 | 一条记录从创建到结束经过哪些状态、谁能推进状态、要不要审批 |
| 权限与可见性 | 谁能看全部、谁只能看自己的、谁能改别人的、谁能删 |
| 数据敏感度与留存 | 算不算敏感（薪资/客户名单/身份证号）、存多久、过期要不要自动清 |
| 通知与提醒 | 需不需要提醒人（到期、被指派）、平台只能"打开时看到"，不能主动推送 |
| 失败与兜底 | 操作失败时用户看到什么、重复提交怎么办、填错了能不能改 |
| 边界与非目标 | 这一版明确**不做**什么、数据超过几千行怎么办、以后可能要加什么 |

**每一类都要给出"你替他做的默认决定"**：用户说"随便/你看着办"时，按推荐项落定并在设计卡里
写明"我按 XX 处理了，如果不对告诉我"。**不要让用户对着空白发呆。**

### 第 2 阶段：设计卡

设计卡是**给用户看的一页纸，全部用业务语言写**，不出现 SQL、路由、字段类型、`access`
这类词。固定七段（模板见 `references/design-interview.md`）：

1. **目的**：这个应用解决什么问题（一句话，来自用户原话）。
2. **用户**：谁用、大概多少人、有没有不在名单里的人。
3. **对象**：要登记的东西 + 每条记录有哪些信息（用"姓名、日期、备注"这种人话）。
4. **动作**：用户能做的几件事（新增、查看、改状态、删除…），按常用程度排序。
5. **权限**：谁能看什么、谁能改什么（说清"默认"与"例外"）。
6. **数据**：敏感程度、保留多久、会不会有人不希望别人看到。
7. **不做**：这一版明确不做的功能（防止范围蔓延，也是验收依据）。

写完**回读给用户并请他确认或修改**（"我按这个做，有要改的吗？没有我就开始设计细节"）。
用户确认后的设计卡是第 3 阶段评审与第 8 阶段验收的共同基准。

### 第 3 阶段：多角色评审（把缺口变成追问）

设计卡确认后，**依次扮演五个角色各审一遍**，列出"设计不到位的地方"，然后
**把这些缺口逐条变成追问用户的问题** —— 你**不许自己拍板**敏感取舍
（默认值可以提议，但必须让用户点头）。

| 角色 | 看什么 | 常见缺口（真实高频） |
| --- | --- | --- |
| 产品经理 | 目标是否可验收、范围是否失控、有没有"其实没人用"的功能 | 没写"什么算做完"；把三期需求混在一版；没写不做清单 |
| 交互设计 | 主流程是否三步内完成、空/加载/失败三态是否都有文案、手机上是否可用 | 只有成功路径；空列表一片白；提交后没有反馈；删除没有二次确认 |
| 数据与状态 | 表与列是否够用又不超限、状态机是否闭环、并发与重复提交、能不能改结构 | 状态没有"终态"；两个人同时改一条记录；字段不够用又要改表（平台没有自动迁移） |
| 安全与合规 | 敏感数据是否真的只在该看的人手里、名单谁维护、删除与留存、导出风险 | 敏感字段进了"谁能打开应用谁就能看"的页面；名单没有维护人；删除无法追溯 |
| 运维与支持 | 出错时用户找谁、日志能不能定位、数据满了怎么办、负责人是谁 | 没有负责人；失败信息只有"失败了"；没人管"库满了 100 MB" |

**「评审发现 → 追问话术」模板**（照抄，把方括号换成你的内容）：

```
【角色】数据与状态
【发现】设计卡里"请假记录"只有"提交"一个状态，没有"批准/驳回"，也没有终态。
【影响】实现时无法判断一条记录还要不要处理，列表也没法排序。
【追问用户】这条记录提交之后，还需要别人处理吗？
  A. 需要，行政批准或驳回（推荐：登记类流程通常需要一个明确的责任人）
  B. 不需要，提交就是最终记录（那我把"状态"去掉，界面会更简单）
  你回 A 或 B 就行。
```

**纪律**：一条缺口对应一条追问；追问同样给选项 + 推荐项；**用户没回答的缺口不许自行落定**
（可以在设计卡里标注"按推荐项处理，用户未反对"，但这句必须写出来让用户有机会推翻）。
五份评审的产出合并成一张**缺口清单**（缺口 / 影响 / 追问 / 用户答复），清单清零后进入第 4 阶段。

### 第 4 阶段：技术方案（前后端分离）

**形态**：静态前端（`web/index.html` + `web/app.css` + `web/app.js`，编译进 wasm 的
自定义段成为**随包资源**）＋ wasm 后端（**只回 JSON**）。宿主对非保留资源**按路径直出**，
所以 CSS/JS 由宿主直接发给浏览器，不经过 wasm。

```
应用页（web/，随包资源）                 wasm 后端（main.go）
  GET /                 ──────────►  宿主把入口交给 wasm（要做名单判定）
                                       wasm: assets.read("index.html") → 响应信封
  GET /static/app.css   ──────────►  宿主**直出**（不经过 wasm）
  GET /static/app.js    ──────────►  宿主**直出**（不经过 wasm）
  GET  /api/notes       ──────────►  wasm: db.query → JSON
  POST /api/notes       ──────────►  wasm: db.exec → JSON
  POST /__picoaide/ai/chat ───────►  客户端 AI loop（本地处理，不经服务端）—— 见专节
```

**路由约定（照着做，不要自创）**

| 路径 | 谁答 | 规则 |
| --- | --- | --- |
| `/`、`/index.html`、`<目录>/` | **wasm** | 入口一律由应用自己答：先判名单，再 `assets.read("index.html")` 作为响应体返回 |
| `/static/*`、`/*.css`、`/*.js`、图片 | **宿主直出** | 命中包内资源就直出；写的时候仍要留一条 wasm 兜底分支（见下） |
| `/api/*` | **wasm** | 宿主**永不**直出这个前缀，即使包里真有 `api/x.json` |
| 其它路径 | 先资源后 wasm | 宿主先试直出（存在才直出），否则交给 wasm 走 404 分支 |
| `/__picoaide/*` | **客户端** | 保留命名空间：只有 AI 桥一条路径存在，其余一律 404，**不会**进到你的应用 |

**错误信封**：API 一律回 JSON，失败也回 JSON（**不要回 HTML**）：

```json
{"error":{"code":"VALIDATION","message":"内容不能为空"}}
```

前端只认这一种形状：`resp.ok` 为假时读 `body.error.code` 与 `body.error.message`，
把 `message` 直接显示给用户，`code` 进 `console.error` 便于排障。
**成功也回 JSON**（`{"notes":[…]}` 这种），不要回 `text/plain`。

**三态写法**（每个数据区块都要有，缺一个就是"白屏 bug"）：加载中（骨架或"正在读取…"）、
空（"还没有记录，先在下面添加一条"）、失败（错误码 + "重试"按钮）。示例见
`examples/go/web/app.js`。

**为什么不在 wasm 里拼 HTML 字符串**（旧写法，别再用）：

- 拼字符串会让页面与逻辑耦合在一份 Go 代码里，改一个按钮要重编译整个 wasm 并重新发布；
- 前端的加载/空/错三态、表单校验、二次确认在 JS 里是几行，在 wasm 里要手写一大堆拼接；
- 静态资源由宿主直出、可缓存、可 304 复验，而"wasm 现拼的 HTML"每次都要跑一遍 guest
  （guest 预算只有 10 秒，且每次请求都要新建实例）。
- `html/template` / `text/template` 依然**被放行**（白名单覆盖，用于导出 HTML 报表之类的
  少数场景），但**默认不要用它渲染页面** —— 页面走 `web/`。

### 第 5 阶段：脚手架与实现

1. **拷骨架**：把 `examples/go/` 整个目录拷到会话工作区（含 `web/`、`preview.mjs`、
   `picoaide.app.json`、`go.mod`），在它上面改。
2. **改 `web/`**：`index.html` 只放结构，`app.css` 放样式，`app.js` 放取数与渲染。
   页面里引用资源一律写**绝对路径**（`/static/app.css`），不要写相对路径。
3. **改 `main.go`**：保留帧读写、宿主调用、`assets.read` 读配置这三块（它们容易写错），
   只改路由分支、表结构与业务 SQL。
4. **改 `picoaide.app.json`**：`access`（写侧只有 `login` / `whitelist`）、`whitelist`（名单）、
   `purpose`（一句话用途）、`data_sensitivity`、`owner`。**字段名与取值只在生成物
   `references/app-config.md` 里维护**，不要凭记忆写。
5. **数据表设计规则**（细节见 `references/abi.md` §3.1）：
   - 一个应用最多 16 张表、每张最多 16 列，列类型只有 `text` / `int` / `real` / `bool` /
     `datetime`；表名列名必须匹配 `^[a-z][a-z0-9_]{0,30}$`。
   - 建表只有 `db.define`（幂等）；**没有自动迁移** —— 改结构要么加列，要么用新表名自己搬数据。
   - 时间统一存 `datetime` 列的 UTC 字符串（RFC3339），展示时再转本地。
   - **不要给"状态"只用自由文本**：状态用固定的几个英文/数字取值，展示时再翻译成人话。

### 第 6 阶段：编译与本地自测

```bash
# ① 四条状态目录一个都不能少（漏了会看到 `package fmt is not in std`）
export GOCACHE="$PWD/.gocache" GOMODCACHE="$PWD/.gomodcache" GOPATH="$PWD/.gopath" TMPDIR="$PWD/.tmp"
mkdir -p "$GOCACHE" "$GOMODCACHE" "$GOPATH" "$TMPDIR"
# ② 编译成 wasm
GOOS=wasip1 GOARCH=wasm go build -o shared-notes.wasm .
```

```bash
# ③ 本地自测：随技能分发的假宿主（零依赖，Node 自带 node:wasi + node:sqlite）
#    预览读的是**打包后**的产物（先做第 7 阶段第 ① 步）—— 假宿主也要按宿主规则
#    直出包内静态资源，所以它需要一份带了资源的 wasm。
node preview.mjs dist/shared-notes-packed.wasm --path / --user zhangwei
node preview.mjs dist/shared-notes-packed.wasm --path /api/notes --method POST --body '{"body":"hello"}'
node preview.mjs dist/shared-notes-packed.wasm --path /api/notes        # 再读一次：数据真的落库了
node preview.mjs dist/shared-notes-packed.wasm --user someone-else      # 看无权限页
node preview.mjs dist/shared-notes-packed.wasm --dump-tables            # 看本地库有哪些表/列/行数
```

`preview.mjs` 按 ABI 收发帧、**用真 SQLite 应答 `db.*`**（Node 内置 `node:sqlite`）、
并按宿主规则直出包内静态资源（所以它必须先被 `pack-assets.mjs` 打包，见第 7 阶段）。

两条使用要点：

- **数据跨调用保留**：库落在 `<产物目录>/.preview/<名字>.db`，可以用任何 SQLite 工具直接打开看
  （`--db <file>` / `--data-dir <dir>` 换位置，`--fresh` 清空重来）。闸门也与线上同向：
  单语句、`db.query` 只读、保留列 `_row_id` 不可提及也不出现在结果里。
- 它**不是**线上：没有 AI（wasm 侧本就没有）、没有并发/配额，名单判定仍是应用自己的事。
  改过预览逻辑或升级 Node 后，可以跑 `node preview.mjs --selftest` 确认语义没漂（8 条自检）。

**看到 `package fmt is not in std` 时不要怀疑 Go 装坏了**：唯一原因是第 ①步的四条环境变量
没生效。回到上面重跑一遍。

### 第 7 阶段：打包与发布（一条命令链，不要让用户手工做任何一步）

```bash
# ① 把前端资源塞进 wasm 的自定义段（SRC=DEST：磁盘文件 → 包内逻辑路径）
mkdir -p dist
node scripts/pack-assets.mjs --in shared-notes.wasm --out dist/shared-notes-packed.wasm \
  web/index.html=index.html web/app.css=static/app.css web/app.js=static/app.js
```

`scripts/pack-assets.mjs` 就在技能目录里（与 `references/` 同级）；若当前目录不是技能目录，
把 `scripts/pack-assets.mjs` 换成技能目录下的绝对路径。规则：
`--out` **不得与 `--in` 同路径**；`picoaide.app.json` 与工具链元数据段名会被直接拒；
路径不超过 256 字节、单段不超过 255 字节；自定义段总量不超过 4 MiB。

```bash
# ② 预检（不占版本号、不进审计，可以反复调）
wasm_app_validate({appId:"shared-notes", version:"1.0.0", title:"共享便签",
                   wasmPath:"dist/shared-notes-packed.wasm", config:{…}})
# ③ 发布（同样参数；非首版必须带 changelog）
wasm_app_publish({appId:"shared-notes", version:"1.0.0", title:"共享便签",
                  wasmPath:"dist/shared-notes-packed.wasm", config:{…}})
# ④ 交付：深链（scheme 由该客户端的渠道配置决定，不要写死）
#    <渠道 deep link scheme>://app/shared-notes
```

- 三个工具都真实存在：`wasm_app_list`（无参，查标识是否被占用、当前版本号）、
  `wasm_app_validate`、`wasm_app_publish`；每个工具都有自己的调用预算（上传预算 90 秒，
  超出会以工具超时返回，按 hints 缩小产物或分片续传）。
- 失败结果带 `code` / `details` / `hints`：**按 hints 改完重发**，失败的发布不占版本号
  （可以用同一个版本号重发）。断在 `UPLOAD_INCOMPLETE` 时把 `details.upload_id` 填进
  `uploadId` 续传。
- 版本号严格递增 `x.y.z`（可带 `-prerelease`）；非首版必须写 `changelog`；
  **已落行的版本号永久占用**（含被拒与软删的）。
- 发布流程、工具参数与错误处理见 `references/publishing.md`。

### 第 8 阶段：交付与验收

1. **给深链**：`<渠道 deep link scheme>://app/<app_id>`（例如官方/预发客户端是
   `picoaide-app`，其他渠道由渠道配置决定；**永远不要写死某个 scheme**）。
   scheme 由客户端本机只读路由 `GET /api/pico/wasm-apps/channel` 给出
   （`{appOriginScheme, deepLinkScheme, productName}`）——**拿不到时分享入口 fail-closed
   （不渲染，也不要编链接）**。
2. **核对名单**：提醒用户"不在名单里的人打开会看到一页『你不在名单里』+ 他的账号"，
   让他照着核对拼写（**平台不校验账号是否存在**，拼错只能靠这一页发现）。
3. **讲清四种状态**（员工侧，产品级口径）：

   | 场景 | 员工看到 |
   | --- | --- |
   | 应用**被冻结**（管理员停用） | **不列进目录**；深链仍可打开 ⇒ 404「应用已被管理员停用（冻结）」 |
   | 应用**被下架**（作者操作） | **仍列在目录**、带「已下架」标记；打开是 **410「应用已下架」** |
   | 应用**被删除** | 不列进目录；打开 ⇒ 404「应用不存在」 |
   | 有登记但**没有 approved 版本** | 404「应用还没有可用版本」 |
   | 我**不在名单里** | 应用**照常出现在目录**；点开后由**应用自己**返回 403（页面显示本人账号） |

   **排障口诀**：员工说"应用不见了" ⇒ 先分清**被冻结**（目录里真的不见了）/
   **被下架**（目录里还在、带标记）/ **权限不符**（在目录里、点开 403）。三者处置完全不同。
4. **告诉他怎么打开**：唯一形态是客户端内 `<渠道 app 源 scheme>://<app_id>`（每个应用一个
   origin），或点深链 `<渠道 deep link scheme>://app/<app_id>`（可带 `?path=/相对路径`）。
   **没有 `entry_url`、没有可贴进浏览器的地址。**

## 十一条硬约束

1. 编译目标是 **`wasm32-wasip1`**（Go：`GOOS=wasip1 GOARCH=wasm`）；官方支持的语言只有 **Go**。
2. **平台保留列 `_row_id`**：每张表由 `db.define` 自动追加 `INTEGER PRIMARY KEY AUTOINCREMENT`
   主键；它的 SQLite 别名 **`rowid` / `_rowid_` / `oid` 同样禁止**出现在 SQL 与列名里
   （带引号形态 `"rowid"`、`[rowid]`、`` `rowid` `` 一视同仁）。提到即 `DB_DENIED` +
   `details.reason = "reserved_column"`、`details.column = "_row_id"`。`SELECT *` **不会**
   把它带回来（结果投影层按列名剥掉），但 `INSERT INTO b SELECT * FROM a` 走 `db.exec`、
   **不经过投影**，列数语义要你自己对齐。
3. 应用**无状态**：实例每个请求新建，全局变量存不住任何东西 —— 状态只能进数据库。
   **同一应用内所有用户共享数据**；要区分用户就在自己的表里加一列存 `user.username`。
   **cookie 不可用**：自定义协议下 `document.cookie` 恒为空、`Set-Cookie` 不落盘。
4. **stdout 只写协议帧**（`RS` + 十进制长度 + `\n` + JSON）；**日志走 `log` 宿主调用**
   （单条不超过 4 KiB，每请求最多 100 条，超出丢弃并回计数；level 空串回落 `info`）。
   **事务里只允许 `db.query` / `db.exec` 与两个出口 `tx_commit` / `tx_rollback`**：
   `log` / `assets.read` / `db.define` 与再开一个事务一律 `DB_DENIED`，事务超时（5 秒）强制回滚。
5. **服务端 wasm 侧没有任何 AI 能力**：八个宿主方法里没有 AI。应用里的 AI 只能由
   **应用前端**调保留路径 `POST /__picoaide/ai/chat`（**双下划线**，客户端本地处理、
   绝不转发平台），结果再 POST 回应用自己的路由落库。老写法 `ai.chat` 不存在。
6. **不能主动发起网络请求、不能读文件、不能开线程**（**不要对外说成"不能联网"**：
   CSP 不约束顶层导航与弹窗）；HTML/CSS/JS/图片都必须编进 wasm（外链与对外 `fetch` 一律失败）。
7. **准入由你自己判**：入口第一件事就是 `assets.read("picoaide.app.json")` 读 `whitelist`
   并比对 `user.username` / `user.id`；无权限页**必须显示本人账号**，这是作者发现名单
   拼错的唯一途径。平台只把 `auth.mode` 注入帧，**不比对名单**。
8. **平台不提供员工名录**：名单只能手填已知账号；**改名单 = 发一个新版本**，运行期改不了。
9. **不要依赖 `$HOME`**：四条状态目录（`GOCACHE`/`GOMODCACHE`/`GOPATH`/`TMPDIR`）**必须**
   指向会话工作区，否则你会看到 `package fmt is not in std` 这种指向完全错误方向的报错。
10. **发布前先本地自测**：Node 自带的 `node:wasi` + `node:sqlite` 零依赖就能跑产物
    （`preview.mjs`，数据落本地库、可用 `--dump-tables` 看），通过后再走
    `wasm_app_validate` → `wasm_app_publish`。
11. **应用名就是标识**：`app_id` 同时是应用 origin 的 host 段（`<渠道 app 源 scheme>://<app_id>/`，
    渠道参数化：official/beta 取值 `picoaide-app`）；小写字母/数字/连字符、不超过 63 个字符、
    不能纯数字、不能 `xn--` 开头、不能是平台保留字；**一经发布不能改名**，也不能与别人的
    应用重名（同名不同人是不同的应用）。

## 应用里的 AI：客户端 AI loop

**权威链路**（术语统一叫 **客户端 AI loop**，"前端桥"只是其中一段）：

```
应用前端 JS  —— POST /__picoaide/ai/chat（双下划线保留路径）
        │
        ▼  宿主协议 handler **本地**处理，绝不转发平台
   ① 首次授权闸门（按 用户 × 应用 记录）
   ② 该应用的隐藏会话 `app:<app_id>`（不出现在侧边栏，诊断可查）
   ③ 桌面客户端跑一轮 ctx.agentLoop（工具集为空，只带本次 messages）
   ④ assistant 增量以 SSE 回给应用页
```

- **路径**：`POST /__picoaide/ai/chat`（**双下划线**）。整个 `__picoaide/` 是宿主保留命名空间：
  只有这一条路径存在，其余一律 404，**不会**进到你的 wasm（请求在宿主层就被截走）。
  ⇒ **随包资源不得占用 `__picoaide/` 前缀**：发布期直接拒（`ASSET_DENIED` +
  `details.reason = "reserved_path_prefix"`）。应用内部就算写了同名路由也没用 ——
  它永远收不到那个请求。
- **请求契约**：`{"messages":[{"role":"user"|"assistant","content":"…"}],"stream":true|false}`；
  **未知字段一律拒**；`messages` 最多 64 条、单条正文不超过 16 KiB（超限回 400），
  `stream` 缺省 `true`。
- **响应**：`stream:true` ⇒ `text/event-stream`，`delta` 事件带增量、`done` 收尾带全文；
  `stream:false` ⇒ 一次性 `{"content":"…","usage":{…}}`。
- **只做对话**：没有工具、没有文件、没有连接器、没有记忆、没有用户的其它会话。
  应用**不能**声明系统提示 / 模型 / 温度 —— **平台统一注入一条固定系统提示**
  （`APP_AI_SYSTEM_PROMPT`），并且**不注入记忆、不注入用户的历史会话**；
  请求体里只有平台提示 + 本次 `messages`。
- **多轮**：隐藏会话 `app:<app_id>` 承载上下文，但**只有你这次传的 messages 会进模型**；
  需要多轮就把历史一起传（传累积历史即可，宿主会按最长公共前缀只喂新增的尾巴）。
- **授权**：首次调用弹一次性说明卡，用户同意后按 用户 × 应用 记一次。
  **撤销的唯一入口是应用详情页的 AI 面板里的「撤销授权」按钮**（客户端设置页里**没有**
  这个入口）。未授权/已撤销 ⇒ 403 `app_ai_denied`，且**不消耗任何 token**。
- **计费与归因**：走**使用者本人**既有的 LLM 链路（扣他自己的余额）、用平台统一默认模型。
  ⚠️ **应用维度用量归因尚未接通**：客户端/宿主不出站 `X-Pico-App-Id` 头，服务端只按该头
  归因 ⇒ **不要向用户承诺"能在应用详情页看到这个应用的 AI 用量"**（应用详情页也不显示）。
  唯一能看到的是管理端 webadmin 的应用中心看板，它在窗口内没有归因数据时显示
  「统计尚未上线：暂无应用归因」——那不是"零调用"，是"还没开始统计"。
- **并发与超时**：AI 桥**没有自己的超时预算**（宿主给普通应用请求设的那条预算
  **对它不适用**），唯一边界是**页面关闭 / 导航离开**触发的 abort 与下游 LLM 链路；
  并发按**隐藏会话串行**—— 同一应用的第二个请求会**排队**，不是被拒绝。
- **仅前台**：应用页面一关闭，这一轮就被取消 —— **不存在**后台跑 AI 的通道。
- **六个错误码**（一律 JSON 信封，`stream` 下以 `error` 事件给出）：

  | 码 | HTTP | 含义与处置 |
  | --- | --- | --- |
  | `app_ai_denied` | 403 | 使用者尚未授权（或已撤销）⇒ 引导他点开应用详情页的 AI 面板授权 |
  | `app_ai_unavailable` | 503 / 401 | 客户端 AI 不可用 / 未登录 ⇒ 提示稍后重试，不要绕回 wasm 自己实现 |
  | `app_ai_invalid` | 400 / 405 / 413 | 请求体不合法、方法不是 POST、或请求体过大 ⇒ 修请求 |
  | `ai_balance_insufficient` | 402 | 使用者余额不足 ⇒ 提示他去客户端看余额，**不显示金额、不要重试** |
  | `ai_rate_limited` | 429 | 上游限流 ⇒ 稍后重试，不要在循环里猛调 |
  | `ai_cancelled` | 499 | 页面关闭或主动取消 ⇒ **正常收尾**，不要当故障弹错 |

- **老应用迁移（硬切，不静默）**：`ai.chat` **从来不是** WASI 导入，而是 stdout 上
  JSON-RPC 的宿主方法名；平台也**不做反编译**。所以仍调用它的老产物**会通过发布校验**，
  直到**运行期第一次调用**才失败：JSON-RPC error `code = "NOT_FOUND"`、message 逐字
  **`未知的宿主方法: ai.chat`**（纵深还有一条 `HOST_METHOD_UNKNOWN`，它的 hints 会列出
  可用能力：`db.define, db.query, db.exec, tx_begin, tx_commit, tx_rollback, log, assets.read`）。
  唯一的迁移形态：**前端调 AI loop → 结果 POST 回应用自己的路由 → wasm 落库**，
  wasm 侧一行 AI 调用都没有。

## 存储放哪里（**选错会丢数据**）

| 存储 | 可用 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| 服务端**应用库** `db.*` | ✅ | **不随清缓存 / 切账号被清**；跨设备一致 | **一切要留存的东西**（业务数据、设置） |
| `localStorage` | ✅ | 按 origin 隔离；**随客户端清缓存 / 切账号被清** | 可再生的界面偏好 |
| `sessionStorage` | ✅ | 同上，且随窗口关闭消失 | 单次打开的临时态 |
| `IndexedDB` | ✅ | 按 origin 隔离；**随清缓存 / 切账号被清** | 体积较大的可再生素材缓存 |
| **`Cache Storage`（`caches.open` / SW 缓存）** | ❌ **禁止依赖** | — | `caches.open()` 会成功，但 `cache.put(new Request('<app scheme>://…'))` 必抛 **`TypeError: … Request scheme '<app scheme>' is unsupported`**；不要写"离线优先" |
| cookie | ❌ | — | `document.cookie` 恒为空、`Set-Cookie` 不落盘（自定义协议下没有 cookie 语义） |

⇒ **要留存 → 放应用库；浏览器存储只当可再生的缓存。**

## 包内资源与保密（放机密之前必读）

- **保留资源只有一个：`picoaide.app.json`**（平台在发布期写入，**永不直出**）。
- **其余包内文件会被宿主按路径直出给任何能打开应用的人** —— HTML/JS/CSS/图片/字体/数据文件
  都是如此，**与 `access` 无关**（登录只决定**谁**能打开应用）。
  ⇒ **不要把机密、账号名单、内部说明、口令、内网地址放进非保留资源**：
  `GET /data/users.json` 任何能打开应用的人都能拿到。
- **名单放 `picoaide.app.json`**（`whitelist` 字段）：它是保留资源，只有应用自己用
  `assets.read` 读得到。用 `pack-assets.mjs` 加不进去（脚本直接拒）。
- `assets.read` 的结果**必带判别字段 `encoding`**（`text` / `base64` / `empty`），
  按它决定读哪个字段，不要用 `size == 0` 猜。

## 并发与队列（默认值，运维可在控制台改）

同一应用默认最多 **4 个请求并发**（读并发；**写仍串行**，SQLite 只有一个写者）。
但**单个用户在同一应用内默认只有 1 路**（`user_per_app_running=1`）：自测时用同一个账号
打并发看不到 4 路，这是**排队规则不是平台串行**（被排队的只是同一个用户）——不同账号才吃满 4 路。

队列 32、每用户同应用排队 4 个、每用户跨应用在跑 4 个、全局实例 32 都是**默认值**，
不是固定值：运维可在控制台「应用中心 → 限制项」改（队列可调到 4096、全局实例可调到 256）。
作者不可调（运维可在控制台「应用中心 → 限制项」改）；撞到 `APP_QUEUE_FULL` / 429 时按
`references/diagnostics.md` 处理。

## 窗口尺寸（`window.*`，可选）

`picoaide.app.json` 的 `config` 里可以声明窗口：

| 字段 | 取值 | 语义 |
| --- | --- | --- |
| `window.ratio` | `"W:H"`（如 `"16:9"`）或浮点（如 `1.7778`） | **强制锁定**的宽高比（客户端 resize 时按比例约束）；**合法区间 `0.25`–`4.0`**，越界（含 `0`/负数/非数字）⇒ **发布期 `APP_CONFIG_INVALID`** |
| `window.width` / `window.height` | 像素数字，可选 | 首次打开的默认尺寸；缺省 **1280×720**，写了 ratio 时按比例校正 |

`ratio` 是**锁定**不是建议：布局要能适配同一比例下的不同像素尺寸；窗口尺寸只决定
"首开默认"，之后由客户端按应用/按用户记忆。布局请用响应式（宽度变化时不要错位）。

## 三条最容易踩的坑

- **把日志打到 stdout**：非 `RS` 开头的输出会被平台当日志丢掉（不会污染协议，但你也看不到
  级别/条数管理）—— 用 `log` 宿主调用。
- **把不该做的事放进事务**：事务内只允许 `db.query` / `db.exec` + 两个出口 `tx_commit` /
  `tx_rollback`；`log` / `assets.read`（`details.kind = "blocking_capability"`）、`db.define`
  （`kind = "ddl"`）与再开一个事务（`kind = "nested_tx"`）一律 `DB_DENIED`；
  事务超时（5 秒）**强制回滚**。需要它们就先提交事务再做。
- **表结构想改就改**：不能用 DDL，也不能自动迁移；改结构 = 用 `db.define` 建新表或加列，
  自己搬数据（一个应用最多 16 张表、每张最多 16 列，平台的 `_row_id` 不占列配额）。

## 数据边界（要主动告诉用户）

这是一个**内部小工具**：同一应用里所有人看到同一份数据，平台不做行级隔离（要隔离就自己
加一列存 `user.username` 并在每条 SQL 里带上它）；应用在客户端内以独立 origin
（`<渠道 app 源 scheme>://<app_id>`，渠道参数化）打开，与主站、与其它应用都不同源，
但**应用拿不到任何平台凭证**，宿主只会告诉它"当前使用者是谁"。
需要"按人隔离"或"敏感数据"时，先跟用户确认再动手 —— 并在设计卡的「数据」一段里写清楚。
