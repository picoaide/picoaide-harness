访问模式

平台只注入模式与身份，名单由应用自己比对（R24）

login 与 whitelist 的区别

login：要求登录。登录后全员可用 —— 平台注入身份，应用不需要任何登录逻辑。

whitelist：要求登录 且 应用自己比对名单。平台同样只注入身份与 auth.mode，不比对、也不校验名单里的账号是否存在 （否则等于账号枚举接口）。

R24：名单判定永远在应用侧 —— 入口第一件事就是读自己的 picoaide.app.json 比对，不在名单里返回 403 页面并 显示本人账号（那是作者发现名单拼错的唯一途径）。

名单必须放 picoaide.app.json（平台保留资源，永不直出）； 放进会被直出的非保留资源，等于把名单公开给任何能打开应用的人。

10

存储边界

要留存的东西放应用库；浏览器存储只当可再生的缓存

  • db.*（服务端应用库） 不随清缓存 / 切账号丢失，跨设备一致 —— 一切要留存的东西（业务数据、设置）
  • localStorage 按 origin 隔离；随客户端清缓存 / 切账号被清 —— 只放可再生的界面偏好
  • sessionStorage 同上，且随窗口关闭消失 —— 单次打开的临时态
  • IndexedDB 按 origin 隔离；随清缓存 / 切账号被清 —— 体积较大的可再生素材缓存
  • Cache Storage 不可用：caches.open() 会成功，但 cache.put(new Request('<app scheme>://…')) 必抛 TypeError —— 不要写「离线优先」
  • cookie 不可用：document.cookie 恒为空、 Set-Cookie 不落盘；帧里的 headers 也不含 Cookie

页面里的「历史」那一屏读的就是应用库中的真实数据，可以拿来对照： 换账号、清缓存之后它还在。
